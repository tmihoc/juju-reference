# Skeleton v5.5 for entity reference pages (proposal, session 79, 2026-10-20; v5 plus the E21 to E21d corrections and the E31 removal of topic labels)

Status: proposed, not ratified; supersedes the typed/layered forms. Every rule below cites the experiment in `structure-discovery-plan.md` that supports it; rules without a citation are conventions and carry the tag `convention`.

## What the evidence says the skeleton must be

1. **Parts are conditional on artifact classes, not typed templates.** Over 36 domains only state is universal; 11 parts give 28 distinct part sets (E19). Typed templates fit poorly (typing C needs 10 types for 81% leave-one-out accuracy, E17b). So the skeleton is a fixed spine plus parts printed only when their artifact class is non-empty at an exposed tier.
2. **Spine = identity and state; for a topic that earns a page, also interface, dynamics and failure.** Among the 15 paged domains interface is present in 100%, dynamics and failure in 93% (E19b, post hoc, n = 15; E21 agrees on 5 further topics). Observation (67%), agent (73%), removal (53%), status (40%), configuration and the migration exceptions are conditional. Identity states, besides the name and multiplicities, the **scope** (controller database, model database, or both) and the **lifecycle** (life column present or not). Scope and life together predict the removal mechanism (life column in the model schema implies a removal job, 6 of 6) and the observation part (89% against 58%); migration facets are not predictable from the schema (E17b, corrected by E21). Scope, life, status tables, watched tables and immutable tables are version-stable and change exactly where the schema changes (E15, E15b).
3. **Page unit = a noun of the exposed interface.** Entity pages exist for domains with a client or cross-process artifact (15 of 15 import-exposed, E20; the measure undercounts, since facades reach services through interfaces and CLI, config and HTTP surfaces were not counted, so the rule is consistent with the pages but not yet tested with a correct exposure measure). A page may draw on several domains and a domain may carry several pages (network: space, subnet, zone). Topics with only internal artifacts (T3) get no page; their facts stay in `doc.go` and the schema (E11 tiers, E20).
4. **Statements come from the code, with a gate.** 94% of the claims of four hand-written pages are decidable by the code and 29% of the conceptual ones fail (E13, E14); human reference pages carry almost no identifiers (E16). Every statement cites an artifact, or is tagged `convention`.
5. **Parts are separable kinds of sentence** (kappa 0.87, E7 to E10): identity, interface, state, dynamics, agent, observation, failure, plus the annotations applicability and guidance.

## The page

| Part | Present when | Rendered from (artifact) | Tier |
|---|---|---|---|
| Identity | always | schema (tables, scope, life column), service and state code for how the entity comes into being and goes away (four recurring kinds over 36 domains, E24: life column with states (8), deleted by an operation (19), expired by a worker or timer (7), append-only or removed only by cascade (9); a domain may have several) | T1 |
| State | always | tables, lookups (allowed values first, with the spelling of each value per surface: storage, API, CLI), views and read-time computed attributes (derived attributes), invariants tagged with their enforcement site (schema constraint, trigger, service check), explicit transition tables | T1 and cross-process |
| Interface | at least one channel reaches the entity | per channel type: API facade methods with parameters and authority; HTTP routes registered in `apiserver/apiserver.go` (generated, not enumerated: at least 19, among them backups, tools, resources, log sink, migration uploads, registration, SSH relay and tunnel, health, each with its own authorizer); CLI commands and flags (`cmd/juju`); hook tools (`internal/worker/uniter/runner/jujuc`); the local control socket; charm metadata and configuration keys | T1 |
| Dynamics | any mutating method exists in any domain that writes the entity, or a removal or migration facet with entity-specific rules | service mutators (the writer may be another domain's service), preconditions and effects; removal cascade and guards (shared Removal page, per-type row); migration only where the data is filtered, remapped or prechecked (model tables otherwise migrate generically, see the Migration page) | T1, T2 |
| Observation | a live stream is exposed beyond one process (client facades have almost none in 4.1: `WatchAll`, `WatchAllModels` and the summary watchers are not implemented, E25) | change-log namespaces and `Watch*` methods consumed by client or agent facades; trigger semantics, never method names | T1, T2 |
| Agent | a manifold or worker is keyed to the entity (its own process or engine is the strong case) | manifolds and workers keyed to the entity; workers that only consume its streams belong to the consumer's page | T2 |
| Failure | errors exist | error constants with reachability. Open (2026-10-20): whether an entity page has any failure part. Settled so far: each error is authored once, nested under the rule or operation that raises it; the lookup by message string is one generated index page for all entities. No per-page error section until that is decided. | T1, T2 |
| Configuration | operator-set keys or files exist for the entity | model, controller and provider configuration keys with type, default, mandatory, immutable and secret flags (`environs/config`, `internal/secrets/provider/*/config.go`), files and environment variables | T1 |
| Applicability, guidance | when the statement needs them | annotations on the statement they qualify (provider and version scope; obligations; deprecated or vestigial, since exposed is not always live) | convention |

Order: hard constraints from the evidence (E10): identity first; state before dynamics and failure; dynamics before failure. Beyond those the order is the user's decision of the causal chain, kept as a convention: records (state), change streams (observation), agent, operations (interface and dynamics, each operation naming its channel), then configuration and the failure index; observation and agent only when present. The evidence neither supports nor contradicts it.

## v5.2 corrections (E21b)
- **No topic labels (E31).** Identity states facts, each only when it is true: the scope (controller database, model database, or both); the life column and its states, or the deletion kind (deleted by an operation, expired, append-only or removed by cascade, deleted when its last referrer goes); the entities it attaches to ("applies to", named; true when at least three entities carry tables of its noun or a table attaches by foreign key); the tables it owns. The labels entity, facet, mechanism and vocabulary are not inputs to any rule: every facet tested has interface, dynamics and failure, and the label could not be derived from the facts for credentials and charm resources (identity without a life column). A topic can state two clauses at once (charm resources: own removal job, and attached to application, charm and unit).
- **Configuration.** A key has one home, the page of the entity it configures. The controller or model configuration page is a generated index of keys by owner. Per-key flags come from the key's own schema (provider schemas: mandatory, immutable, secret; controller config: the updatable set; model config: its own mechanism), and a flag the schema lacks is not printed.
- **Operation entries** carry: authority (required level; caller-scoped; owner by tag; none beyond login; inherited), the block kind the operation honours (change, remove, destroy), the mapping from error constants to facade error codes, and the actors that carry out its steps (a worker that consumes the entity's stream and writes the results is an actor of the operation, not an Agent part).
- **Migration** states the generic export, the legacy 3.6 import operation where the domain registers one, and any exception (filter, remap, precheck).
- **State** lists seeded rows (alpha space, reserved key comments) and synthetic keys that a view adds.
- **Removal** is stated in Dynamics for every entity, by one of three paths: a life column with a removal job (model-scope domains with a life table, 6 of 6; some life tables are advanced by their parent's removal), a removal job without a life column (secret, resource), or deletion by the cascade of another entity or by an operation.
- Page boundaries: a page may draw on several domains (ssh keys: four) and a domain may carry several pages (network: space, subnet, zone); operation, task and action are one table set and one page unit to be decided by the interface nouns.

## v5.3 corrections (E21c)
- **Parts are closed, entries are open.** Nine parts held on 368 artifacts of five further topics (3 fit none). New sub-kinds keep appearing (provider extension points, non-schema stores such as the status history log, stub facades, ordering dependencies between migration operations, hand-written exports); each is placed in the nearest part with a tag for its sub-kind, and the gate requires a citation, not membership of a closed list.
- **Invariants** carry an enforcement tag from: schema constraint, trigger, service check, facade check, comment only (not enforced). A comment is never evidence of enforcement.
- **Authority** adds the value parameter-dependent (for example `Force` needs superuser). **Block kind** states the chain (`RemoveAllowed` also checks the change block; `DestroyAllowed` checks destroy, remove and change). **Error-code mapping** is optional: many constants reach clients with no code.
- **Migration** also states ordering dependencies between import operations and blob transfer over HTTP where they exist.
- **Shared tables** (`relation_status`, owned by the status and the relation topics) have one stated home with a pointer from the other page. **Stub facades** (a facade whose methods all answer not implemented, while the real methods live in another facade) are listed as unavailable under the facade that serves the noun.
- **Status** is three things (per-entity status values: a facet; the history: a log store; the full-status aggregation: a read model) and is documented as such.


- Identity gains scope and lifecycle statements (E17).
- Observation lists only streams a client or agent can reach (model shrinks to the credential stream, machine gains two, E11).
- Dynamics gets the authority field and, for model-scope lifecycle entities, links to the Removal page (cascade, guards, force and wait); controller-scope lifecycle entities have no removal job type of their own and state how they go away instead: the controller node record is deleted as a step of removing the controller application's unit (`domain/removal/service/unit.go:338`); the object store backend's life column drives its drain, and blobs are removed by path (`domain/objectstore/service/service.go:402`) (E17, checked against the code).
- Migration is a shared mechanism (generic export of model tables); an entity names only its exceptions (E21, correcting E17b, which measured a legacy package).
- Authority is stated for reads as well as writes, as a value with a kind: required access level (72% of client methods), caller-scoped (results filtered by who asks), inherited (a version wrapper delegates), or none (pure or unimplemented); it can also depend on a parameter (E21, E23).
- A guard that one entity imposes on other entities' operations (block commands) is stated once on the page that owns it, with a pointer from each affected operation (E21).
- The claim gate trusts code, never code comments (five contradictions found, E21).
- Entities with no exposed artifact get no page (E20).
- A method that is exposed but answers NotImplemented or NotSupported is listed as unavailable, never as an operation (E21, E25).
- Part presence is generated, not authored; the page never prints an empty part (E19: 28 distinct part sets).
