## The registered rules

**P — scope and control:** distinguish (a) a target invariant demonstrated on the supported path, (b) a selector rule made by a particular interface, and (c) shared behavior actually applying across multiple interactions. Present target facts at the target, selector conditions with their interface, and a genuinely common rule at a shared address; link them. An address may be a page or section. Per-interaction differences must remain local. The links and one-home practice are editorial conventions. P's source-grounded classification of facts is not proof that a particular file is uniquely right.

**U — target-centered:** put all facts concerning the model under the model, including the selector. This can remain completely accurate if the tool and conditions are explicitly qualified and linked; it does not have to assert that name alone is unique. **I — interface copies:** put the complete same rule at each relevant interface. ## Case 1: qualified model identity versus DB REPL selection

A controller model has a UUID, name and qualifier; the release schema has a unique index on `(name, qualifier)`, **not on name alone** (`domain/schema/controller/4.0.15-controller-release.ddl:395-429`). For the DB REPL, `.switch controller` selects the controller database; `.switch model-<name>` strips the prefix and executes `SELECT uuid FROM model WHERE name=?` using `QueryRowContext(...).Scan`, then passes the resulting UUID to the database getter (`internal/worker/dbrepl/worker.go:277-318`). There is no qualifier predicate, ambiguity check, or ordering in that query. `.open <model-uuid>` instead passes the supplied UUID to the getter (`worker.go:320-335`). These are **tool-specific** selectors; the schema's qualified identity rule remains a separate fact.

**Synthetic smoke:** an in-memory SQLite database loaded the actual `CREATE TABLE model` and `idx_model_qualified_name` from `domain/schema/controller/sql/0007-model.sql:25-59`, with SQLite foreign-key enforcement off for the isolated schema. It inserted synthetic `demo/alice` and `demo/bob`, printed both rows, and the exact name-only query's `fetchone()` returned one row (`id-a` in this run). A second `demo/alice` insertion produced `IntegrityError`. This exercises the real schema and SQL shape, not `execSwitch`, a Juju database, the SQL driver's `QueryRow` implementation, or a live controller. Without `ORDER BY`, do not claim which matching UUID a real controller chooses. The source path does not explicitly report ambiguity before opening the UUID returned by `QueryRow`.

**Risk/lead:** an operator using name-only `.switch` in a controller with same-name models may not be selecting the intended owner's model; subsequent DB REPL SQL can modify state. This is a source-based possibility with a synthetic SQL exercise, not a demonstrated live incident. Use a known model UUID with `.open` when disambiguation is needed; choosing the right UUID and database access remain the operator's responsibility. Record the unresolved contract/possible defect rather than rewriting docs as if collision resolution were verified.

**Same-facts placements:** P states `(name, qualifier)` uniqueness under model and the name-only query, no ambiguity check and UUID selection at the DB REPL, with a cross-link. U puts both fully qualified descriptions under model and links there from the REPL. I repeats both full descriptions in each entry. None need misstate behavior. P's operational reason is that the REPL controls its selector whereas the model's qualified identity is not defined by the REPL; it does not prove U is semantically invalid or measure which layout users prefer.

**Behavioral verdict:** supported on the cited schema, query/caller path and synthetic SQL. No live `.switch` or controller was exercised. No prior source trace of the same-name selector was found in the searched history; the broad model and tool facts were already known.

## Case 2: CLI plugin context versus remote model identity

The ordinary non-embedded Juju CLI tries a `juju-<subcommand>` executable for a missing built-in command (`cmd/juju/commands/main.go:225-242`; `cmd/juju/commands/plugin.go:51-79`). Its argument extractor recognizes the four **separate tokens** `-m`, `--model`, `-c`, `--controller` and takes the following argument. For a nonempty parsed model or controller flag it overrides the corresponding variable in the child environment; otherwise it retains the inherited environment. It forwards the original plugin arguments and streams (`plugin.go:29-48,99-129`). Equal-sign tokens such as `--model=newmodel` do not equal the recognized token `--model` and are not used by this extractor; they are still forwarded to the child. A plugin might itself parse them: Juju's child environment alone does not establish its final choice or a valid remote model.

**Real CLI smoke:** two temporary executable plugins on a temporary PATH printed their received environment. Running the actual 4.1 CLI `go run ./cmd/juju e64probe -m newmodel -c newcontroller` with inherited `JUJU_MODEL=oldmodel` and `JUJU_CONTROLLER=oldcontroller` printed `newmodel` and `newcontroller`, and the child received the original flags. With no flags it printed the inherited values. With `--model=newmodel` it printed the inherited `oldmodel` and received the equals-form argument. A second distinct plugin command `e64other -m newmodel -c newcontroller` likewise received the overridden values. Scripts and temporary directory were removed. These are actual local Juju plugin-dispatch and subprocess observations, not a controller login, model lookup or external plugin's own option handling.

**Same-facts placements:** P locates plugin flag/environment precedence with the plugin invocation interface, linking the model/controller identifiers and generic CLI environment rather than presenting it as a property of model state. U can put the same fully qualified plugin behavior under the model and link from the plugin interface. I can repeat it for each plugin command; arbitrary external plugins mean the actual generated family is not bounded by the two examples. Both U and I can accurately describe the child environment and the equals-form exception; neither is falsified merely because P is more closely scoped.

**Behavioral verdict:** supported by source and actual local subprocess execution for the tested forms and two distinct synthetic plugins. It is not a complete plugin flag parser, external plugin behavior or controller authorization audit. The exact precedence path was not found in the searched reference/history; broad plugin propagation was already known.

## What E64 resolves—and what it does not

**Supported and operational:** identify a model's qualified identity separately from `.switch` and `.open` selection; identify plugin environment composition separately from the remote model's state. This predicts which conditions must accompany each fact, and catches an incorrect inference that name-only REPL selection must disambiguate owners. Shared plugin dispatch supports a reusable contract for the two traced invocations; its flags and inherited environment conditions must be preserved. For applicable entity roles retain the user's settled causal order. The useful rule concerns *semantic scope*, not Go package placement, SQL names, questions or present filenames.

**Not resolved:** U and I can preserve the same facts as P; P's placement and one-home practice remain editorial preferences. In particular, a standalone shared page reduces exposure to the specified hypothetical parent move but adds one page; a section avoids that page but depends on the parent address. No source observation proves which tradeoff readers or maintainers prefer. The bounded tests do not choose a site-wide physical-file policy, prove coverage for every reference entry, or establish that the earlier primitive/attribute hypothesis is wrong. No human raters were used.

**Candidate, not approved documentation:** put interface-specific selection behavior at the interface and the target's invariant at its target; link a source-demonstrated common contract where repeated. Prefer a section when it is a facet of one interface, a standalone page for a subject or mechanism whose semantics demonstrably span otherwise independent entries, but leave file-level ties open when both meet the same requirements. This is a consistent working policy, not a source theorem or an authorization to implement. The existing question-as-relevance rule and user's sequence gate still apply.
