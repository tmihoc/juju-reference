# Bounded surface probe -- session 111

## Registration (before tracing)

Question: can a bounded, runtime-reachable API surface be inventoried and reconciled to reader questions and existing story owners without treating package layout or an interface registry as the documentation universe?

Scope: the client-facing secrets facade on the 4.1 anchor. Discover its actual registration and callable exported methods, then trace their request/result surfaces and locate their existing reference owners. For each method record a named client question, disposition and evidence; distinguish shared subject vocabulary or behavior from call-specific contracts. Check the facade's registration and any conditional exposure or permissions, and identify asynchronous or non-facade surfaces as explicitly outside the sample. Do not treat listed methods alone as proof of runtime reachability, exhaustive error coverage, every supported version, all secret surfaces or global completeness.

Decision rule: the probe succeeds only if its method roster is explicitly bounded to a traced registered version and every method is reconciled or its uncertainty recorded, including at least one concrete question that crosses methods or exposes an ownership conflict. A declaration without proof of registration is not a callable-method inventory. A current page heading alone is not proof the implementation matches it. A missing or ambiguous owner is reported, not filled by assertion. Stop after this one facade; do not modify documentation or claim reader benefit. Source tracing is not a live-controller test.

### Cross-method result: share concepts, not all validation

A client needs to understand the URI returned by creation and label used in listing, updates, deletion and grants; `secret.md:32-41` defines URI/name/label inside the database section although both API requests and responses carry them. A shared vocabulary home is still a proposal, not an authorized edit or a uniquely selected heading.

**A critical boundary:** a common selector helper does not imply the same contract for all calls. Update validates that exactly one of URI and existing label is supplied before looking up (`rpc/params/secrets.go:152-163`, `secrets.go:332-338`). Remove and grant/revoke call `secretURI`, which uses URI first when both are nonempty (`secrets.go:364-371,401-405,452-462`); grant/revoke separately checks for neither and returns `must specify either URI or name` at whole-call level (`:452-454`), while removal records the helper's `must specify either URI or label` per item (`:364-367,401-405`). `secret.md:250,260` states the update distinction and `:223` the grant error; removal's error list at `:310-315` does not list the missing-selector error. Treat that as a source-traced candidate gap; no live API test or error-code attribution was done. Put shared meaning once, but preserve call-specific selection, precedence, validation order and error placement with the calls. Do not turn the shared behavior proposal into a blanket rule that URI and label are mutually exclusive.

### Registration anomaly and limits

The same smoke program printed six reflected methods for v1 as well, because its registry entry claims `*SecretsAPI` even though its factory returns `*SecretsAPIV1` (`register.go:17-31`). The program separately observed that the wrapper type is not assignable to the registered type; `root.go:627-635` rejects such a factory result after successful construction. This is a source-traced likely v1 runtime defect, **not a live facade call**, and it means the advertised v1 method list must not be counted as proven callable. Do not change Juju code or documentation on this observation alone; trace real client negotiation and reproduce with an authorized live or realistic facade invocation before assigning impact.

One facade is not the secrets universe: hook commands, agent/controller facades, watchers, CLI, status, logs, database inspection, provider differences and other versions or configurations were not inventoried. The six rows answer one client-facing slice, not every reader question, schema, error, or exposed surface. The probe was preregistered above before source tracing, rather than in `structure-discovery-plan.md` as the handoff convention specifies; this is a recording-location deviation, not an after-the-fact prediction.
