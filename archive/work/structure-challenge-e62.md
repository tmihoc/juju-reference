# E62 — Testing the organizing principles

## Question, result and scope

E62 was registered in `structure-discovery-plan.md` before this session's case source inspections. It asks whether contracts must be organized as attributes of one notion, whether relationships and mechanisms need representation, and whether a call-only form can express the same behavior. **All three registered behavioral paths meet their bounded evidence criteria**, but the first is not a genuinely new challenge to the project: the pre-existing `object-store.md:24-32,118-123` already states the shared-path and last-path deletion behavior. That comparison was noticed after registration. The case independently re-traces the implementation but cannot establish a held-out win over the prior reference work. The result does not prove one reference architecture, a unique page hierarchy, global completeness or reader benefit. Other nouns and some surrounding behavior had also appeared in prior maps; the specifically traced status-history and tagging paths were not claimed as wholly unknown subjects. Paths are relative to `/tmp/juju-41-tree` at `e5db99d585`.

The source establishes what inputs and outcomes matter, not what counts as an indivisible notion. In particular, the preregistered single-subject alternative is **underspecified**: if an arbitrarily broad subject may include every related object or its entire history as an attribute, the observed relationships cannot falsify that alternative. If it means a narrowly local current record alone, the cases below contradict it. That narrower reading is a post-hoc qualification, not a registered universal failure. We cannot honestly declare the user's earlier primitive/attribute hypothesis refuted or proven from this test.

### 1. A reference, content and a deletion

`object_store_metadata_path` keys paths separately and references a digest/size metadata row; digests have unique indexes (`domain/schema/model/sql/0006-objectstore-metadata.sql:1-33`). On the file-backed put path the contents are hashed and persisted, then metadata is associated with the path (`internal/objectstore/fileobjectstore.go:776-845`). When an equal digest and size already exist, the state insertion looks up the existing metadata UUID and inserts a different path (`domain/objectstore/state/state.go:294-359,362-376`).

`RemoveMetadata` removes a particular path and counts the remaining paths for its metadata UUID; if any remain, it retains the metadata and placement; otherwise it deletes those records (`domain/objectstore/state/state.go:439-529`). The file backend then checks for remaining metadata for the hash and deletes the underlying file only if none is found (`internal/objectstore/fileobjectstore.go:873-898`). This deduction requires the calls to reach these branches and succeed; it does not promise concurrent or cross-controller behavior, a successful future read, or behavior of every backend. `juju-db-repl` can open a model database and query these rows (`internal/worker/dbrepl/worker.go:237-269,320-335,781-785`), satisfying E62's supported-inspector criterion. The investigating agent did not establish that surface; it was independently traced here, not assumed absent.

**Smoke:** an in-memory SQLite database loaded the actual object-store DDL. Using synthetic hashes and two paths, equivalent SQL for insertion, lookup and the reference-count branch printed `after puts: 2 paths, 1 content`; `after removing /one: 1 path, 1 content`; `after removing /two: 0 paths, 0 content`. This exercises schema and the selected SQL semantics, not the Go state service, a file backend or a controller.

**Structural implication.** A path, its shared content and the removal interaction have distinct identities/effects. They can be explained as linked facets of an object-store subject or as separately addressed relations; this evidence does not select a physical file or prove that either representation is uniquely correct.

### 2. A current status and a historical observation

For a unit's workload and agent status respectively, the service first writes the current state and returns immediately if that write fails. It then calls `RecordStatus`; if that call returns an error, it logs a warning and still returns nil (`domain/status/service/service.go:401-424,452-484`). The agent path adds its own status validation, including a required message for `error`; workload validation is separate. The current unit-agent row uses an upsert (`domain/status/state/model/modelstate.go:1454-1487`).

The history recorder builds a status-history log record; it can return an error when serializing data, while its `Logf` call does not return a delivery result (`internal/statushistory/statushistory.go:74-89`; `internal/statushistory/logger.go:27-50`). Both status encoders also serialize data before the current write (`domain/status/service/status.go:237-257,293-313`), so **do not assert that a particular normal API input reaches the post-write error branch**, or that a log transport failure is detected. The service's branching is conditional source behavior, not observed data loss.

An authorized client can call `StatusHistory`, which validates a single request and delegates to the status-history reader (`apiserver/facades/client/client/status.go:53-109`; `cmd/juju/status/history.go:213-268`). The reader scans log records for the requested model and status-history labels and the service filters by kind, tag and optional time/count (`internal/statushistory/statushistory.go:127-137,147-206`; `domain/status/service/statushistory.go:17-58,61-125`). Model domain services obtain a per-model logger context (`internal/worker/domainservices/worker.go:230-262`); the model log writer attaches the model UUID (`internal/worker/logsink/loggers.go:133-145`), while the status service reads `logsink.log` (`domain/services/model.go:303-316`). Actual routing, retention, cross-node history and live completeness remain unproved.

**Smoke:** a temporary Go program called the real `StatusHistoryReader.Walk` on two synthetic log streams and printed `current=active history=[blocked active]` and `current=active history=[maintenance active]`. `current=active` was an input label in the probe, not a database read. The program was removed. The example demonstrates the reader can represent two histories with the same supplied current value; it does not run the setter, logger, API or a controller.

**Post-hoc history-kind discrepancy, exercised in-process:** The real `juju help show-status-log` lists `filesystem`, `volume`, `task`, `saas`, `container` and `juju-container`, and `HistoryKind.Valid()` accepts them (`core/status/status_history.go:73-115`). The history service's `matches` switch handles other kinds but falls through for those six; its caller checks `!ok` before `err`, so the default error is discarded and the record is skipped (`domain/status/service/statushistory.go:29-43,74-104`). A throwaway Go program invoked the real `GetStatusHistory` and real history reader using synthetic matching log records: `kind=workload valid=true matched=1 error=<nil>`; `kind=filesystem valid=true matched=0 error=<nil>`. The probe and its directory were removed. This demonstrates the actual service behavior for those synthetic inputs, not a live controller, stored filesystem history, RPC or CLI request. The CLI returns `no status history available` when it receives no statuses from its clients (`cmd/juju/status/history.go:266-287`), but whether a particular end-to-end request reaches that response is unverified. Treat this as a potential code/contract defect to investigate, not a reason to conceal the issue by documenting a false success. The registered E62 status case is the separately traced unit/workload path and is not re-scored.

**Structural implication.** Current state and history have different data and observation conditions. An entry for a unit can contain both as attributes; an independently linkable history mechanism can also be sensible. The evidence distinguishes the contracts, not a mandatory top-level status-history page or one uniquely correct owner.

**Post-hoc cross-subject check:** The same current-write → history-attempt → warn-on-recorder-error sequence appears in the traced application, machine and cloud-instance status setters (`domain/status/service/service.go:281-311,749-781,919-944`). This supports a candidate shared status-history rule spanning more than one entity, while each setter's validation and caller remain specific. It does not establish every status writer or enforce a shared implementation. On the provisioner facade's instance-status path, `provisioning error` or `error` additionally triggers a machine-status write **after** the instance-status write (`apiserver/facades/agent/provisioner/provisioner.go:1092-1125`; `core/status/status.go:272-273`). The writes use separate state transactions (`domain/status/state/model/modelstate.go:2376-2429,2565-2618`); if the first succeeds and the second fails, the call can return an error after the first change. This conditional deduction is not a live failure. It shows why the shared history rule alone cannot replace the call-specific cross-subject effect. The registered equal-content two-call comparison below is unchanged.

### 3. Model tags, machine state and a provider request

The model provisioning prelude reads the `resource-tags` model configuration (`domain/provisioner/state/model/state.go:44-65,718-751`). For a selected machine, the service parses these values, combines them with model/controller UUIDs, machine name, controller role and principal unit names, and returns the resulting `Tags` (`domain/provisioner/service/service.go:236-246,257-268,451-488`; `internal/cloudconfig/instancecfg/instancecfg.go:1033-1042`; `environs/tags/tags.go:59-73`). The agent-facing `ProvisioningInfo` checks whether the authenticated agent may access the named machine and returns those tags (`apiserver/facades/agent/provisioner/provisioner.go:75-106`; `provisioninginfo.go:22-29,54-84,91-104`). This is a supported agent surface, not an operator-facing inventory of actual cloud labels.

For the traced EC2 start, the provisioner passes the tags through the instance configuration (`internal/provisionertask/provisioner_task.go:876-891,1027-1034,1499-1502`); EC2 adds a machine-derived `Name` and sends instance and root-volume tag specifications in `RunInstances` (`internal/provider/ec2/environ.go:686-703,705-723,726-743`). A provider failure may prevent an instance or tags from existing externally. The trace does not prove a cloud applied tags, later updates propagate, all providers behave alike, or a user can observe the provider's actual tags through this API.

**Smoke:** a temporary Go program called the real `environs/tags.ResourceTags` helper with the same synthetic `cost-centre=42` and controller UUID but two different model UUIDs. It printed the same custom value and controller plus the corresponding different model UUID for each call. It did not call the unexported machine composition, the agent API or EC2; the program was removed.

**Post-hoc distinction, not a separate held-out pass:** Juju also has a **`tags` constraint**, which MAAS converts into positive/negative node-selection tags (`internal/provider/maas/constraints.go:49-67`), while the EC2 validator registers that constraint as unsupported (`internal/provider/ec2/environ.go:265-284`). Those selection tags are not the EC2 resource-label map above. A shared word or database name is therefore not a safe chunking rule; a model setting, a machine-specific result and a provider interaction all contribute different conditions.

## Equal-content comparison: two unit-status interactions

This is a structural comparison, not a reader study. The same exact source rule **R** appears on both the `SetAgentStatus` and `SetUnitStatus` paths: *if the current status write fails, return its error without the history attempt; after success call the history recorder; if that call returns an error, warn but do not fail the setter.* Agent-status-specific validation (an `error` needs a message; `lost` and `allocating` are rejected) remains with the agent call. Workload-status encoding remains with the workload call. Actual API entry points and permissions are in `apiserver/facades/agent/uniter/status.go:58-98` and `apiserver/common/unitstatus.go:46-90`; the shared conditional sequence is in `domain/status/service/service.go:401-424,452-484`.

| Form | Same facts R, plus each call's own conditions | R statements | Links |
|---|---|---:|---:|
| C: call-only | Write R in full under each of the two setters; retain agent/workload differences at their calls. | 2 | 0 to a shared R |
| B: shared interaction rule | State R once in a status-history interaction section; link both setters to it and retain their individual differences at the calls. | 1 | 2 to R |

The fact set and condition order are held constant in this constructed comparison; the count is of statements of R, not a measurement of page length, navigation, user comprehension or performance. C is expressively valid: repetition alone does not falsify it. B reduces copies of R but adds indirection and requires checking that both code paths continue to obey R; the source has two similar implementations, not one enforced shared function. Choosing a home and a one-copy practice is an editorial decision, not a property proved by the source.

### Worked placement proposal: status history

Recommend a linkable **Status history recording** section on the existing status reference, rather than a separate new file. Its scope is the bounded shared recording behavior for the traced unit-agent, unit-workload, machine and cloud-instance status setters. State R once and say explicitly which traced setters it covers; link it from those calls. Keep unit-specific validation at the unit agent/workload calls, and keep the provisioner call's conditional instance-to-machine status write and possible partial result at that call. Explain the supported history query, filters and unverified retention separately from current status.

The reason for a shared status address is that the same conditional history behavior crosses unit and machine identities; choosing the existing `status` file is a conservative editorial choice that avoids a new file, **not** a consequence uniquely forced by the code. Call-local full copies remain semantically valid and have different navigation/maintenance tradeoffs. Existing `status.md:10-73` and unit/machine call anchors must be compared and preserved before any change; no heading or anchor has been added. Broader applications and untraced status writers must not silently inherit R.

## Outcome for the organizing principles

1. **Distinguish behavior before choosing its presentation.** At minimum, capture participating identities/scopes, relevant mutable state/history, conditions, operation, result and observation whenever they change the answer. The three cases each need more than a single current value; this is a finding about the traced contracts, not a fixed page template.
2. **Do not equate independent variation with a page.** Shared content, history or provider request fields may be separately described, nested or linked facets. The code proves distinctions and conditional effects, but not a unique physical home or the right total number of chunks.
3. **Treat both the old attribute-of-a-notion account and the current relationship/mechanism account as hypotheses.** A broader notion can contain related state and history; the test did not disprove that representation. Specify actual counterfactual ownership claims before a later falsification attempt rather than calling an extensible ontology disproved by definition.
4. **Shared versus call-specific is a conditional editorial tradeoff.** The controlled two-setter example shows one fewer duplicate rule statement with two links; it does not establish reader benefit, complete behavior or shared implementation. Preconditions or outcomes that differ must stay at their own calls.
5. **Update the candidate, not the docs.** Preserve the settled applicable entity-part ordering as an editorial decision; use interactions, participant conditions, state versus observation and platform/provider qualification when deriving content. Keep semantic-address and one-home choices provisional. Review status/history, object/path and model/machine/provider placement as explicitly linked candidate contracts. No documentation or repository rule change is authorized by E62.

## Limits

No Juju controller, agent, object store or cloud provider ran. SQLite used synthetic values against the real DDL; the history-reader and resource-tag helpers ran with synthetic inputs. The status history probe did not run writes or retention; the object probe did not run the Go object store; the tag probe did not execute per-machine composition or EC2. Prior E59, E60 and E61 outcomes are unchanged. The denied session-115 `WorkloadModel`, `HookCommandPages` and `KubernetesCloudAttributes` agents were not relaunched or worked around.
