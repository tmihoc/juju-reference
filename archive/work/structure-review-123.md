## Roles from contrasting subjects

A **character** is a subject-level notion; its **leg** is a dependent aspect of that subject. A **shared abstraction** is a source-demonstrated contract over notions in multiple pages, not a repeated word. A **semantic address** is a linkable location, whether page or section. These distinctions require examination of actual scope, participants, interactions and effects; identity, lifecycle, database table or number of uses alone is not a mechanical classification rule. Character versus leg is not the entire boundary rule: an actual cross-page abstraction can warrant a page too. If the relation to a parent or common abstraction remains uncertain, investigate and label it unresolved; equal-content layouts do not settle the classification.

Roles follow supported properties rather than fixed headings: a stream needs an actual holder/payload; an actor needs a traced action; a process uses its real phases; a tool needs invocation and selection, not an invented entity table. For applicable entity roles retain the user's causal order above, with necessary vocabulary before use. Each operation keeps actor, guard, target, timing, observable result and errors; CLI and other clients expose their own syntax/local behavior rather than owning platform semantics. Figures belong with the actual structure, dynamics or interaction illustrated, with source/model and accessibility checks separate from the outline.
