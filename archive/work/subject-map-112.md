## Status and reading key

This is a **working system-wide candidate**, not a proven complete inventory or an authorized docs change. It extends the source-grounded boundaries in `work/system-derivation-111.md` and `work/endpoint-boundary-111.md`; the surface ledger is `work/surface-ledger-112.md`. Source paths are relative to `/tmp/juju-41-tree` at `e5db99d585`; docs paths refer to the PR worktree at `48ef1fca17`. Evidence is source-traced unless a runtime check is explicitly named. Each row identifies a candidate address, not a proof that a separate physical page is necessary. Bracketed addresses are proposed subject-owned anchors, not assumed existing labels. A cited path is evidence for the bounded behavior in that row, not for all fields and calls of the subject.

The underlying graph is not an execution pipeline: users and agents interact with a controller; a controller manages models against clouds; model applications realize charm definitions as units; application endpoints compose relations, sometimes across models; units execute hooks and tasks; infrastructure and storage are provisioned from external providers; access, configuration, constraints, lifecycle processes and observation cut across these subjects. Conditions, authentication, provider behavior, concurrency and asynchronous progress limit prediction.

## Candidate internal form derived from the map

The useful unit is the subject or interaction, not a fixed schema/streams/calls template. At a stable address: identify the subject and scope; define its relationships and vocabulary before relying on them; state the shared behavior and independently varying state; then give subject-specific interactions and their actor, preconditions, effects, outcomes/errors and observation as applicable. Put a common contract at its subject/mechanism home, with call-specific differences alongside each call and links from affected subjects. State when a result is asynchronous, conditional on authorization/model/provider, or depends on external charm or cloud state. Persistence is included for supported, relevant inspection rather than forced on every subject. Independent aspects have no source-proven total order. Established page conventions, including the no-version-scoping decision, remain in force until the user explicitly authorizes any change; this form is a proposal, not a demonstrated improvement in human or AI findability.

Concrete predictions: a single unit's life may differ while its application remains; a relation's unit entry can be refused even if endpoints matched; an action run and an admin command can both create operation/tasks; and a provider precheck can still refuse a machine after constraint merge. Each is bounded by the cited path and not a promise that the overall deployment completes. A timer-driven hook shows why neither all events nor all failures can be deduced from database-change narratives.

## Review-bot implications

Use one shared, version-controlled human/bot guidance source, but do not modify repo guidance without authorization. Maintain a structured subject ledger with semantic address, scope, relationship/owner, supported surface, source revision and line anchors, conditionality, exclusions and investigation status. Deterministic checks may verify syntactic anchors, duplicate addresses, link targets, known title/file and section conventions, source-path existence and explicitly scoped inventory reconciliation. They cannot prove subject boundaries, audience relevance, actual factory authorization, source reachability, semantic correctness, completeness or message/code attribution. A bot should treat a heuristic discrepancy as a lead; trace real registration, factory/dispatch, runtime conditions and the relevant effect, then report evidence and uncertainty. API and doc changes both need to trigger relevant review. The proposed move of existing checker scripts remains separately awaiting the user's word.
