## `agent-version`

**Definition and boundary:** The model's target agent version and stream describe desired agent software; an agent reports its running version separately, and binary availability is another dependency. Neither a target value nor a client version alone proves every agent has upgraded (`apiserver/facades/client/modelmanager/modelmanager.go:1103-1108`; `internal/worker/upgrader/upgrader.go:125-135,170-187`).

1. **Target, reported version and binaries:** Distinguish target and actual versions, binary platform and stream; model info exposes the target. The controller-model target also drives the traced controller upgrade (`domain/controllerupgrader/service/service.go:342-384`).
2. **Version change stream and agent reaction:** In the traced upgrader, the agent reports its running version, waits for upgrade-step readiness, watches API version changes, then reads desired version. Equal or disallowed target is not upgraded; an already downloaded matching binary can produce an upgrade-ready result, otherwise the worker looks up tools (`internal/worker/upgrader/upgrader.go:125-155,158-210`). Watcher notification and later agent replacement are distinct; lookup/download can fail.
3. **Changing the target and observing progress:** Link rather than duplicate the controller upgrade process; the controller CLI calls the model-upgrader against the controller model, with optional target, stream and dry-run (`cmd/juju/commands/upgradecontroller.go:375-401,414-432`). 4. **Failure/compatibility index:** On this agent worker, cross-major downgrade is rejected, while the precise full compatibility matrix and subsequent restart/completion behavior are unresolved (`internal/worker/upgrader/upgrader.go:111-123,185-202`).

**Pending links:** agent, model, controller-upgrade, model upgrade and binary delivery. **Unresolved:** complete agent/binary distribution paths, stream selection, supported version matrix and rollout completion/failure conditions; no universal timing claim.

## `model-migration`

**Definition and boundary:** Migration transfers management of an existing model between source and target controllers; it is a multi-actor process, not equivalent to destroying and redeploying workloads (`apiserver/facades/client/controller/controller.go:623-665`; `work/control-infra-model-115.md`, “Removal and migration change different relationships”).

1. **Participants and request:** A controller superuser submits model and target information; the API reports a migration ID or error per model. Initiation is not completion (`apiserver/facades/client/controller/controller.go:623-665`). Source/target credentials, version compatibility, model and agents are separate prerequisites, to be described only for traced paths.
2. **Quiescence and prechecks:** The migration worker locks down concurrent activity, runs source and target prechecks, waits for agent/minion quiescence and runs prechecks again; errors or unsuccessful waits can enter abort (`internal/worker/migrationmaster/worker.go:298-320,413-473`). User API access is restricted differently for importing and exporting models; this is separate from upgrade restrictions (`apiserver/root.go:528-566`).
3. **Import and validation:** The source exports model state, imports it to target, uploads binaries, waits for agent validation, checks provider/target machine agreement and requests target activation. In this path activation prepares an import that remains gated; source and target conditions can abort or fail (`internal/worker/migrationmaster/worker.go:476-481,518-578,581-618`).
4. **Success, adoption, logs and reaping:** After entering success the worker waits for agent reports and requests target resource adoption; this is the target point of no return, not initial request acceptance or the earlier preparation. It transfers logs unless source Loki forwarding is enabled, then reaps the source model (`internal/worker/migrationmaster/worker.go:641-692,789-800`). The import can also handle external-controller references and target-wins image-metadata conflicts; link those subjects (`internal/migration/import.go:408-429,589-613`).
5. **Abort and failure index:** Earlier precheck/transfer failure may abort; target import cleanup on the traced abort path is best effort (`internal/worker/migrationmaster/worker.go:413-433,476-481,803-810`). Distinguish phase, per-model request error and eventual result; never promise automatic recovery or all-or-nothing rollback.

**Pending links:** model, controller, external-controller, credential, image-metadata, object-store, agent-version and log. **Unresolved:** full eligibility, every phase's retry/recovery and cleanup, all resource/provider outcomes and a live migration.

**Chunk rationale and current-page comparison:** A migration is one source–target process with participants, preconditions, phases and rollback boundary; external records, metadata and credentials are dependencies, not separate complete state machines on every page. Current `model-migration.md:16-113` presents phases, drivers, schema, streams and links calls to the model page. The process order above is source-grounded for the cited worker; current detailed watcher, schema and driver claims require additional traces, and call/phase anchors need preservation review.

## `object-store`

**Definition and boundary:** A namespaced object store manages stored object content and metadata, separate from database records, provider volumes and the workload's persistent storage (`internal/objectstore/fileobjectstore.go:302-303,776-845`; `work/system-model-115.md`, “One system, multiple clocks”).

1. **Objects, namespaces and references:** Describe object path, digest and size metadata versus blob content; controller and model namespace usage is evidenced by backup (`internal/worker/backupcreation/creator.go:188-231,284-312`). Consumers such as resources and agent binaries have their own authorization and paths.
2. **Change stream and file-store actor:** A file-store worker creates a metadata watcher and serializes get, put and remove requests through its loop; this is the traced file backend, not a claim about every backend (`internal/objectstore/fileobjectstore.go:463-540`). A notification is separate from the write result; no universal event-delivery guarantee is established.
3. **Put/get interaction and failure:** In the file backend `Put` waits for the worker response or cancellation/shutdown. It writes a temporary blob, validates the applicable hash, persists under a hash lock, then saves metadata; if metadata save fails the blob is not necessarily removed immediately (`internal/objectstore/fileobjectstore.go:302-350,776-845`; `internal/objectstore/base.go:73-120`). A successful local write does not prove later remote retrieval or replication.
4. **Backup, migration and lifecycle:** Backup inventories controller/model exports and streams referenced objects, not necessarily every imaginable blob (`internal/worker/backupcreation/creator.go:188-231,284-312`; `work/backup-subject-113.md`). Link migration and the appropriate resource-specific paths rather than duplicating their authorization.
5. **Configuration/failure index:** File-store failure, cancellation, hash mismatch, backend reachability and consumer-specific errors are different; backend-specific behavior needs separate evidence.

**E62 refinement, proposal:** For the file-backed path, distinct logical paths can share one digest metadata row. Removing a path retains metadata and the blob while another path remains; removing the last path can remove both, conditional on successful steps (`domain/objectstore/state/state.go:294-359,439-529`; `internal/objectstore/fileobjectstore.go:873-898`). DB REPL inspection provides a supported observation. `object-store.md:24-32,118-123` already describes the shared-path idea: retain and verify its scope rather than claiming the fact is missing. Source does not settle whether path/content is one notion with attributes or multiple linked chunks, nor establish all backend/concurrency guarantees (`work/structure-challenge-e62.md`).

**Pending links:** database, controller/backup, resource-charm, agent-version, task output, model-migration and lease. **Unresolved:** backend configuration and full drain/removal, replication, retention, cross-node retrieval and watcher guarantees; backup physical home remains open.

**Chunk rationale and current-page comparison:** Stored object, backing blob, database metadata, backend configuration and migration/backup transfers are related but independently changing primitives or processes; the file backend's ordering is not a universal backend guarantee.
