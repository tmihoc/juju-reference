## constraint

**Definition and boundary.** A constraint is a resource-selection requirement supplied at a scope such as model, application or machine; it is neither existing capacity nor the separate placement directive. Effective values and acceptance depend on the consumer and provider validator (`domain/application/service/provider.go:938-981`; `domain/machine/service/provider.go:191-219,248-283`; `domain/deployment/placement.go:64-116`).

**Chunk and attribute rationale.** The requirement set is a reusable input to two separately scoped consumers, while effective-value resolution is a shared calculation with consumer-specific inputs. This justifies one stable constraint-values/merge address and separate links to placement and machine/application allocation, rather than a page per holder or merging placement into constraints. The distinguishing attributes are value, holder/fallback, validator and consuming operation; the sections follow those dependencies (`domain/application/service/provider.go:957-981`; `domain/machine/service/provider.go:191-219,248-283`).

1. **Values and scopes.** Explain model fallback versus more-specific application and machine values and the fact that the direct machine path stores the effective merged values. Use the actual consumer path rather than a universal precedence table.
2. **Merging and validation.** For application resolution a provider validator is used, falling back to the default when the provider supplies none; merge model then application and fill a missing architecture with its default (`domain/application/service/provider.go:938-981`). For the default validator, specified values replace fallback, unspecified values carry forward and conflicts can remove fallback values (`core/constraints/validation.go:336-345,365-387`). The E50 direct-code example and its limits are in `system-derivation-111.md:63-65`. Do not generalize its conflict behavior to every provider validator.
3. **Allocation and placement interaction.** Direct machine creation strips container constraints, merges machine inputs over model fallback, validates, and invokes provider precheck on base and merged values; only a provider placement is passed as provider placement. A failed merge or precheck prevents that creation path; successful precheck is not successful allocation (`domain/machine/service/provider.go:191-219,248-283`).
4. **Configuration and failure index.** Point readers to the relevant input at each call, provider validation/precheck errors, and later machine provisioning status; do not imply a universal rule that placement overrides constraints.

**Pending links/corrections:** link model, application, machine, placement-directive, space and zone where the relevant value is consumed; review constraint merging and placement wording against the bounded paths. **Unresolved:** complete attribute vocabulary, source-specific merge/validation rules and change propagation to already-created resources; no general constraint change-stream contract established.

## link-layer-device

**Definition and boundary.** A network-node-associated link-layer device and its addresses are network observations, distinct from a machine, subnet or space. The state query groups devices by network node and joins optional provider and parent information; address/DNS data are associated with devices (`domain/network/state/linklayer.go:21-44,53-103,128-151`). This is not a disk/block-device inventory.

**Chunk and attribute rationale.** The device is attached to a network node and has its own properties; IP/DNS associations and provider/parent information are related but not equivalent primitives. Node/device/address groupings are therefore useful anchors here, with machine and subnet as participants rather than collapsed synonyms. Ordering record relationships before observed updates and status follows the consumer joining them (`domain/network/state/linklayer.go:21-44,53-103,128-151`; `apiserver/facades/client/client/status.go:923-949`).

1. **Representation and relationships.** Describe names, device type, parent/provider information, MAC, MTU, gateway and enabled state as fields on the queried records, and associated IP/DNS data separately (`domain/network/state/linklayer.go:59-103,128-151`). These fields do not themselves establish physical topology or reachability.
2. **Observed updates and actors.** On `SetObservedNetworkConfig`, the machine agent's authorization is checked against the target machine; the facade converts machine-origin configuration and calls the network service. The service resolves its network node, ignores an empty interface list, and passes the machine's unmanaged status as the missing-subnet flag (`apiserver/facades/agent/machine/machiner.go:249-284`; `domain/network/service/netconfig.go:41-69`). This does not describe every provider or update source.
3. **Status interaction.** Full status fetches interfaces and addresses, which can be empty before deployment completes; when an instance ID is known, machine status maps device names to IPs, MAC, gateway, DNS, space names and enabled state. A pending instance is represented differently (`apiserver/facades/client/client/status.go:180-207,923-952`). Absence or presence is not proof of live connectivity.
4. **Change stream, conditionally relevant.** The controller-network notify watcher is consumed by the API-address setter for its specific controller-network selection work; initial notification is consumed before later events (`domain/network/service/controller.go:231-240`; `internal/worker/apiaddresssetter/worker.go:151-186`). Do not present it as a public per-device event stream or as a delivery guarantee.

**Pending links/corrections:** link machine, status, subnet, space and watcher; separate network devices from the machine-only disk-inspection facet. **Unresolved:** full discovery/merge precedence, all interface types, timing and availability of every field, and provider-level configuration/failure semantics.

## machine

## space

**Definition and boundary.** A space is a model network grouping associated with subnets; application endpoint bindings refer to spaces. A space is not a subnet, availability zone, interface or application endpoint (`domain/application/service/application.go:1581-1600`; `domain/application/state/application_endpoint.go:25-53`; `apiserver/facades/client/subnets/subnets.go:111-148`).

**Chunk and attribute rationale.** A space groups subnet associations; an application endpoint binding and a machine's space requirement independently refer to that grouping. Their distinct targets and validation consequences justify space, subnet, binding and constraint addresses connected by the move interaction; exposure belongs to the application/firewall process, not to the space's identity (`domain/application/state/application_endpoint.go:25-53`; `domain/network/state/movesubnets.go:26-73`; `internal/worker/firewaller/firewaller.go:1145-1218`).

1. **Membership and bindings.** Present space identity and subnet association before application endpoint-to-space mapping, including the default mapping when no mapping is stored on the traced application path. Binding is not an exposure rule and does not prove network reachability.
2. **Affected change stream and actor.** In the machine firewaller path, a subnet namespace watcher triggers `subnetsChanged`: the handler refreshes space topology and, only for units of applications exposing endpoints to at least one space, flushes ingress rules (`domain/network/service/watcher.go:64-95`; `internal/worker/firewaller/firewaller_adapters.go:260-262`; `internal/worker/firewaller/firewaller.go:304-310,431-438,483-519`). This establishes this consumer, not universal stream behavior for every space edit or successful provider application.
3. **Moving subnets.** The state move path filters already-associated subnets and checks positive and negative machine space-constraint/binding failures; force can bypass reported failures before the move (`domain/network/state/movesubnets.go:26-73`; `work/control-infra-model-115.md:35-41`). State acceptance does not prove external reachability.
4. **Removal, platform and failures.** The Spaces facade prevents removal of alpha and performs a dry-run for the controller management space; it can return application binding and application/model constraint violations. Force changes violation handling but is not a removal-completion guarantee (`apiserver/facades/client/spaces/remove.go:22-80`). At the CAAS API root the Spaces facade is restricted to list, reload and show (`apiserver/restrict_caasmodel.go:95-115`).
5. **Exposure interaction.** On the traced machine firewaller path exposed spaces resolve to subnet CIDRs and are intersected with unit open ports, with named endpoint exposure taking precedence over wildcard; provider application and reachability remain separate (`internal/worker/firewaller/firewaller.go:1145-1218`).

## ssh-key

**Definition and boundary.** A user public SSH key and its model authorization association are distinct from the SSH server, a server host key and a tunnel's ephemeral key. State joins `user_public_ssh_key` to `model_authorized_keys` by user and model (`domain/keymanager/state/state.go:119-147,459-471,599-655`); the server's model/key check is a separate interaction (`internal/worker/sshserver/authorization.go:36-65`).

**Chunk and attribute rationale.** A public key associated with a user and the model authorization relationship vary separately; their checks differ from the SSH server's host key and a per-request ephemeral key. Give the persistent key and model-key association stable addresses, then place list/add/import/delete semantics against the actual target selected by each call, linking server authorization rather than equating the two (`domain/keymanager/state/state.go:459-471,599-655`; `apiserver/facades/client/keymanager/keymanager.go:68-153,163-210,271-335,387-420`).

1. **Records and scope.** Describe user-associated public key, fingerprint/comment and model authorization association, without asserting that key possession alone grants all model operations or that every SSH path uses this server.
2. **List and add.** The traced facade allows list after model read or the stronger write check, and resolves the authenticated user for each list request. Add checks model-admin/controller-superuser through the model-admin helper and a model change block, then adds to the authenticated user (`apiserver/facades/client/keymanager/keymanager.go:38-65,68-153,163-210`). List returns fingerprint or key according to mode; validate the command-specific presentation before prescribing CLI output.
3. **Import and delete differ.** Import checks the same write authority and change block but resolves the supplied user name; each key-source URL can produce its own result/error (`apiserver/facades/client/keymanager/keymanager.go:271-335,343-383`). At this anchor the CLI validates `lp:` or `gh:` IDs and passes the user name `admin`, not necessarily the authenticated user (`cmd/juju/sshkeys/import_sshkeys.go:75-106`). Delete checks the remove block and resolves the authenticated user; state removes model associations and prunes unused user-key rows (`apiserver/facades/client/keymanager/keymanager.go:387-420`; `domain/keymanager/state/state.go:599-655`). Avoid presenting import as targeting the caller merely because add/list/delete do.
4. **SSH authorization interaction.** The traced server requires model access and checks that the presented authenticated public key is associated with the destination model; failure of either condition prevents authorization (`internal/worker/sshserver/authorization.go:36-65`). This is not a demonstration of successful SSH or behavior of direct/CAAS alternatives.
5. **Failure index.** Organize permission, command-block, invalid source/user/key and source-specific import errors by operation; don't infer external service availability.

**Pending links/corrections:** link SSH server, user/access, model blocks and CLI command references; review any wording that treats all key operations as targeting the caller. **Unresolved:** complete key change/propagation consumers, every list/add/delete validation and supported source; no general public key event-stream guarantee traced.

## ssh-server

## storage

**Definition and boundary.** Storage spans distinct, independently addressable contracts: a model pool is reusable provider configuration, an instance is an identified store with filesystem and/or volume backing, and an attachment relates an instance to a unit with machine-side consequences. Their differing checks and lifetimes motivate separate anchors on this common page, not a proven need for separate files (`work/storage-boundary-114.md:5-15,19-35`).

**Chunk and attribute rationale.** Pool provider/attributes can be selected for multiple separately identified instances; attachment and unit ownership relate an instance to participants, while volume/filesystem backing and machine attachments can have distinct scopes and transitions. A directive expresses inputs to instance creation rather than being the resulting resource. Stable pool, directive, instance, unit-attachment and backing/machine-attachment addresses expose these primitives even if retained on one page; ordering records, relevant streams and actors before their operations follows their dependencies (`domain/storageprovisioning/unitstorageargs.go:127-142,183-235`; `domain/application/state/unitstate.go:1035-1051,1070-1113,1129-1186,1399-1428`; `work/storage-boundary-114.md:5-15,25-35`; `work/filesystem-lifetime-114.md:21-36`).

1. **Storage records and relationships.** Describe the named pool and provider attributes, instance identity/kind/size and pool link, filesystem and/or volume backing, and unit/machine attachment relationships as distinct inspector-facing records. A unit directive picks a pool and count; the traced argument generator gives each requested instance its own UUID (`domain/storageprovisioning/unitstorageargs.go:127-142,183-235`; `domain/application/state/unitstate.go:1035-1051,1070-1113,1129-1186,1399-1428`).
2. **Storage change streams.** The uniter's `WatchUnitStorageAttachments` authorizes access to a unit, creates a unit-scoped strings watcher and returns its initial changes; its state query selects storage IDs and attachment life for that unit. `WatchStorageAttachments` instead resolves one unit/storage attachment and returns a notify watcher scoped to that attachment UUID (`apiserver/facades/agent/uniter/storage.go:373-416,422-491`; `domain/storageprovisioning/service/service.go:459-508`; `domain/storageprovisioning/state/state.go:539-561,750-759`). Distinguish the two payloads and authorization; do not infer exhaustive storage streams or delivery guarantees.
3. **Provisioning actor and composition.** The storage provisioner validates volume parameters and calls the provider; a stored directive or instance is not a completed volume or mount (`domain/storageprovisioning/state/volume.go:1289-1392`; `internal/worker/storageprovisioner/volume_ops.go:19-101`). Provider scope and kinds determine composition: rootfs supports machine-scoped filesystem but not block; EBS can yield a machine-provisioned filesystem over a model-scoped volume (`internal/storage/provider/rootfs.go:69-95`; `internal/provider/ec2/ebs.go:170-198,313-320,360-362`; `domain/storageprovisioning/provisioning.go:90-138,147-170`).
4. **Pool calls.** Creation checks model write and validates name/provider/configuration; listing checks read. Detach can select one unit or all attachments, checks the charm minimum for an alive unit and schedules relationship/backing-attachment removal. A non-forced job waits for dead life; forced processing can proceed from dying. Deleting an attachment can also delete the owner's relationship but not the instance itself (`apiserver/facades/client/storage/detach.go:45-50,70-113,157-222,228-274`; `domain/removal/service/storage.go:258-317,385-475`; `domain/removal/state/model/storage.go:409-467`). Other operations can explicitly request instance destruction.

Forced jobs can remove attachment records without waiting for regular detach; neither durable data survival nor reattachment or integrity is guaranteed (`work/filesystem-lifetime-114.md:5-17,21-36,50-52`; `domain/removal/state/model/machine.go:193-225,246-299`).

## subnet

**Definition and boundary.** A subnet is a network record with a CIDR and space association, with zero or more recorded availability zones; it is not the space grouping or an availability zone (`apiserver/facades/client/subnets/subnets.go:111-148`; `domain/network/state/movesubnets.go:47-73`).

**Chunk and attribute rationale.** The CIDR-bearing subnet is separately observed and moved between spaces; the zone-name association filters it, and the watcher feeds a specific firewall consumer. Therefore keep a subnet record and its membership/change interactions together, while space, zone and firewall each retain their own addresses (`apiserver/facades/client/subnets/subnets.go:111-148`; `domain/network/state/movesubnets.go:26-73`; `internal/worker/firewaller/firewaller.go:431-438,483-519`).

1. **Record and relationships.** Explain CIDR, space association and recorded zone set before filtering or moves; other provider/address attributes and exact creation semantics remain untraced.
2. **Change stream and actor.** A subnet watcher filters by requested UUIDs, with an empty input set meaning no filtering; the machine firewaller uses an empty set. On an event it refreshes space topology and flushes ingress for units of applications exposing endpoints to at least one space (`domain/network/service/watcher.go:64-95`; `internal/worker/firewaller/firewaller_adapters.go:260-262`; `internal/worker/firewaller/firewaller.go:304-310,431-438,483-519`). ## zone

**Definition and boundary.** An availability zone is a provider location used in the traced compute and subnet observations, not a network space or subnet. The API returns provider-reported zone names and availability to a model reader; listing failure propagates (`apiserver/facades/client/subnets/subnets.go:67-69,87-105`). Availability is an observation, not a capacity or fault-isolation guarantee.

**Chunk and attribute rationale.** Zone names and availability come from the provider query; the separately stored subnet association and constraints are uses of that name, while provisioner distribution is a process using provider capabilities. This warrants an availability-zone address linking to association and allocation, not treating an observed name as synonymous with a subnet or guaranteed isolation domain (`apiserver/facades/client/subnets/subnets.go:87-105,111-148`; `internal/provisionertask/provisioner_task.go:1066-1094,1222-1257,1483-1540`).

1. **Provider-reported names and availability.** Describe the `AllZones` read check and provider result/error; do not promise an identical zone model for every provider.
2. **Subnet association and filtering.** A subnet can report zone names; filtering does not exclude subnets with an empty zone set (`apiserver/facades/client/subnets/subnets.go:111-148`). Link subnet for the exact filter behavior.
3. **Placement and provisioning actor.** In the IAAS machine provisioner, the zoned-provider branch tracks zone/machine distribution; start parameters include constraints, placement and subnet-to-zone topology. It selects a suggested zone and calls `StartInstance`; on a potentially zone-specific error it can try another untried zone, subject to conditions and retry strategy (`internal/provisionertask/provisioner_task.go:1027-1035,1066-1094,1222-1257,1483-1540`). This is not proof of final provider placement or successful allocation; providers without the zoned interface take a different path.
4. **Failure index.** Point to provider zone lookup, constraint selection, zone-specific start failure and final machine status rather than a universal zone failover policy.
