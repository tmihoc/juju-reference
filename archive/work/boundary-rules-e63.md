# E63: what distinguishes a page from a section?

**Result:** the three traced behaviors satisfy E63's bounded behavioral criteria, but the case set is **not a valid three-case held-out structural challenge**. After registration we found the existing reference already describes the core annotation and sequence behavior; those two cases are historically contaminated. The image-selection exact/partial path was not found in the searched research history or the inspected image-metadata reference. These purposive cases support distinctions and expose competing editorial choices; they do not select a unique file layout, prove reader benefit, or lock in a reference-wide skeleton. E63 was registered in `structure-discovery-plan.md` before source-path inspection. Source citations below refer to `/tmp/juju-41-tree` at `e5db99d585`; existing reference comparisons refer to the separate PR worktree. No live controller/provider or page/rule edit.

## 1. Rules being tested

E63 registered three different procedures, not three names for the same page form:

* **V — variation:** a named value or record gets a page if it varies independently and is exposed on a supported surface, including DB inspection. Thus inspectable machine and storage counters can become separate pages.
* **O — operation:** a named subject gets a page if it has its own exposed read/write operation; otherwise its contract is nested at the principal target. Annotation and managed image metadata have operations; an allocation counter without a demonstrated direct operation does not get a page.
* **D — dependency:** determine the supported contract, its participants, conditions and effects first. A common cross-subject contract has a linkable shared address if the evidence and relevance justify it; target-specific conditions stay at the affected interaction. Independent variation alone is not enough. A directly managed subject or relevant shared mechanism can be a page, but a section can also supply an address. A physical-file tie remains a tie if neither behavior nor an explicitly chosen editorial convention distinguishes the alternatives. One-home-plus-links is a proposed convention, not an implementation invariant.

These are deliberately explicit competing hypotheses. V and O can be implemented with enough sections and links to express the same facts as D; a fact that they choose a different page is not by itself a logical contradiction. D includes an editorial one-home convention; its source-grounded parts do not uniquely entail that convention or a filename.

## 2. Results

### Image metadata → candidate image → provisioning

**Behavioral criterion met, bounded; exact/partial matching path not found in searched research history.** Image metadata management lists filtered candidate records and returns image IDs/attributes (`apiserver/facades/client/imagemetadatamanager/metadata.go:38-66,104-115`); it is not a machine or a successful cloud instance. In the EC2 instance-start path, an explicit image constraint can replace input metadata; EC2 then applies provider storage preferences and calls `FindInstanceSpec` (`internal/provider/ec2/environ.go:628-655`; `internal/provider/ec2/image.go:18-63`). The helper rejects architecture mismatches, prefers an exact virtualization match to a partial match with unspecified image virtualization, and returns a selected candidate and instance type or an error (`environs/instances/image.go:67-127,180-194`). This is not a full metadata-source-priority audit or an EC2 invocation.

**Direct real-code probe:** a throwaway Go program called `instances.FindInstanceSpec` with synthetic inputs and an `amd64` / `hvm` instance type. A partial and exact image together selected `exact`; a partial alone selected `partial`; an incompatible `arm64` image returned `no "" images in example matching instance types [example]`. A second synthetic probe supplied two otherwise identical image records in reversed orders: the helper selected the first supplied ID in each case. Both files were removed. These probes execute the helper, not a controller, EC2 start, metadata service, cloud fetch or API.

**Placement:** V and O both predict an image-metadata page because the metadata is observable and has management operations. D recognizes management/filter contract separately from the machine/provider selection interaction and recommends a shared metadata address linked from machine provisioning; a page versus anchor is not runtime-forced. All three can represent the same filtered candidates and subsequent selection if they retain both contracts.

**Post-hoc priority discrepancy, not a live finding:** the provisioning service sorts cached and externally fetched metadata in *ascending* numeric `Priority` (`domain/provisioner/service/service.go:403-447`), and its provisioning response converts the array in order (`apiserver/facades/agent/provisioner/provisioninginfo.go:128-145`). The provisioner task converts that array in order but does not carry its numeric priority into `ImageMetadata` (`internal/provisionertask/provisioner_task.go:1013-1037`). EC2 preserves relative input order within each selected storage group; with otherwise identical matching candidates of the same architecture, virtualization and selected storage, the common helper's tie ordering chooses the first input (`internal/provider/ec2/image.go:18-41`; `environs/instances/image.go:89-127,145-156,196-207`). In that *conditioned source path*, low numeric priority reaching the list first can therefore precede a higher numeric priority; the helper probe exercises order sensitivity but supplied no priorities and did not execute the service, API or provider. The existing reference says the highest priority wins (`image-metadata.md:23,32`), while priority constants call 50 custom and 10 default (`environs/simplestreams/datasource.go:50-69`). This is a **potential code/contract discrepancy** requiring further end-to-end investigation, not a live result, a complete precedence rule, or permission to fix the prose. Image-ID override, filters, exact versus partial matching, provider and storage selection can change the outcome.

### Annotation → target relationship

**Behavioral criterion met, but historically contaminated.** The client API checks model read for `Get`, model write for `Set`, parses each entity tag and dispatches to the annotation service (`apiserver/facades/client/annotations/annotations.go:46-96,103-166`). Machine and application tags map to distinct kinds and names (`core/annotations/annotations.go:20-26,35-47,51-80`). The shared service validates the ID and keys, partitions nonempty values into upserts and empty values into deletions (`domain/annotation/service/service.go:86-112,149-161`). State resolves a machine or application UUID, selects the corresponding kind's table and upserts/deletes only that UUID and key inside a transaction; get resolves that target and reads its UUID's values (`domain/annotation/state/state.go:129-183,191-200,207-275,406-447`). Thus for two existing targets, a successful deletion for the machine does not itself delete the application's key, and an invalid key is rejected before state mutation. Different lifecycle/cleanup rules have not been audited here.

The pre-existing PR `docs/reference/annotation.md:10-21,26-39` already identifies multiple targets, one key per entity and the shared empty-value deletion rule. This was noticed only after registration: the trace is evidence about actual behavior, but not an independently novel challenge to the prior reference. The prior research also described annotation as a cross-target facet (`structure-discovery-plan.md` historical E21b/E31); the claim at registration that the key path needed tracing was too broad relative to the actual reference. The exact state queries still corroborate target isolation; no API call was made.

**Placement:** V and O predict a page; D predicts one address for shared key rules, with the target identity, supported kind and target-specific lifecycle kept visible. A page for the shared contract or a section of a cross-subject metadata reference could both express the same facts. Neither code nor the shared `Set` implementation proves a separate file is required, and cross-subject reuse is not itself proof of reader benefit.

**Separate call-contract lead:** the `Set` implementation appends an entry for each **error** but not for successful entities (`annotations.go:79-96`), while `annotation.md:31,37` says one result per entity. This is a potential source/documentation contract discrepancy, not exercised through RPC; do not silently change either code or docs. It does not change the E63 boundary judgment.

### Sequence → machine and storage identifiers

**Behavioral criterion met, but historically contaminated.** In a supplied transaction, `sequencestate.NextValue` inserts namespace value zero or increments an existing value, checks that exactly one row was affected and reads the new value, returning errors on failures (`domain/sequence/state/sequence.go:24-62`). Machine allocation calls it with namespace `machine` and formats the result as a machine name (`domain/machine/state/placement.go:131-147,237-245`; `domain/machine/sequences.go:8-13`); unit storage allocation calls it with `storage` and combines the result with a storage name (`domain/application/state/unitstate.go:1399-1428`; `domain/storage/sequence.go:10-15`). These consumers have distinct namespaces and return different identifiers, and both use the same allocation code inside a caller-provided transaction. What happens when a transaction fails or later allocation/reservation occurs must not be recast as an unconditional global promise about gaps, never-reuse or chronology.

The model database has `sequence(namespace, value)` with a namespace primary key (`domain/schema/model/sql/0029-sequence.sql:1-4`). An authorized DB inspector can open a model database and execute a SQL query (`internal/worker/dbrepl/worker.go:237-268,320-335,781-785`); this is a DB-inspection surface, not evidence of a general client counter-management API, an ordinary operator inventory, or a live DB query. Only absence of a direct client operation from the bounded traces is established; no exhaustive absence claim.

The pre-existing `docs/reference/database.md:41-43,106-117` already states these namespaces, allocation in the needing transaction, zero start and increment. The research outline's warning that this needed source-checking did not mean the path was new to the project. The case is contaminated as a held-out test; its source supports the bounded behavior and permits an inspector-focused shared contract, not its unique home. No sequence allocator or controller was run here.

**Placement:** V requires a separate page for each inspectable, independently varying named counter; O nests allocation with each target absent an established direct operation; D can put the shared allocation semantics at one inspector-relevant address with machine/storage-specific names and links. V and D do not differ on what SQL does; O cannot infer nonexistence of a counter operation from this bounded trace. D's proposed shared section versus standalone page is an editorial decision, not a source-derived fact.

## 3. Same facts, different structures

Take this exact, scoped fact set **R**: the traced shared allocator starts a new namespace at zero, increments an existing one and uses its caller's transaction; the machine and storage paths use separate named namespaces and use their returned values in their respective IDs. Mention failure and inspection limits as above; do not generalize allocation across all paths. Hold R and all limits constant:

| Arrangement | Statement of shared R | Navigation | What it shows |
|---|---:|---|---|
| Two target-local descriptions, a permissible O presentation | 2 complete copies | No shared-R link | Makes each description self-contained; duplicates the shared rule. |
| One shared section, linked from both target-specific descriptions, a D presentation | 1 | 2 links | One copy; readers following target entries need a link. |
| One shared standalone page, linked from both targets | 1 | 2 links | Same fact and link counts as the section; different page level. |

V's literal independently-varying-counter rule additionally assigns machine and storage counter pages; its generic allocator explanation can be copied or linked, because V does not specify a sharing rule. These are constructed *same-facts* layouts, not measured reader behavior, evidence for unique ownership, a performance test, or proof the code enforces one implementation forever. Links can point to a section or page without changing this fact graph. No new headings or links were added.

## 4. Decision and remaining uncertainty

**Supported substance:** distinguish the managed candidate from the provider selection, the annotation relationship from either target, and the shared sequence allocator from the generated identifiers. Put conditions where their scope is accurately stated; no arrangement may equate image selection with successful cloud creation, delete annotations of all targets, or promise contiguous IDs.

**Competing file rules:** V and O make concrete but conflicting predictions for inspectable sequence records: V mandates separate pages, O does not when there is no demonstrated direct operation. Both can still preserve the facts, so neither is empirically falsified by the page placement. Image metadata and annotation do not discriminate V and O; each predicts a page for both. D exposes what a reader must interpret and permits a shared address, but its preference for a shared section and its leave-ties-open rule are design choices, not proven superior navigation. A comparison that simply labels a named value an independent subject would assume the conclusion. E63 therefore does **not** establish a winner for physical page or section boundaries, and it does not invalidate the primitive/attribute hypothesis.

**Candidate decision procedure, not an approved skeleton:** (1) establish a meaningful supported surface, scope and actors; (2) derive behaviorally distinct subjects/relationships/observations and the conditions connecting them; (3) keep the full same facts under every proposed arrangement; (4) define an address for relevant shared semantics and target-specific rules, with links only as an editorial convention; (5) resolve page versus section only where a separately stated and defensible editorial rule selects one, otherwise record an explicit tie. For applicable entity roles retain the user's settled causal order. This is a more explicit separation of factual and editorial decisions, not a claim E63 proves one-home or that page-level uncertainty is solved.

**Next discriminating work:** pre-register a comparison of explicit editorial page-level policies using equal source facts and a reproducible structural metric that the policies genuinely predict (for example, stable address/link topology under a specified subject change). The metric must be justified as a maintenance property rather than a surrogate for reader benefit; do not use competency questions to decide boundaries. Challenge it on genuinely unexamined paths and inspect prior reference pages *before* declaring held-out novelty; the two contamination findings show the history-only search was insufficient. Record when two arrangements remain behaviorally and metrically equivalent instead of manufacturing a source-derived winner. Individual hook/action-command and five Kubernetes-cloud outlines and the prior workload slice remain blocked by denied `HookCommandPages`, `KubernetesCloudAttributes`, and `WorkloadModel` agents (402); do not relaunch or work around them.

E63 did not change the original E59, E60, E61 or E62 results. It does not authorize applying any queued page, structural or repository-rule changes. Lock in the structure first, then revisit those proposals and seek explicit approval.
