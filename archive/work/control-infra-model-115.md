## Control scope and access

A controller is a management and API context for models, not a synonym for any one model or the cloud substrate. Its API server installs authenticated and model-addressed handlers; a request can be routed to a specified model or, on other routes, the controller model (`apiserver/apiserver.go:655-670,782-855`). Model info carries the model UUID, name and qualifier, controller UUID, controller-model flag, type, life, cloud, region, provider type and optionally a credential (`apiserver/facades/client/modelmanager/modelmanager.go:1061-1100`). Thus one model's applications, machines and storage can vary without redefining the controller or another model. A controller model is special, but still appears as a model with its own life; do not collapse it with the entire controller.

Authentication of a client and authorization of an operation are separate from the requested model's state. The API root filters controller-only versus model login, restricts CAAS methods, and further restricts user access during upgrade or migration; controller-machine agent logins are exempted from the maintenance-root restriction on this path (`apiserver/root.go:496-525,528-566`; `apiserver/restrict_caasmodel.go:95-115`). Factory and method-specific checks still apply; neither registration nor successful login implies every operation is permitted.

A grant relates a user to a target, so the same user can have different access to different clouds, models, controllers or offers. Target type constrains valid levels: cloud add-model/admin, controller login/superuser, model read/write/admin, offer read/consume/admin (`domain/access/service/permission.go:34-64,94-109`; `core/permission/access.go:86-105,129-140,169-206`). A cloud credential is not this Juju grant: it supplies cloud-facing authority, while the grant controls Juju-side authorization. A user may be authorized to request a change but lack working provider access, or the reverse.

Model command blocks are an additional model-local condition, not a grant. On calls using the common checker, remove checks remove then change blocks; destroy checks destroy, remove then change (`apiserver/common/block.go:51-94`). For example, an otherwise authorized machine removal is refused by the relevant block (`apiserver/facades/client/machinemanager/machinemanager.go:450-455`). This is not proof that every model-changing call uses that checker.

## Cloud, model creation and credentials

A cloud definition and region select a provider context; the model is the separately identified management scope using it, and a cloud credential is a separately keyed cloud/user/name record which may be used by multiple models. In the traced model-create path, an omitted cloud uses the controller default, and the default region is used only if the chosen cloud equals that default cloud. A non-admin must have add-model permission on the selected cloud and use a qualifier corresponding to the logged-in user. If no credential is specified, lookup is for the API user's default for that cloud; missing default is allowed to proceed because some clouds can create models without credentials. The API obtains cloud/region/optional credential, constructs model-type-specific provider preflight, then creates controller-database state, model config and activation, model-database information and reloads spaces (`apiserver/facades/client/modelmanager/modelmanager.go:174-215,217-289,306-362,365-420`). An accepted provider preflight is not a successful future workload allocation. Creation spans steps/databases; the code itself notes rollback coordination is incomplete (`:233-236`), so an error after earlier writes must not be described as an atomic no-op.

Controller model defaults are separately managed per cloud with region values, while a model also has its own configuration (`apiserver/facades/client/modelmanager/modelmanager.go:1215-1257,1261-1275`; model-create `:311-325`). Exact precedence and whether changing a default affects an existing model must be traced for each setting; neither follows merely from their names.

A controller superuser or model admin can request a model credential-reference change, subject to a model change block; the new credential must already be on the controller (`apiserver/facades/client/modelmanager/modelmanager.go:1357-1400`). Updating credential content and changing the model's reference are different operations. The credential update facade accepts owner-or-controller-admin access, and a forced update requires controller superuser (`apiserver/facades/client/cloud/cloud.go:87-116,524-566`). On the actual controller credential service path, cloud auth-type compatibility is checked and models using the key are enumerated, **but per-model credential validation currently returns no errors without performing its intended check** (`apiserver/facades/client/cloud/register.go:37-53`; `domain/services/controller.go:165-169`; `domain/credential/service/service.go:284-320,323-373`). Therefore successful update/check is not evidence the new content can access any existing model's resources. Other validation contexts, including migration's separately constructed validator, are not thereby characterized. Invalidating a shared model credential affects all models using that credential (`domain/credential/service/service.go:253-273`); ordinary revoke refuses when models still use it, whereas force bypasses that particular in-use refusal and then calls removal (`:375-412`). Actual cloud reachability and consequences of forced revocation remain provider/state dependent.

## Requirements, placement and machine realization

Model and application constraints describe inputs to resource selection, not existing cloud capacity. In the application resolution path the provider supplies a validator, with a default validator if none; model constraints are the fallback and application constraints are the more specific input. Missing architecture is filled with the default (`domain/application/service/provider.go:938-981`). The default merge retains unspecified fallback attributes, substitutes specified values, and discards conflicting fallback values (`core/constraints/validation.go:336-345,365-387`). The earlier direct-code E50 exercise produced `arch=amd64 cores=2 mem=8192M` from fallback `arch=amd64 mem=4096M` plus specific `cores=2 mem=8192M` (`system-derivation-111.md:63-65`). This demonstrates that validator, not every provider-specific conflict rule or actual allocation.

Placement is a separate instruction about where/how to place. Parsing distinguishes no placement, an existing machine, a provider-scoped directive and a container directive (`domain/deployment/placement.go:47-61,64-116`). For direct machine creation, machine constraints override model fallbacks, container constraints are stripped, the provider prechecks the base and merged constraints, and only a provider-type placement is passed as provider placement; only then are effective constraints persisted with machine state (`domain/machine/service/provider.go:170-219,248-283`). Provider interpretation, validation, capacity and platform matter; no general 'placement always overrides constraints' rule is established.

A Juju machine is a model-managed entity and may have an associated external cloud instance; its identity, life, pending/provisioning/error state and instance association are distinct. The IAAS compute provisioner watches model machines (`internal/worker/computeprovisioner/computeprovisioner.go:132-136,316-321`). Its task classifies relevant machines, queues pending starts and dead-machine cleanup (`internal/provisionertask/provisioner_task.go:241-270,358-393,530-574`). For a start it sets instance provisioning status, constructs provider inputs, invokes `StartInstance`, can try other availability zones/retry, and eventually records provider instance ID, hardware, network and volume information. A failed start can produce provisioning-error status; if registration of a newly started instance fails the worker attempts to stop it, but that cleanup can itself fail (`:1425-1432,1435-1510,1520-1591`). A returned machine name or successful precheck is therefore not proof that its instance, agent or workload is ready.

This path is not a universal compute model: the API root has CAAS restrictions, and the traced `AddUnits` API rejects CAAS even though it accepts IAAS calls (`apiserver/root.go:517-523`; `apiserver/facades/client/application/addunit.go:23-47`). Do not extrapolate machine placement and direct machine provisioning to Kubernetes applications; Kubernetes-specific paths need their own trace.

## Network connects allocation, applications and observation

A space is a model network grouping to which subnets are associated; it is distinct from a subnet, a provider availability zone, a machine interface/address and an application endpoint. An application's endpoint binding maps endpoint names to space IDs, with a default mapping when none is stored (`domain/application/service/application.go:1581-1600`; `domain/application/state/application_endpoint.go:25-53`). Subnet listing can filter by space and zone; a subnet with an empty zone set is not excluded by the zone filter, and available zones are returned from provider information (`apiserver/facades/client/subnets/subnets.go:87-105,109-148`). These relationships are inputs and observations, not proof of a reachable network path.

Changing one network relationship can invalidate another: moving subnets between spaces checks whether existing machines still satisfy positive/negative space constraints and bindings, with force able to bypass reported failures (`domain/network/state/movesubnets.go:20-73`). Removing a space has special alpha and controller-management restrictions and may report application bindings or application/model constraints (`apiserver/facades/client/spaces/remove.go:20-80`). CAAS specifically permits only list, reload and show on the Spaces facade at the API root (`apiserver/restrict_caasmodel.go:95-115`).

Binding an endpoint is not the same as opening ingress. On the traced machine firewaller path, exposed spaces resolve to subnet CIDRs and endpoint-specific exposure intersects the unit's opened port ranges; a named exposure takes precedence over the wildcard case for that endpoint. Remote relation ingress is handled separately (`internal/worker/firewaller/firewaller.go:1145-1170,1176-1218,1224-1262`). Provider rule application, routing and external reachability remain separate conditions. Full status fetches machine network interfaces and explicitly allows them to be empty before deployment finishes (`apiserver/facades/client/client/status.go:180-207`).

## Persistent storage is pool, instance, backing resources and attachment

A model pool is reusable configuration naming a storage provider and attributes, not the storage it creates. Creation checks model write access; the service checks provider availability/configuration. List checks read access, while `UpdatePool` and `RemovePool` on the traced 4.1 facade return not-yet-available rather than invoking the domain's independent update/remove methods (`apiserver/facades/client/storage/pool.go:58-90,160-228`; `domain/storage/service/storagepool.go:110-164,225-304`). E57 directly exercised the two not-yet-available facade methods; this was not an RPC or controller exercise.

A unit storage directive chooses a pool and a count. The traced new-unit path resolves its provider and creates a distinct instance UUID for each requested instance, all linked to the selected pool; the instance may require a filesystem, a volume or both (`domain/storageprovisioning/unitstorageargs.go:127-142,178-235`; `domain/storageprovisioning/provisioning.go:68-138`). The backing volume provisioning path retrieves instance/pool/provider parameters and the provisioner validates and calls the volume source; individual provider errors may be rescheduled with pending status (`domain/storageprovisioning/state/volume.go:1289-1392`; `internal/worker/storageprovisioner/volume_ops.go:19-101`). Creation of the state/arguments is not creation or mounting of a provider volume.

An attachment is a relationship between an existing storage instance and a unit, with machine-side filesystem/volume attachment consequences. Attach checks model write and change block, resolves unit and storage separately, then validates life, charm identity, kind, minimum size, count, sharing and machine ownership compatibility (`apiserver/facades/client/storage/attach.go:19-75`; `domain/application/service/unit.go:390-445,470-535,538-584`). Detach accepts a specific unit or, if no unit is specified, all unit attachments. It advances attachment life and schedules a removal job, with related backing-attachment jobs; a non-forced job waits for dead life, while forced processing can proceed from dying (`apiserver/facades/client/storage/detach.go:45-113,157-222,228-274`; `domain/removal/service/storage.go:258-317,385-475`). Deleting the unit attachment also deletes the unit-owner relationship if that unit was owner, but this transaction does not delete the storage instance (`domain/removal/state/model/storage.go:409-467`). An owner and an attachment are related but not identical; a successful scheduled detach does not prove provider-side detachment or portability.

Provider capabilities are part of this behavior: provider scope, kind, dynamic provisioning and release are separate capabilities (`internal/storage/interface.go:28-101`). `rootfs` supports filesystem, not volumes, and is machine-scoped (`internal/storage/provider/rootfs.go:69-95`). EBS supports block only and has environment scope, but Juju can make a machine-provisioned filesystem over a model-scoped EBS volume. When a volume exists, ownership classification uses its scope (`internal/provider/ec2/ebs.go:170-198,313-320,360-362`; `domain/storageprovisioning/provisioning.go:90-138,141-170`). Kubernetes's registry recommends filesystem rather than block and names Kubernetes, rootfs and tmpfs providers (`internal/provider/kubernetes/storage.go:79-133`); this is not a claim about all implementations' data guarantees. E57/E58 directly called real rootfs and EBS/composition helpers; neither exercised a live provider.

## Removal and migration change different relationships

Removal is not a single instantaneous deletion. On the machine API path, write authorization and the remove/change blocks precede per-machine handling; dry run reports without scheduling, while `keep` attempts to mark the cloud instance to retain and, under force, logs rather than fails if that setting fails (`apiserver/facades/client/machinemanager/machinemanager.go:441-513`). A direct machine removal without force is refused for non-dead units or child machines. With force the cascade advances machine, cloud-instance, child and unit lives, selects machine-owned storage and schedules separate removal jobs for affected entities (`domain/removal/state/model/machine.go:120-225,246-299`; `domain/removal/service/machine.go:66-144`). The model network node cannot be deleted while unit or storage-attachment references remain, including on the forced path (`domain/removal/state/model/machine.go:502-540,828-908`). Force affects waiting and cleanup conditions, not a promise that the provider is immediately cleaned up.

E58 supplies a discriminating case: an ordinary newly created EBS-backed filesystem has a machine-provisioned filesystem over a model-scoped volume, and the IAAS ownership-list builder does not record that backing storage as machine-owned (`domain/storageprovisioning/unitstorageargs.go:324-363`). For the traced direct forced machine-removal cascade, non-machine-owned instances are not selected by the machine-owned query, and the unit cascade uses `destroyStorage=false`, marking unit attachments dying rather than selecting owned instances for destruction (`domain/removal/state/model/machine.go:193-225,246-299`; `domain/removal/state/model/unit.go:78-112,130-177`). On a successful regular volume detachment the provisioner calls the provider and removes the attachment record, and EBS issues EC2 `DetachVolume`, not `DeleteVolume` (`internal/worker/storageprovisioner/volume_ops.go:358-423`; `internal/provider/ec2/ebs.go:1052-1091`). Forced jobs can delete dying filesystem/volume attachment records without waiting for dead (`domain/removal/service/storage.go:1093-1128,1158-1193`). Therefore the conditional source deduction is that the storage instance and backing records are not selected for destruction in this path; it is **not** proof that cloud detach precedes forced cleanup, that data survives EC2 termination, or that reattachment works. The mount is not the backing volume. A separate unit removal can request destruction of unit-owned storage (`domain/removal/service/unit.go:85-107`; `domain/removal/state/model/unit.go:97-112`).

Model destruction is broader and has its own controls: model admin or controller admin and destroy-block checks, a tri-state storage destruction argument, force and wait; persistent storage can cause an error when no explicit storage choice is supplied (`apiserver/facades/client/modelmanager/modelmanager.go:883-928`; `domain/removal/service/model.go:80-109`). The cascade advances controller and model state in separate steps and schedules model, relation, unit, machine, application and storage jobs (`domain/removal/service/model.go:147-272`). Some child scheduling errors are logged after life has already advanced (`:441-454,459-489`), so even an error or accepted request is not a single all-or-nothing completion signal. The exact state after a failure depends on which step ran; do not infer that a persistent-storage error reverses any earlier controller-side changes.

Migration instead changes which controller manages a model; it is not equivalent to destroying the workload and redeploying it. A controller superuser initiates it with a model and target; the call reports per-model success/error (`apiserver/facades/client/controller/controller.go:623-665`). The worker restricts concurrent activity, runs source and target prechecks before and after agent quiescence, transfers model state and binaries to the target, waits for agent validation, checks provider/target machine agreement and requests target activation. Activation prepares a still-gated import; in the success phase the worker waits for agent reports and asks the target to adopt cloud resources, the target's point of no return. It then transfers logs unless source Loki forwarding is enabled, and reaps the source model (`internal/worker/migrationmaster/worker.go:298-375,413-482,518-578,581-618,641-692,789-800`). Failed prechecks or transfer can take an abort path; removing the imported target model during abort is best effort (`:413-433,476-481,803-810`). After the success phase the worker states there is no turning back (`:650-662`). Target compatibility, provider adoption, agent availability and phase-specific errors limit completion; no live migration or exhaustive recovery proof follows.

## Observation and independent mechanisms

`FullStatus` is an authorized, composed observation: controller superuser or model read can see it; the server fetches model, spaces, applications/units, machines, network and relations, and includes offer details only for admins (`apiserver/facades/client/client/client.go:49-73`; `apiserver/facades/client/client/status.go:126-181,204-210`). It is neither a guarantee of completion nor an atomic snapshot of all provider reality. Provisioning state, instance status, machine life, unit status and attachment state describe different parts of progress and can differ. Per-operation errors, observed status and logs are likewise not interchangeable.

Watchers are selected change/notification mechanisms used by workers, not identical to status or hooks. The machine provisioner's watcher loop expects an initial set of relevant machines and processes later machine IDs (`internal/provisionertask/provisioner_task.go:253-270`); a generic notify watcher sends an initial notification, filters/maps changes, and emits an empty notification rather than a full state snapshot (`core/watcher/eventsource/notify.go:93-149`). A relation-units watcher instead fetches and sends a relation change payload (`apiserver/facades/agent/uniter/watcherrelationunit.go:104-139`). Separately, a unit's update-status timer changes the remote status version, and the resolver chooses the update-status hook only after earlier eligible work (`internal/worker/uniter/remotestate/watcher.go:679-688,720-729`; `internal/worker/uniter/resolver.go:362-390`). Hence neither every notification nor every hook is one identical database-change-to-hook pipeline; no universal ordering, delivery, freshness or exactly-once guarantee is established.

## Deducible cases and limits

1. **Allowed user, blocked operation:** a model writer can pass the permission check but receive a block error on machine removal; lifting the block alone does not satisfy occupied-machine force requirements or make provider cleanup complete. Both predicates and subsequent asynchronous work matter.
2. **Shared credential, different models:** two models may refer to the same cloud credential while having separate Juju grants, machines and status. Invalidating the shared credential affects both; changing only one model's reference does not by itself change the other. A successful update cannot establish provider access because the traced per-model validation is unimplemented.
3. **Inputs versus realization:** for the default validator, the E50 constraint example yields the stated effective values. A provider precheck can still reject the base or placement, and a later instance start can fail even after precheck succeeds; none of these outcomes proves a unit is operational.
4. **Two stores, one pool:** a directive for two instances produces two UUIDs with one pool UUID. Detaching one unit/instance relationship does not request pool deletion or deletion of the other instance; compatibility, life, count and successful asynchronous provider handling remain conditions.
5. **Network edit with cross-subject effects:** moving a subnet may make an existing machine's binding/constraint invalid even though the application and machine identities have not changed; force can permit the move despite the recorded failures. An exposure to the same space still requires relevant opened ports and does not itself prove reachability.
6. **Machine loss versus storage loss:** under E58's explicit EBS composition and direct forced-removal conditions the backing instance is not selected for destruction; a rootfs provider has different machine scope. Neither case warrants a universal filesystem-lifetime sentence or an unconditional data-survival promise.
7. **Migration versus removal:** successful initiation does not mean target activation or source reaping has completed; an abort's target cleanup is best effort, while after success resource adoption and remaining work must proceed. Source and target controller identity, model identity, agents and provider-owned resources are distinct participants.

These are deductions from selected paths, not experiments of a running deployment. Untraced boundaries include full controller bootstrap/destruction and HA behavior; all cloud/provider and credential-validation implementations; exact settings precedence and propagation; full constraints/placement combinations and CAAS scheduling; complete network reachability, exposure and provider firewall effects; other storage providers/removal paths and live data integrity; all migration recovery phases; and status-history/watch delivery guarantees. Existing pages, user questions, and package or table names do not settle where any resulting reference fact belongs.
