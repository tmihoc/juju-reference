## Reading the intersections

Keep **cloud definition/region records**, **a selected credential**, **requested placement and constraints**, **provider precheck**, and **the resulting remote instance/network/storage** separate. In the traced bootstrap CLI path, a supplied region is validated, a credential and region are selected or detected, and the resulting cloud spec passes regional endpoints and that credential into preparation (`cmd/juju/commands/bootstrap.go:600-630,766-785,1280-1332`). This does not establish one universal selection precedence or other clients' behavior. In the traced machine-add service path, machine and model constraints are merged, provider placement is passed to precheck only for a provider-type directive, then merged constraints are persisted before later provisioning (`domain/machine/service/provider.go:178-219`). A passed precheck is not a machine, allocated IP, attached disk or successful bootstrap. Each provider outline below identifies its own decisive differences; generic subjects own shared behavior rather than these pages duplicating it.

## `amazon-ec2.md`

**Proposed order, from primitive interactions:**

1. **Cloud region and chosen credential.** Distinguish AWS region/endpoint in the cloud record from a credential selected for the controller/model. EC2 declares `access-key` (`access-key`, `secret-key`) and `instance-role` (`instance-profile-name`); its spec validator accepts those two types (`internal/provider/ec2/credentials.go:33-59`; `internal/provider/ec2/provider.go:76-88`). The client uses static credentials for access-key and EC2 role credentials otherwise (`internal/provider/ec2/client.go:118-126`). Bootstrap finalization replaces the credential with an instance-role credential when bootstrap constraints contain an instance role; that is a conditional handoff, not a claim that every controller has a role (`internal/provider/ec2/environ.go:197-213`). Link **cloud**, **credential**, **controller**, **constraint**.
2. **Bootstrap VPC checks and model configuration.** Bootstrap preparation optionally verifies credentials and validates the configured `vpc-id` with its force flag; new-model validation separately checks credentials and VPC (`internal/provider/ec2/environ.go:165-188`). These checks are not resource creation or proof of external access. Link **model configuration** and **VPC/subnet**.
3. **Machine request → precheck → selected location.** EC2 accepts `zone=` or `subnet=`; the subnet matcher distinguishes CIDR, `subnet-` ID, and Name tag. The provider locates the zone/subnet, checks availability, and rejects an explicit placement incompatible with existing EBS attachment zone; a separate requested availability zone is also checked (`internal/provider/ec2/environ.go:409-473,984-1064`; `internal/provider/ec2/subnet.go:25-41,51-86`). Precheck also checks a specified instance type/architecture combination (`environ.go:465-491`). Only when those attachment parameters are actually supplied does this establish their compatibility. Link **machine**, **placement directive**, **zone**, **subnet**, **constraint**.
   In the separate launch path Juju rederives zone/subnet, chooses subnet and image/type, submits `RunInstances` with security groups, block-device mappings and required metadata tokens, then on an explicit `allocate-public-ip=false` attempts public-IP disassociation; it returns the instance and hardware only after subsequent steps succeed (`environ.go:550-553,585-650,704-765,776-799`). These are conditional operations and results, not unconditional resources.
4. **EBS pool vs resulting volume.** EC2 exposes the `ebs` provider alongside common IAAS providers; its provider reports block support. Schema attributes include `volume-type`, `iops`, `encrypted`, `kms-key-id`, `throughput`; `io1`/`io2` require nonzero IOPS, non-GP3 other types reject positive IOPS, and throughput is GP3-only (`internal/provider/ec2/ebs.go:34-57,184-199,209-238,249-299,313-315`). These are pool/config checks, not proof an EBS volume was provisioned or attached. Link **storage provider**, **storage pool**, **storage instance/attachment**.

**Comparison and missing attributes:** `D:amazon-ec2.md:153-174,246-280,318-356` already gives the auth, placement and EBS slots; give the explicit placement/attachment conflict and the distinct validator stages a home rather than assuming the listed resource inventory is always realized. Named unresolved attributes: full VPC-force semantics, effective root disk pool and volume encryption/KMS combinations, profile creation and permissions, and security-group selection plus public-IP allocation branches beyond the explicit false case (`D:amazon-ec2.md:282-315,352-356`). Trace them before making guarantees.

## `google-gce.md`

**Proposed order:**

1. **Project credential and regional model inputs.** Declared `oauth2` attributes are `client-id`, `client-email`, `private-key`, `project-id`; `jsonfile` supplies `file`; `service-account` supplies its account name. Spec validation accepts all three and requires a nonempty account name on the service-account branch (`internal/provider/gce/credentials.go:20-65`; `internal/provider/gce/provider.go:70-85`). Provider config has `base-image-path`, immutable `vpc-id` and `vpc-id-force`; config validation checks force/ID and immutability (`internal/provider/gce/config.go:18-58,69-100`). Link **credential**, **cloud/region**, **model configuration**.
2. **Placement and subnet constraints before launch.** The GCE parser accepts `zone=` or `subnet=`. Zone derivation checks zone status and that existing disk attachments share a zone with explicit zone placement (`internal/provider/gce/environ_instance.go:167-191`; `internal/provider/gce/environ_availzones.go:72-94,110-158`). Precheck also validates explicit instance type and specific root-disk/type combinations, and checks for subnetworks when not using auto-subnets (`internal/provider/gce/environ_policy.go:18-57`). When auto-subnets are required, a placement subnet or space constraint is rejected; otherwise spaces filter candidate subnet IDs, with a placement match or selection among candidates (`internal/provider/gce/environ_network.go:93-110,113-170`). Link **placement directive**, **constraint**, **space**, **subnet**, **zone**.
3. **Realization and identity.** `StartInstance` resolves an image and machine type using region, base, architecture and constraints, then invokes creation; returned hardware is not identical to the request (`internal/provider/gce/environ_broker.go:31-56,71-100`). On the controller path a bootstrap instance-role constraint or, otherwise, a service-account credential can supply a service account; a general instance-role constraint is considered subsequently (`environ_broker.go:166-190`). Explain this as branch ordering, not universal account attachment. Link **machine**, **controller**, **image**, **constraint**.
4. **Persistent-disk provider.** `gce` is registered along with common providers. Its provider supports block and explicitly rejects direct filesystem sources even though the pool adviser recommends `gce` for both block and filesystem kinds (`internal/provider/gce/disks.go:25-45,49-64,78-83,98-112`). Distinguish an adviser recommendation from the lower-level provider capability; link **storage provider/pool**, **filesystem**, **volume**.

**Comparison and missing attributes:** `D:google-gce.md:83-102,188-227,251-290` names the auth modes, placements and disk type, but not the auto-subnet incompatibilities or the explicit branch precedence for controller service account. Its filesystem and block implications need the provider/adviser distinction. The precise disk-type list and defaults, VPC-force exceptions, and public IP/firewall realization are untraced here; `D:google-gce.md:236-258,267-290` should not be treated as verified in full.

## `lxd.md`

**Proposed order:**

1. **Localhost versus remote cloud record.** Detection begins with the localhost cloud and can discover LXD-protocol LXC remotes. Finalization resolves an empty localhost endpoint from the local host; for a non-local cloud with no regions it adds a default remote region (`internal/provider/lxd/provider.go:216-253,273-317`). The add-cloud schema for a remote specifies endpoint and certificate auth; selected cloud spec validation requires a credential, a valid endpoint and certificate material (`provider.go:75-121,372-395`). Do not equate this provider with an LXD container placement within another machine cloud. Link **cloud**, **region**, **machine/container**.
2. **Credential enrollment is not runtime auth.** `certificate` declares `server-cert`, `client-cert`, `client-key`; `interactive` declares optional `trust-token` and `trust-password`. In finalization, supplying both is rejected; when one is present and client certificates are absent, the branch generates/reads client certs and changes to a certificate credential, then finalizes it (`internal/provider/lxd/credentials.go:31-38,68-117,290-334`). Runtime spec validation accepts certificate rather than interactive. Link **credential**; avoid claiming success without host trust.
3. **Cluster member and instance form.** Placement accepts a plain node name or `zone=<node>` and validates a nonempty node against available zones (`internal/provider/lxd/environ_broker.go:421-450`; `internal/provider/lxd/environ_policy.go:20-26`). The validator lists supported `virt-type` values and server-supported architectures; CPU power, tags, container, allocate-public-IP, image-ID and IP-family are registered unsupported (`environ_policy.go:29-53`). Starting selects tools for host architecture, resolves the requested/default virtual type, finds an image and asks the target to create the instance (`environ_broker.go:31-84,90-140`). Link **placement**, **constraint**, **machine**, **image**.
4. **Profile/network intersection.** Instance spec includes applied profile names and constraints (`environ_broker.go:192-216`); NIC selection starts with profile NICs, lets later profile definitions overwrite earlier ones, and adds NICs for requested subnet networks when needed (`environ_broker.go:283-350`). This bounded path is not a guarantee that every model has extra NICs or space discovery. Link **network**, **space**, **subnet**, charm profile.
5. **LXD filesystems and host pool.** The LXD provider is advertised only when the server reports storage support; it supports filesystem kind and returns unsupported for volume sources. Config allows `zfs`, `dir`, `btrfs`, `lvm` drivers; default driver is `dir`, default LXD pool name `juju`. `lxd-zfs` and `lxd-btrfs` default-pool entries are appended only if validation succeeds (`internal/provider/lxd/storage.go:45-73,94-109,118-169,192-223`). A Juju storage-pool record, host pool and filesystem are distinct. Link **storage provider**, **storage pool**, **filesystem**.

**Comparison and missing attributes:** `D:lxd.md:71-124,190-219,256-293` covers local/remote, credentials and basic placement. Its `ceph` driver entry is not in the traced checker (`storage.go:94-100`); reconcile rather than carry it forward. Qualify the optional default pools and profile/device branches. Remaining named gaps: local credential discovery/access prerequisites, exact image source priority, project lifecycle, and forwarding/network backend conditions (`D:lxd.md:74-76,229-247`).

## `maas.md`

**Proposed order:**

1. **Inventory endpoint and OAuth credential.** A MAAS cloud record supplies the server endpoint; the selected `oauth1` credential has `maas-oauth`. Cloud validation checks the endpoint and credential type, then requires exactly two colon separators in the token (`internal/provider/maas/environprovider.go:117-149`; `internal/provider/maas/credentials.go:20-35,76-84`). Detection from `.maasrc` is distinct from selecting/validating the credential (`credentials.go:38-73`). Link **cloud**, **credential**.
   The provider-specific model config schema and defaults are empty; this is not a claim that generic model configuration is absent (`internal/provider/maas/config.go:15-25,43-67`).
2. **Allocate existing or compose VM.** The ordinary acquisition path sends converted constraints, positive/negative space IDs, disk requirements and optional node/zone/system ID to `AllocateMachine`. For `virt-type=virtual-machine`, Juju first asks MAAS VM hosts to compose, marks the result, waits for readiness, then allocates; absent hosts and unsuccessful matching fail, with attempted cleanup on selected failure paths (`internal/provider/maas/environ.go:630-687,690-778`). This is a request to MAAS, not evidence that a node was actually available. Link **machine**, **constraint**, **model**, **controller**.
3. **Selection and network.** A plain directive is a node name; `zone=` validates a MAAS zone; `system-id=` selects that ID. The precheck rejects nonempty system ID when `HasVirtType()` is true, a broader literal condition than merely testing a particular virt-type value (`environ.go:408-446`). During start, explicit node or system ID clears the availability-zone variable; bindings/constraints are translated into positive and negative space requirements passed to allocation (`environ.go:828-893`). Link **placement**, **zone**, **space**, **endpoint binding**.
4. **Disks at acquisition, not dynamic volumes.** MAAS registers a `maas` storage provider; `tags` accept strings/list, and whitespace inside a tag is rejected (`internal/provider/maas/volumes.go:32-59,80-103,123-168`). Provider `Supports` returns false for all kinds, `Dynamic` and `Releasable` return false, and its volume source is unsupported (`volumes.go:189-209,218-234,267-273`). Machine start filters to MAAS volume parameters and builds the allocation requirements (`environ.go:863-875`); VM compose passes storage specs to MAAS (`environ.go:705-728`). This does not imply the provider dynamically adds or detaches arbitrary volumes. Link **storage pool**, **root disk**, **volume**.

**Comparison and missing attributes:** `D:maas.md:135-138` describes both allocation and VM composition, but the earlier blanket pre-existing statement (`:17-22`) needs qualification for the compose branch. `:169-175` should distinguish plain hostname from `zone=` and capture the `system-id`/`HasVirtType` precheck. `:203-234` should distinguish the `maas` provider's actual capability predicates and compose storage request from physical-only wording. Still untraced: detailed MAAS release behavior, deployment OS selection, the full space-to-NIC conversion and all volume lifecycle constraints.

**Proposed order:**

Cloud spec validation accepts service-principal-secret and managed-identity, not interactive (`internal/provider/azure/environprovider.go:156-171`). Treat interactive enrollment and the resulting runtime credential as separate; the schema alone does not prove external identity creation or role assignment. Link **credential**, **cloud**, **controller**.
2. **Model settings, subnet placement and constraints.** Azure's config declares `load-balancer-sku-name`, `resource-group-name` and `network`; the latter two are marked immutable, and the SKU defaults to Standard (`internal/provider/azure/config.go:21-31,41-63,128-167`). Link **placement**, **subnet**, **space**, **constraint**, **model configuration**.
3. **VM request vs actual resources.** Start requires a controller UUID, sets at least its minimum root-disk constraint, finds an instance spec and attempts creation (`internal/provider/azure/environ.go:641-700`). The start path requests a public IP unless the constraint disables it, retries a conflict without creating the availability set, and initializes its returned instance without addresses; the bootstrap VM path adds network-template resources only when neither a custom network nor placement is supplied (`environ.go:762-812,855-874`). Subnet selection and cloud operations may fail; an address or VM is not implied by a request. Link **machine**, **image**, **controller**, **network**.
4. **Managed disk provider.** `azure` provider accepts `account-type` `Standard_LRS`, `StandardSSD_LRS` or `Premium_LRS`, defaulting to `StandardSSD_LRS`; it declares block, dynamic, non-releasable and no direct filesystem source (`internal/provider/azure/storage.go:24-30,60-75,85-98,121-147,168-175`). The pool adviser recommends `azure` for block or filesystem (`storage.go:44-56`); keep that recommendation distinct from the direct source kind. Link **storage provider**, **storage pool**, **volume**, **filesystem**.

**Comparison and missing attributes:** `D:microsoft-azure.md:92-127` should expose the actual auth attribute names and enrollment/runtime distinction; `:218-220` mentions Standard SKU but omits the resolved-subnet `/64` check and its skip condition. `:294-301` covers disk types but not the provider's non-releasability/direct filesystem limit. Named untraced: identity permissions and cross-subscription behavior, exact availability-set membership, later address retrieval and network security group realization (`:97-104,224-225,249-267`).

## `openstack.md`

**Proposed order:**

1. **Cloud endpoint and selected credential.** Cloud spec validates auth URL and accepts `userpass` or `access-key` (`internal/provider/openstack/provider.go:2388-2404`). `userpass` declares username/password plus optional tenant, identity version, domains and trust; `access-key` declares key/secret plus optional tenant/version (`internal/provider/openstack/credentials.go:23-35,39-112`). Credential conversion selects the auth mode, infers v3 for domain/trust when no version supplied, rejects a trust ID with explicit version below 3 and rejects trust scope combined with tenant/domain (`provider.go:826-875,879-900`). Link **cloud**, **region**, **credential**; external Keystone configuration remains conditional.
2. **Zone, flavour and root-disk request.** Only `zone=` is recognized in this provider placement parser, and zone lookup/validation occurs before use. Precheck derives zone with attachment information, validates an explicit Nova flavour, checks root disk source and rejects `root-disk` plus `instance-type` without a nonlocal source (`provider.go:682-759`). The root source accepts `local`, `volume` or a valid pool name on this path. Link **placement**, **zone**, **constraint**, **machine** and **storage pool**.
3. **Conditional Cinder integration.** Only if the environment has a volume service URL is `cinder` appended to provider types; absent that URL, registry/adviser fall back to common providers. Cinder's direct provider reports block kind (`internal/provider/openstack/cinder.go:109-150,235-241`). Root disk configuration is a separate provisioning decision (`provider.go:1665-1668`); do not promise Cinder exists or a disk was created merely because its pool is described. Link **storage provider**, **volume**, **root disk**.
4. **Network config and conditional Nova/Neutron realization.** Provider-specific config declares `network`, `external-network`, `use-default-secgroup`, `use-openstack-gbp` and `policy-target-group`; network config is parsed as a comma-separated list (`internal/provider/openstack/config.go:19-56,71-100`). The start path selects networks, conditionally creates a GBP policy target, and skips setting up security groups if a selected Neutron network explicitly disables port security; otherwise it calls group setup before attempting Nova `RunServer` (`internal/provider/openstack/provider.go:1096-1104,1110-1152,1166-1214,1253-1259`). These are conditional calls, not promises of created resources. Link **model configuration**, **machine**, **network**, **space** and **subnet**.

**Comparison and missing attributes:** `D:openstack.md:80-82,93-126` has both auth sections but the example names only userpass; add the alternative while preserving trust scoping. The root-disk note at `:221` names only literal `volume`, whereas the detailed list at `:243` already includes a pool name; align those statements. `:291-317` needs the Cinder-service-URL condition. Named untraced: floating-IP reuse, Neutron port creation, network discovery and boot-volume parameter translation (`:253-294`).

## `vmware-vsphere.md`

**Proposed order:**

1. **vCenter, datacenter and credential record.** The add-cloud schema requires endpoint, auth types and regions; the schema models regions as datacenters and offers `userpass` (`internal/provider/vsphere/provider.go:65-90`). Credential schema supplies `user`, `password` and optional `vmfolder`, with validation of the chosen auth type (`internal/provider/vsphere/credentials.go:13-44`; `provider.go:166-177`). Distinguish credential VM folder from cloud region and model datastore/network settings. Link **cloud**, **credential**, **region**, **model configuration**.
2. **Resource-pool zone and datastore precheck.** `zone=` is the provider placement form; precheck resolves placement, checks constraint zones and validates a named root-disk datastore against accessible datastores (`internal/provider/vsphere/environ_instance.go:106-124`; `internal/provider/vsphere/environ_policy.go:17-76`). At actual selection the compute resource's datastores are considered; no accessible datastores or multiple accessible datastores without an explicit choice fail (`internal/provider/vsphere/internal/vsphereclient/createvm.go:464-524`). Link **placement**, **zone**, **constraint**, **root disk**.
3. **Template and VM request.** Instance creation chooses the zone and datastore, asks a template manager to ensure a suitable template for base/architecture, constructs VM creation arguments including template, resource pool, datastore, constraints and network devices, then calls the VM client (`internal/provider/vsphere/environ_broker.go:125-180,250-274`). Template lookup tries image-metadata templates, then previously imported templates, then download/import when earlier lookups are not found (`internal/provider/vsphere/vm_template.go:45-72`). This describes Juju's path, not verified permissions, availability or a completed clone. Link **machine**, **image**, **controller**, **model**.
4. **Network and storage scope.** The creation spec generates primary `eth0` DHCP configuration and optionally `eth1` when an external network is configured (`environ_broker.go:205-238`); provider config declares `primary-network`, `external-network`, `datastore`, disk UUID/hardware version and disk provisioning type (`internal/provider/vsphere/config.go:19-25,30-64`). The environment firewaller returns unsupported for open/close and ingress-rule operations (`internal/provider/vsphere/environ_network.go:17-29`). Registry exposes only common IAAS storage providers, not a vSphere-specific storage provider (`internal/provider/vsphere/storage.go:21-28`). Do not infer that common providers or every desired guest address are unavailable/successful. Link **network**, **storage provider**, **storage pool**.

**Comparison and missing attributes:** `D:vmware-vsphere.md:199-234,282-312,318-361` covers templates, datastore and devices. Separate validated placement from successful target datastore/clone and distinguish no vSphere-specific provider from no storage of any kind. `:29-116` lists minimal permissions; exact privilege coverage is not proven by these calls. Named remaining gaps: complete template cache/import details, credential `vmfolder` interaction, supported disk-provisioning vocabulary at validation/consumer boundaries, and external network reachability.

## `unmanaged.md`

**Proposed order:**

1. **Existing SSH host is the starting object.** The manual cloud record schema requires an endpoint representing the controller host; `Open` strips `ssh:` and splits optional `user@host` (`internal/provider/unmanaged/provider.go:51-65,121-148`). Its provider detects an empty credential and declares empty auth with no attributes (`internal/provider/unmanaged/credentials.go:13-25`); this is not the same as SSH authorization. Link **cloud**, **credential**, **controller**, **machine**.
   There are no provider-specific configuration fields in the traced schema; `ModelConfigDefaults` separately supplies generic `enable-os-refresh-update=true` and `enable-os-upgrade=false` defaults (`internal/provider/unmanaged/config.go:15-17,29-56`). Link **model configuration**.
2. **Controller bootstrap configures that host.** Bootstrap checks whether the host is provisioned, ensures the Ubuntu user, detects base/hardware, then returns a finalizer that configures the machine over SSH (`internal/provider/unmanaged/environ.go:103-134`). A host, Juju machine record and successful agent setup are separate things; this does not create the host.
3. **Add a supplied machine, not cloud allocation.** In the `add-machine` CLI path `ssh:` selects the manual provisioner and passes host, user, keys and model update behavior (`cmd/juju/machine/add.go:310-315,390-430`). That provisioner initializes the Ubuntu user, checks/detects the host, records the machine, obtains a provisioning script and runs it over SSH, attempting record cleanup after certain errors (`environs/manual/sshprovisioner/provisioner.go:21-72`; `environs/manual/sshprovisioner/sshprovisioner.go:254-294`). Link **machine**, **agent**, **model**, add-machine interface. An agent-install attempt is not proof of host readiness.
4. **Explicit provider limits and discovery.** The unmanaged provider's `StartInstance` and `StopInstances` return unsupported-operation errors (`internal/provider/unmanaged/environ.go:64-74`). Its provider precheck validates constraints and rejects nonempty provider placement with an instruction to use SSH; unsupported constraint registrations include CPU power, instance type, tags, virt-type, allocate-public-IP and image-ID (`environ.go:308-350`). This is not a ban on every machine/container placement form or every other provider's SSH onboarding. `SupportsSpaces` returns true while provider `Subnets` and `NetworkInterfaces` return unsupported (`internal/provider/unmanaged/environ_network.go:18-32`); do not infer a complete discovery workflow from that flag. Link **placement**, **constraint**, **space**, **subnet**.
   On the unmanaged bootstrap-instance implementation specifically, open/close ports return nil without cloud firewall operations and ingress rules are nil (`internal/provider/unmanaged/instance.go:44-53`); this does not prove the behavior of every manually onboarded instance or host firewall.

**Comparison and missing attributes:** `D:unmanaged.md:17-25,91-98,145-152,197-216` has the existing-host and empty-auth distinction, but the zone placement listing needs reconciliation with the provider precheck, and the broad discovery narrative needs a traced consumer. Check the exact timing of empty credential persistence, cleanup, supported guest OS, firewall behavior for non-bootstrap hosts and generic storage capabilities before repeating the claims in `:19-25,91-93,208-225`. The `ssh:` path shown is an operation-specific path, not an unconditional all-client contract.
