## `client.md` — user-facing client and controller connection

**Chunk.** A client is software acting through a controller interface for a principal; the local CLI is one implementation. Its principal, target, connection, local selection and available API operations can vary independently of model state. An agent may use the same API infrastructure with a different identity and purpose. The local client store is an implementation-specific local record, not the controller database; externally hosted clients need not use it. API authorization is owned by the user/access and affected subject contracts, not by this page.

**Ordered sections.**
1. **Role and client families:** distinguish interactive `juju` CLI, browser/dashboard, and other external integrations as examples with separately maintained contracts; distinguish client from agent and controller. Registration and the Go API prove interface components, not third-party client compatibility (`cmd/juju/commands/main.go:215-266`; `api/apiclient.go:113-125`).
2. **Context and local records, where applicable:** CLI controller endpoints/CA, per-controller model selection and account details are locally held; controller and model names resolve independently of the server's authoritative state (`api/jujuclient/interface.go:17-39,81-107`; `api/jujuclient/file.go:425-455,495-510,737-795`). Link CLI data-directory and environment behavior to `juju-cli.md`; cloud credentials to `credential.md`.
3. **Connect and identify:** the Go API validates connection info, dials WebSocket endpoints, uses a configured login provider or legacy provider, and closes on login error; `Open` can return redirect information. Unspecified URL schemes default to `wss`; TLS/proxy options are conditional. This is a traced Go-client path, not a mandatory flow for every external client (`api/apiclient.go:113-124,143-153,188-228,550-590,622-631,648-693`).
4. **Invoke and receive:** RPC calls carry facade name/version, object ID, method and parameters; available facade versions and login scope matter. Other HTTP handlers have their own scopes/authorizers, so do not conflate them with all RPCs (`api/apiclient.go:1498-1514,1644-1651`; `apiserver/apiserver.go:1074-1093,1109-1129`). Link controller API, per-subject calls and generated command pages.
5. **Limits and failures:** connection, authentication and authorization are distinct; controller-only vs model login, CAAS restrictions and upgrade/migration modes can restrict the root (`apiserver/root.go:496-525,528-560`). Connection/login failures or redirects do not establish operation outcomes. For login alternatives, the repository has legacy tag/password/macaroons, session tokens and client-credentials providers (`api/legacyloginprovider.go:49-56,132-169`; `api/sessiontokenloginprovider.go:41-51,80-99`; `api/clientcredentialsloginprovider.go:47-54,75-95`).

**Comparison/proposal.** `docs/reference/client.md:14-50` already distinguishes agents and has a store inventory. Add a connection/transport section, qualify store details as CLI-specific, and replace the exclusive password-or-macaroon narrative with appropriately scoped login-provider alternatives. Qualify “every call”/“can make the calls” (`:31-38`): trace each relevant facade, permission and route rather than promising uniform authorization or success. Keep third-party client mentions as external integrations rather than treating their features as proven by the Juju tree.

**Unknowns.** Complete login-provider selection for each CLI operation and deployment; every HTTP and facade authorization policy; exact support, version compatibility and state model of each external client; all redirect/reconnect behaviors. Resolve with the login factory call sites, route/facade implementations and each external project's versioned contract.

## `juju-cli.md` — local user command interface

**Chunk.** The local `juju` executable is a command dispatcher and environment-dependent client; it has its own invocation, options, local context and output/exit semantics independent of controller state. Local plugins are separate executables; web CLI is not automatically the same command set.

**Ordered sections.**
1. **Invocation and discovery:** `juju <command> …`, help and command index; no-argument interactive shell only when stdin and stdout are terminals; `--version` has special dispatch (`cmd/juju/commands/main.go:128-195`). Command-specific syntax, flags, output and errors belong on command pages.
2. **Select target:** on the traced `ModelCommandBase` path, explicit model identifier precedes `JUJU_MODEL`; absent controller resolves through environment/current store and absent model through the current model. Conflicting controller qualifiers in `JUJU_MODEL` and `JUJU_CONTROLLER` fail in `DetermineCurrentController` (`cmd/modelcmd/modelcommand.go:165-193`; `cmd/modelcmd/controller.go:145-169`). `juju switch` inspects or changes current context with its own syntax (`cmd/juju/commands/switch.go:42-55,94-105`). Do not claim these exact defaults for every command.
3. **Local data and configuration:** `JUJU_DATA` overrides platform default; otherwise Unix-like data home uses `XDG_DATA_HOME/juju` or `~/.local/share/juju`, Windows uses `APPDATA/Juju` (`juju/osenv/home.go:57-92`). Link env variable and client-store references; local files may include account information (`api/jujuclient/interface.go:90-107`).
4. **Command execution and extensions:** registered built-ins receive flags/args; missing local commands may execute `juju-<name>` on PATH, inheriting streams and selected `-m`/`-c` environment; embedded mode disables plugin fallback (`cmd/juju/commands/main.go:220-245,303-319`; `cmd/juju/commands/plugin.go:29-79,99-137`). Plugins have their own versioned behavior.
5. **Observations and limits:** output and exit status are command-specific; initialization, selection, permissions, API version, model type, provider and maintenance can fail before or after dispatch (`cmd/cmd/cmd.go:438-459`; `apiserver/root.go:496-525`). Link per-command and compatibility references rather than promising uniform output or backward-compatible features.

**Shared command-page form from contract.** `cmd/cmd/cmd.go:41-61,255-276,438-459` provides a real common interface: command purpose/name, positional args, flags, initialization and run. Therefore a command reference can consistently give **purpose → invocation/options → target/context → effects/output/errors → examples/related subjects**, but effects and permission/model restrictions need source-specific traces, not generated help alone. The nested list is a discovery index, not proof of behavior (`work/surface-ledger-113.md:13-15`). Authored exceptions must remain explicit: `switch` is locally scoped and ambiguity-sensitive (`switch.go:45-55`); `dashboard` has a currently unimplemented server call (see below); external plugin interfaces are not registered built-ins; action/exec asynchronous task behavior belongs in action/script references.

**Comparison/proposal.** `docs/reference/juju-cli.md:8-47` has an index, data directory, compatibility and LXD example but omits invocation, selection, plugin dispatch and conditionality. Add those sections; qualify same-major compatibility (`:29-31`) through the child policy and operation-specific checks instead of guaranteeing that simple commands work. Keep LXD as one provider example, not the definition of local execution.

**Unknowns.** Full command-to-base-class/flag precedence inventory, supported OS/package matrix, output formats and error cases, all plugin discovery rules, version-policy enforcement. Trace individual command implementations and release-specific generated/source diff.
