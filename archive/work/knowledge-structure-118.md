## 1. What the system does

Juju connects a user's intent to work carried out over time in a model. A controller hosts authenticated entry points and coordinates models; a model has its own identity, cloud/region association, settings and access relationships. A request is made by a principal against a target under a particular access level; model command blocks are separate controls checked by particular calls, not a synonym for permissions. A cloud credential is also separate: forced removal on the traced path clears references from models in the transaction, whereas the downstream provider outcome is not established. Updating a credential checks authentication type, but its per-model connectivity checker does not actually test connectivity. Sources: `work/system-model-115.md:9-13`, `work/model-command-blocks-113.md`, `work/held-out-115.md`.

A charm supplies declarations and executable logic; an application realizes a charm in a model; its units are individually managed. A charm endpoint declaration, application endpoint/binding, and relation between participating application endpoints are not the same thing. A relation has participant-specific state: on the traced path a unit can enter only if the relation and unit are alive and the unit belongs to a participating application; writing application-scoped relation data requires leadership. Cross-model ingress has its own relation and network conditions; those checks do not prove that a provider firewall was applied. Sources: `work/endpoint-boundary-111.md`, `work/system-model-115.md:15-21`, `work/skeleton-workload-117.md:31-42,76-87`.

Agents act on changes and execute workload code. Some unit hooks follow watched state, but `update-status` has a timer-driven path: a watcher is neither every event's cause nor proof that a hook has run. Hook and action commands operate in a context that affects what they can do. A declared action is different from an invocation, and an operation groups tasks for targets; the traced administrative exec path can also target machines. A task being enqueued does not establish its completion. Sources: `work/system-model-115.md:23`, `work/skeleton-mechanisms-117.md:34-54,89-99`, `work/skeleton-workload-117.md:7-17`.

On the traced machine path, requested constraints are merged with model fallback and validated; provider placement is passed to precheck when applicable. Only later does a provisioner attempt to realize a machine as a cloud instance. Model resource tags and machine-specific inputs form tags for a provisioning request; the traced EC2 path adds an instance name and supplies tags to its request. Neither accepted state nor the constructed request proves the cloud created or tagged an instance. MAAS's `tags` **constraint** instead selects nodes: a shared word does not imply the same contract. Sources: `work/skeleton-infrastructure-117.md:7-18,37-51`, `work/structure-challenge-e62.md:41-49`.

Storage combines a reusable pool, an identified instance, backing filesystem and/or volume, and attachments connecting it to units and machines. Detaching an attachment is not the same as destroying the instance. In the traced EBS-backed filesystem case, filesystem provisioning is machine-scoped but its backing volume and ownership are model-scoped; force-removing the host schedules attachment cleanup without selecting that instance and its volume for destruction. This does not guarantee that forced provider detachment runs, or that data survives or can be reattached. Source: `work/storage-boundary-114.md`, `work/filesystem-lifetime-114.md:5-36`.

Finally, observations are separate from the things observed and from the request result. Full status composes subject information; a current unit status and the history records queried later are different. For the traced unit setters a successful current write is followed by a history-recording attempt; a recorder error is logged rather than returned. Audit recording has its own enablement, filtering and buffering conditions. Logs, telemetry and database inspection expose other views, none by itself proving provider success or a complete past. Object-store paths can share content; removing one path is not necessarily removal of shared content. Sources: `work/structure-challenge-e62.md:15-39`, `work/held-out-116.md`, `work/skeleton-mechanisms-117.md:55-65,101-122`.

## 2. The distinctions that constrain reference chunks

A **contract** here means a bounded statement of identity or vocabulary, a condition-dependent behavior, or an observation exposed on a supported surface. A **semantic address** is a stable link target for a contract; it can be a section rather than a file. Both are analysis terms, not additional Juju object types.

The system's evidence demands that the reference preserve distinctions where collapsing them changes a reader's deduction:

* **Scope and identity:** controller/model; charm/application/unit; machine/cloud instance; cloud credential/agent password/user grant. Shared names, storage location or dependence do not make these interchangeable. For example, agent login is identity-bound and does not itself authorize a later target operation (`work/authentication-challenge-116.md`).
* **Declaration, request and realized effect:** a charm declares an endpoint; the application realizes a binding; a relation composes endpoints. A provisioning request has inputs and a later provider result. A bundle plan is not a deployed model. Keeping these distinctions allows accepted-but-not-yet-realized and failed outcomes to be described without contradiction (`work/endpoint-boundary-111.md`; `work/skeleton-mechanisms-117.md:25-32`).
* **Relationship and participants:** a grant relates a principal and target; a storage attachment relates instance and unit; relation state varies with the participant. A relationship's validation and removal may be different from either participant's. A linkable explanation can sit within a larger page: the evidence does not require one file per relationship.
* **State, transition, and observation:** current status differs from historical records; a watcher delivery differs from the state change and from an actor's subsequent work; an audit record differs from the operation recorded. Specify the producer, conditions, timing and observable result only where those distinctions matter; a table or worker alone is not an inclusion test (`work/structure-challenge-e62.md`; `work/disk-inspection-116.md`).
* **Shared and varying rules:** constraints are an input to more than one allocation path, but validation and provider behavior can differ. Status-history logic is similar in the traced setters, but call-specific validation and instance-to-machine consequences remain distinct. A reusable explanation plus links is a maintainability choice; call-local copies are equally expressive. No experiment has established that either arrangement helps readers more (`work/structure-challenge-e62.md:51-66`).
* **Interface and target:** `juju ssh`, a hook command, a database REPL and an API call have different callers, contexts and result surfaces even when they refer to the same subject. A generated help page proves a generated representation, not that a backend path succeeds or is available in every context (`work/skeleton-nested-117.md:29-56`, `work/skeleton-infrastructure-117.md:87-101`).

These distinctions disprove neither a broad subject with relationship/history attributes nor a call-only documentation form. E62's single-subject comparator was underspecified; its object-store case was historically contaminated. The case evidence supports semantic distinctions, not an indivisible ontology or unique owner. Physical filenames, a one-home convention and link navigation are editorial choices to review, not measured properties of the code.

**E63 refinement:** `work/boundary-rules-e63.md` compares independently varying records, exposed operations and a scope/dependency rule against image selection, target-specific annotations and ID allocation. All three paths met bounded behavior criteria, but the annotation and sequence cases were already described in existing reference prose and are contaminated as held-out cases. The same facts can be represented with a shared section or a shared page with identical rule/link counts; no rule has won a physical-file decision. A post-hoc source trace raises a potential image-priority discrepancy; the helper-only synthetic probe is not a live provider outcome. The structure is not locked in.

**E64 refinement:** `work/operational-boundaries-e64.md` operationalizes target invariant versus interface selector and supports the distinction on the model/DB-REPL and plugin-context paths. A real CLI/plugin smoke and synthetic SQLite query confirm the explicitly bounded observations; the `.switch` name collision is a possible defect, not a live finding. The preregistered equal-content comparison measures two copies versus one with two links, but a shared section and a shared page still require an editorial tradeoff. Neither competing accurate placement is falsified; the global structure remains unsettled.

## 3. Candidate connected reference structure

The following is a map of **addresses and links**, not a new classification imposed on all pages. A named address can be an existing section. Arrows mean “link to the contract needed to interpret this one,” not a universal execution sequence.

### Control and access

`controller` ↔ `model` → `cloud` / `credential` / `model-defaults` / `configuration`; `user` → access/grant → target; `model` → command blocks → only calls that check them; `agent` → agent authentication → target-specific authorization. `controller` links to high availability, upgrade, database, object store and backup; `model-migration` links both controllers and the model. Backup's neutral address is needed, but controller versus a separate mechanism home remains unresolved. The controller, model, credential, user and agent entries expose their own scope and interactions; a shared access address defines the target-dependent vocabulary rather than repeating a user grant as a cloud credential. Authentication is not authorization for all subsequent calls. Sources: `work/system-model-115.md:9-13,25,31-33`; `work/authentication-challenge-116.md`; `work/backup-subject-113.md`.

### Workload, integration and execution

`charm` → declared options/endpoints/actions/resources/storage; `application` → selected charm, values, bindings, trust and `unit`; `relation` → participant application endpoints, participating units and data; `offer` / `external-controller` → cross-model relation; `hook` / `hook-command` → unit and relevant relation, storage, secret or action context. `action` → shared `operation` / `task` → output and status; administrative `exec` → the same run-record concepts, with machine and unit targets where supported. `secret` → references/revisions → `secret-backend`; keep backend availability and selector differences per call. This graph deliberately connects declaration, realization, participants and execution without forcing all of them onto a single subject page. Sources: `work/skeleton-workload-117.md`, `work/skeleton-mechanisms-117.md:34-54,89-99`, `work/surface-probe-111.md`.

### Infrastructure and dependent resources

`model` / `application` / `machine` → `constraint` and `placement-directive` → provider-specific machine allocation; `machine` → cloud instance, `unit`, `status`, network device and inspection-only disk facet. `space` ↔ `subnet` / `zone`; application endpoint binding → space; exposure and relation ingress link to their own network conditions. `storage` contains separately linkable pool, directive, instance, backing and attachment contracts → unit/machine/provider/removal. Cloud-specific pages link these generic contracts and add only the provider-conditioned intersections demonstrated for that provider: auth, bootstrap, allocation, networking and storage as applicable. Resource labels (`resource-tags`) link model configuration to machine provisioning and the relevant provider; MAAS selection tags link to constraints instead. Sources: `work/skeleton-infrastructure-117.md`; `work/skeleton-cloud-machines-117.md`; `work/structure-challenge-e62.md:41-49`.

### Cross-cutting processes and observations

`removing-things`, `scaling`, `model-migration` and `controller-upgrade` each connect their participants, initiation, stages and supported observations; individual calls retain their own access, guards and return values. `watcher` → particular holder/payload and relevant subject; `hook` → actual trigger and agent; `status` → subject-specific values and separately scoped current/history queries; `log` → audit/agent logging and configuration; `telemetry` → tracing/forwarding. `database` → `juju-db-repl` and inspector-facing records; `object-store` → path/content and backed artifacts; backup connects both. A current value or notification is not a completion guarantee. Do not infer a shared state machine or blanket stream semantics from these links. Sources: `work/skeleton-mechanisms-117.md`, `work/system-model-115.md:31-35`, `work/structure-challenge-e62.md`.

### Interfaces, catalogs and outside systems

A CLI command address describes its invocation, target, selection, result and link to the domain contract; commands differ from hook/action commands, which additionally require their actual execution context. Host tools such as `juju-db-repl`, `juju-introspect`, agent binaries and compute-resource diagnostics describe their host, privilege, input and result, not a model entity's schema. Configuration-key references identify key, scope, type/default and affected behavior only when established; controller keys, model keys, model defaults and charm-declared application options are not one namespace. Cloud pages are intersections of a provider with generic cloud, model, machine, network and storage contracts, not proof all providers behave alike. Dashboard, web CLI, Pebble, plugins and compatibility references describe their actual interface and externally versioned limits. Navigation/index pages point to these addresses but do not define an ontology; preserve the stakeholder-set landing organization. Sources: `work/skeleton-nested-117.md`, `work/skeleton-tools-117.md`, `work/reference-skeletons-117.md:33-46`.

## 4. How an entry acquires its internal shape

For an applicable entity, preserve the user's settled order: **definition and scope → relevant records/invariants → applicable change streams → actors → interactions → configuration and failure indexing**. Introduce vocabulary before claims that need it, and link the migration process and verified subject-specific exceptions where relevant. These are conditional roles, not mandatory headings: an unavailable stream is not evidence no stream exists, and a supported internal record must still be relevant to the audience. The order is a documentation decision, not an assertion that every behavior runs database → watcher → actor; the timer-driven hook is a counterexample.

A process entry instead needs its participants, initiation/guards, stages and dependencies, separately observed outcomes, failures and recovery *where actually established*. A tool entry needs execution context, invocation/inputs, target selection, effects and result/errors; a key entry needs its scoped value, applicable validation/default and consuming effects. A relation entry must identify participants and participant-dependent rules. These are not mutually exclusive page types: a storage page, for instance, can contain an instance description, an attachment relationship and its operations. Similar sections appear when the contracts actually share roles; different validation, timing and observation stay visible rather than being filled from a generic template.

### Worked example A: application endpoint → relation → hook command

1. At `charm`, define the endpoint declaration and link to its realization on `application`.
2. At `application`, describe endpoint/binding and link its relation composition; binding is not a firewall reachability promise.
3. At `relation`, define participants and data scopes, then the traced entry and write conditions. Link the unit and leadership contracts. Cross-model ingress gets its own conditions and links to network policy, not an unconditional cloud-firewall result.
4. At the `relation-set` command, describe its inputs and applicable relation context, including the traced application-data leadership check; link the relation data rules. At `hook`, explain the actual triggers separately; do not say every hook follows a watcher.

The four addresses capture different dependencies. One physical file for endpoint declaration versus a linked section is not settled by that fact. Evidence: `work/endpoint-boundary-111.md`, `work/skeleton-workload-117.md:31-42,76-87`, `work/skeleton-nested-117.md:41-47`.

### Worked example B: remove a machine with filesystem storage

At `machine`'s removal interaction, state the applicable force/guard and that jobs are scheduled, linking the storage and generic removal contracts. At `storage`, distinguish pool, instance, backing volume/filesystem and attachments, then explain which attachment or resource is selected under a traced removal path. At the EBS provider intersection, explain the model-scoped volume/machine-scoped filesystem composition; link rather than assume all providers have EBS lifetime rules. Result: a reader can distinguish deleting an attachment from selecting an instance for destruction, but cannot infer provider detachment, retained data or reattachment. Evidence: `work/filesystem-lifetime-114.md:5-36`; `work/storage-boundary-114.md`. This is a concrete reason to change the unconditional sentence on `storage.md:14`, not proof of a new file.

### Worked example C: status write and history query

At unit or machine status-setting calls, state the particular caller, validation and effect. Propose a linkable `Status history recording` section under `status` for the shared conditional current-write → recording-attempt behavior of the traced setters; link calls to it. Keep the provisioner's conditional second machine-status write at the provisioner interaction, and the query's filters and any verified retention at the query. Equal-content comparison gives one statement plus two links versus two statements; it measures repetition/indirection, not reader benefit or a unique home. The help/validator accepts six kinds the traced history filter does not handle; a real service/reader with **synthetic records** returned a workload match and skipped a filesystem match with no error. This is a possible code/contract defect, not a live result; investigate before finalizing the contract, not a prose-only fix. Evidence: `work/structure-challenge-e62.md:25-40,51-66`.
