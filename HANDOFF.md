## Guidelight
Find a stable skeleton for entity reference pages that captures both the similarities and the differences between topics, is explanatory (fits what exists) and predictive (fits new topics), and is derived from the Juju 4.1 code, not from taste. Every task is judged against it: does it make the skeleton more certain, or show where it is not?

## Session discipline (binding)
1. **Pre-register first.** Write the question, criterion, thresholds and caveats in `structure-discovery-plan.md` before running a test. Report fails as fails; label every post hoc reading.
2. **First principles, not precedent.** The existing pages, how-tos, Terraform provider and JAAS docs predate this work and may chunk wrongly; correcting wrong chunking is the point of the investigation. Derive chunks from the software (identity, address, lifecycle, coupling as the code shows them). Existing patterns are data to explain or correct: agreement is weak evidence, disagreement is a candidate correction, never a criterion (user, 2026-10-20).
3. **Choosing the next step:** when the user asks for the best next thing, optimise for results-oriented and from first principles: the step that produces a concrete result (a list, a rule, a correction, a derived structure) by reasoning from properties of the software, not another round of validating against precedent (user, 2026-10-20).
4. **No arbitrary decisions.** Keep testing an uncertainty until the answer falls out (the user's rule). Do not offer option menus; present the worked artifact or the test. Check the decision record before reopening a settled question (the causal-chain order of parts is the user's decision).
5. **Propose before changing the skeleton or adding a section to a page.** Never add structure to a page unprompted.
6. **Code is the source of truth.** Comments are not evidence. No human raters. Subagents may judge, but re-verify their key findings against the code (one quote, one grep) before relying on them; a blocked or denied agent is reported, never worked around.
7. **Reports are complete.** Define every coined term on first use, give the basis for each claim (experiment, number, citation), say what is sure and what is not, and give an example. The user should not have to ask what a word means.
8. **Git and environment.** Push to origin only and ask before every push and force-push (`--force-with-lease=<branch>:<old sha>`). Never touch the main checkout `~/git/juju`. The sandbox does not start: run git network, Go, Sphinx and shell commands with it disabled. Check both docs builders (`dirhtml` and `latex`). Every PR targets 4.1, branch starts `4.1-`, PR text fenced and never hard-wrapped, no Jira.
