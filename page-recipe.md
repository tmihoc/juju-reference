# Page recipe for an entity reference page (working form, session 82)

Status: the form that the `ssh-key` pilot settled into after about twenty rounds of the user's feedback. Every rule is also at the end of `skeleton-v6.md`. Not tested on readers (E44 showed no structural gain), and tested only on one small entity. Run `tools/check_page_rules.py <page.md>` before showing a page.

## 0. Before writing
1. Confirm the page exists in `experiments/e33/page-manifest.json` and that its level is page, not section (user decision 2026-10-20: kind decides the level).
2. Get the facts, never the prose of the old page:
   - tables: `ggarch scaffold <ddl> --db <model|controller> --tables a,b,c` (4.1 DDL in `experiments/e11/`);
   - calls: `python tools/extract_facade.py apiserver/facades/client/<facade>` gives, per method, the access check, the block check and the client-visible error codes and messages, each with a line;
   - then read each call's service and state code for rules, and the watchers and workers for change streams;
   - the old 4.1 page and the how-to, only as a list of facts to verify.
3. The extraction script reads the facade only. It does not see domain errors that never reach the client with a code, errors raised in helpers, or access checks made in a different layer. Read the code around each method.

## 1. Sections, in this order, each only when its facts exist
| Title | Holds |
|---|---|
| (lede, no heading) | One definition sentence (kind of thing, what sets it apart), then at most two sentences saying where it lives, who holds it, how it comes and goes. Warnings that matter to a user go in a `{warning}` after it. |
| `<Entity> database schema` | Figure, definition, one intro sentence, then the records with their rules (`Rules:` group). Only invariants of the records stay here (uniqueness, always-present parts, the values a field can take); what a call does (defaults it fills in, what it refuses, what it removes) goes in that call (user, 2026-10-20). Only what an interface shows; no column lists. |
| `<Entity> change streams` | Only if a client or agent can watch the entity. |
| `<Entity> calls` | An opener defining the set, then one `###` subsection per call. |
| `<Entities> and model migration` | Only the exception to the generic export, in one paragraph, with the migration linked as background. |
Never: an Identity section, an errors section, an Agent section until the Agent rule exists (C23), a section that announces itself ("this section covers").

## 2. Rules for the text
- Every opening sentence is a definition: the kind of thing, then what sets it apart. "X is how Y does Z" is not one.
- A figure is the first thing in its section. Its alt text carries every fact it shows, in plain English. Its caption carries how to read the figure and what follows from its shape — what to read first, the rule the edges imply — not the cardinality inventory the edges and the record bullets already show (queue item 19, trial pass over model, relation, and application, session 99; the alt text keeps the cardinality for accessibility; sequence and state-diagram captions keep their stories).
- A bullet list never appears without a main-text intro sentence that says something (no counting: "has one rule and two errors"). A list of one item is prose.
- **"Operation" is the domain word; one documented API interaction is a "call" (user, 2026-10-21, session 93).** An operation is only the group of tasks that one run of a script queues across units: the code's `domain/operation`, the CLI's `juju operations` and `juju show-operation`. The editorial sense is a **call**: the section is `<Entity> calls`, the anchor `(x-calls)=`, the lead-in "The caller, the rules, and the errors are:", the prose "No client makes this call". Quoted error strings (`operation is blocked`), CLI page names, and the domain anchors (`action-listing-operations`) keep their words. The rename of the 33 existing pages is one queued commit.
- **"Hook tools" are "hook commands" (user, 2026-10-21, session 95).** Every mention of a specific hook or hook command hyperlinks the name to the section that documents it: a hook links to its anchor on the hook page (`{ref}`config-changed <hook-config-changed>``), a hook command to the old CLI reference page that documents it (`{ref}`relation-set <hook-command-relation-set>``); a name with no page (`leader-elected`, `storage-id`) stays in plain code font. Quoted CLI help text in the imported hook-command pages keeps its own words, as quoted error strings do.
- Call subsections are titled with a gerund and the entity (`Adding SSH keys`), in the how-to's order. Each opens with the gerund phrase as the subject and says what the call does (`Adding SSH keys stores one or more keys ...`, `Destroying models removes a model and everything in it.`), never "<Gerund> is the call that ..." (user, 2026-10-20).
- Per call: `Caller:` (who may make the call: for a client, the user it acts for, with the access level, linked — a client is software, the level is the user's, so the line reads `A client, for a user with write access to the model.`; for an agent, a worker, or a hook command, the identity it must have; the block that must not be on; user, 2026-10-21, session 93), `Rules:` (all rules of the call grouped under one bullet as nested items without the word Rule, even when there is only one; user, 2026-10-20), `Errors:` with the message the client sees, its code, a trigger and a remediation.
- Say what is true, never what is absent. A database schema states life stages (alive, dying, dead) only when the entity has them; for an entity without them it says nothing (a "has no life stages" sentence is an unearned negation with a term the reader has not met).
- State a fact once. Effects of another entity's call (user removal, model removal, migration) are stated as a rule or one paragraph here, never by defining that call.
- Before showing a page, list every term of the page that a reader may not know (agent, unit, application, controller, bootstrap, certificate authority, TLS, facade, API, region) and check that it is linked or defined at its first mention in each section. Link jargon at its first mention in each section: reference page, access-level anchor, external definition. Where no page exists, define it in a parenthetical. Never link to a CLI command page and never write "the CLI offers": reference pages are client agnostic.
- Table names: not in titles, bullet titles, figure labels, or entity-page prose (session 92: the closing mapping paragraphs are gone; see the density test below). The record-to-table mapping, the views that join or filter records, and the `.ddl <name>` pointers live with the database tooling — `juju-db-repl`, and the generated tables-by-topic page once it lands (TODOS item 000000) — and the database page keeps its own mapping, because its subject is the storage layer.
- **Test for a database-schema rule (user, 2026-10-20).** A rule stays in the database schema only if the database itself enforces it (a unique index, a not-null or check constraint, a trigger, or a foreign key) or the schema fixes the allowed values. A rule that a service, a facade, or a worker checks or applies when a call runs (defaults, required parts, what it refuses) goes in that call, even when it holds for every record in practice. Before keeping a rule in the database schema, find the constraint in the DDL and cite it in the working notes; if none exists, move the rule to the call that creates the record.
- **Test for what stays in a database-schema section (user, 2026-10-21, session 92).** A record, field, rule, or sentence stays iff a reader can meet it through a surface the page documents: a call the page documents writes it, a read the page documents shows it, or the database enforces it (the rule test above). Otherwise one of three dispositions: hide (internal bookkeeping stays in the shared JujuSchema, out of the page's view; type case `model_namespace`, removed in session 91), contain (a record that only explains a shown one rides as a `context:` chip), or relocate (prose whose reader is another page's reader moves there; a rule carried by relocated prose moves into its record's bullet first). Type case, decided and done (session 92, the user's call): the record-to-table closing paragraphs are gone from the 33 entity pages — the pages are new and dense and must not read as a code dump — the views and `.ddl` pointers gone with them, because the schema views run `labels: hidden` and `fields: hidden`, so no table name remains on an entity page; the mapping's home is `juju-db-repl` and, when it lands, the generated tables-by-topic page (TODOS item 000000); `database.md` keeps its own mapping because its subject is the storage layer. Personas stay a lens per part, never a structure; removals cite the test with evidence, never a reviewer's taste alone.
- Remediations state what to do, never a consequence ("Remove the models first", not "Remove the models, or the cloud stays").
- Use the Oxford comma in every list of three or more (user, 2026-10-20).
- Put the base case first, then the variants (user, 2026-10-21). On the relation page the regular relation comes before the peer, subordinate, and cross-model relations. Applies to every list of kinds, types, or cases.
- A kind that records decide (a relation is peer when it has one endpoint, cross-model when an endpoint belongs to a remote application) is described in the database schema, in the bullet of the record that decides it, like the cloud types on the cloud page. Keep the label of each kind.
- A status with allowed transitions has its allowed values in the database schema. Its state diagram and transition table live in the call that changes it (the database fixes the values, the service decides the changes). Examples: the model migration phase, the task status on the action page, the relation status. (Amended, 2026-10-30, session 103: a mechanism with its own reference page keeps its machine there — the model migration page; the call that starts it links it.)
- Never write "databag" (user, 2026-10-21; a staff developer: the Juju codebase says records or settings). Say "settings" or "relation settings", as the tables `relation_unit_settings` and `relation_application_settings` do.
- File each fact with its owner (user, 2026-10-21). A subsection of the database schema or of a call holds one subject. A fact about a record goes in that record's bullet (identifiers, defaults, implicit records). A rule goes in the Rules of the call it constrains. A status diagram is the first thing in the call that changes the status, with no subsection of its own. A heading that bundles facts because the old page kept them together is a relic: dissolve it.
- Name the caller first (user, 2026-10-21). A call's opener and the Caller line say who makes it: a client, a unit agent, or a hook command. Order calls by that channel, client first. Never head them by a reader persona. Do not put the channel in the title ("Finding relations", not "Finding relations in hooks").
- The Caller line for an agent states an identity, not a level (user, 2026-10-21). Define "unit agent" (and machine agent, application agent) once, in the introduction of the Calls section: the process that runs the unit's charm, logged in as its unit, acting only for that unit. Each agent call then says "A unit agent, for its own unit." and adds only what is specific (the leader, the lease). Never write "the agent of the unit (see ...)": a pointer to another call is not a definition.
- Draw records and software apart: an entity-relationship view shows records only, a sequence view shows software only (user, 2026-10-21, on the old relation databag figure that mixed them).
- Do not glue two facts with different subjects using ", and" (user, 2026-10-21). Bad: "A request can carry a batch of credentials, and the answer has one result for each." The "and" claims a relation (also, then, therefore) and never says which; the second clause leans on a vague noun in the first; two rules share one bullet. Fix: two short sentences with one subject and one fact each ("The call takes a list of credentials. Each credential in the list gets its own result."). A real relation gets its own word (so, then, because, when). Name the concrete thing: no "batch", no "carry". "And" stays for same-kind items (Oxford-comma lists) and for two verbs of one subject. Applies to docs, commit messages, PR text, and chat replies.
- American spelling (the docs use authorize 55 times to authorise once). Words: `Required access`, not `Authority`.
- No version phrases (user, 2026-10-21, session 93): the pages document 4.1, so no fact is scoped "in 4.1"; such a note belongs to the release notes. The one exception is the how-to for the 3.6 to 4.1 upgrade, whose subject is the version transition.
- Top of the page: `See also: {ref}`Juju | Manage <things> <manage-...>`, {ref}`Terraform Provider for Juju | Manage <things> <tfjuju:manage-...>``.

## 3. Figures
- Database schema: scaffold the tables, keep the full records in the model, and draw the view with `fields: hidden`, `routing: orthogonal`, `labels: hidden` and `same-size` constraints. Chip labels are plain nouns that match the bullet titles; the table stays in `ground`. Records other pages own are `context-record`. Every box is explained by a bullet.
- Align the chips so related chips share a row; lines must be straight.
- A sequence only when the call crosses at least three actors, at least one outside the controller or running on its own, and the order decides what the reader sees. Cite the code per step in a comment; put failures in the caption.
- No separate neighbours figure.

## 4. Check before showing the page
1. `python tools/check_page_rules.py <page>` (titles, forbidden phrases, spelling, lists without intro).
2. `ggarch check`, render the figures, look at them.
3. A full docs build and `latex`; the preview server shows the page.
4. For each rule in a database schema, name the DDL constraint that enforces it; move the rest to calls. Re-run `tools/extract_facade.py` and compare every error and access line with the page.
5. Read the page once against Grice: quality (each claim traced), quantity (nothing missing a client needs, nothing only a Juju developer needs), relation, manner (no metalanguage, no ambiguity).

**The inclusion test (user, 2026-10-30, session 103; full rubric in `work/cq-rubric-103.md`).** A fact stays only if all three hold: it is true, traced to the code on a supported surface (CLI output, API wire, status, an operator log line, or the database through its tooling: `juju dump-db`, `juju-db-repl`, backups) and re-checked whenever the page is touched; a reader can meet it there; and it answers a recorded question of a named audience (operators; client/tool developers; charm developers; storage/incident inspectors; AI readers — the table in the rubric file), with this page owning the answer. When the tests disagree: meetable but this page's reader is not asking → move the fact to the owning page or cut it; someone asks but cannot meet it → write only what they can meet; neither → it stays in the code. Every fact has exactly one owning page; every other page links. A mechanism story (how model migration runs, how watchers work) also has one owning page, told at mechanism level in surfaced vocabulary, and is not exempt from the question test. Not Juju developers: the code is their documentation, except the labeled developer corner of the how-tos.
- **Lede length (user, 2026-10-20, session 85).** A lede is one definition sentence and at most two more (where it lives, how it comes and goes). What a node runs, what a backend keeps, defaults and counts go to the section that owns them. Compare against the model, SSH key and SSH server pages before showing a page.
- **Diagrams belong on reference pages only (user, 2026-10-20, session 85).** How-tos get text and links to the reference; they never carry a figure.
- **A page for a group that the manifest keeps together may carry the entities of its sections (space, subnet, zone).** Each old entity anchor stays on the new page, in the list item or lede that defines it, and the old pages redirect (`docs/redirects.txt`).
- **A list is built up to (user, 2026-10-20, session 85).** The paragraph before a list ends in a colon and says what the list holds (for a change streams section: which things the streams carry), so that the list is the end of the sentence and not a new topic. `tools/check_page_rules.py` flags a top-level list whose previous paragraph does not end in a colon. Applied to the change streams sections of the model, SSH server, controller, secret backend, machine and space pages. (Session 103: the space change-streams section no longer exists; no watcher for spaces is handed out anywhere in the code.)
- **Level of a page is derived, not copied from a prompt (user, 2026-10-20, session 85).** Before folding entities into one page or splitting them, read the manifest (`experiments/e33/page-manifest.json`), the code (own typed ID, own facade method, own lifecycle) and the how-tos, and record the reason in the commit. Space, subnet and zone are three pages: a subnet has its own listing and how-to, and a zone is named by constraints and placement directives.
