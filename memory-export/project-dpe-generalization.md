**Status (2026-10-19):** proposed in conversation, NOT ratified, not tested against all 24 entity pages. Do not rewrite ADR-016, `architecture.md` or any page on it without the user's go.

**The reading.** Premise from `docs/explanation/architecture.md`: Juju keeps a goal state and reconciles reality with it. Declaration, persistence and execution are then three relations to a goal-state record, not places and not times: something writes it (declaration; admission rules: who may write, what is valid), it is held (persistence; integrity rules: identity, uniqueness, life), something reads it and acts on the world and reports back (execution; progress rules: ordering, retries, gating). Placement is a free variable: the record can be a controller or model database row, a client file, an agent file; the actor can be the CLI, the controller, a unit agent. An execution step usually ends by writing another record, which is the next loop's declaration, so a whole flow is a chain of these cells. Bootstrap is the first cell, with the client as writer, store and actor, ending in a write into the controller's store; `architecture.md` already says "This is the typical shape once a controller exists".

**Consequences.** (1) File an error by the kind of rule that failed, not by place or time (`model already exists` is an integrity rule, so persistence). (2) A "lives in / run by" fact per record and loop falls out as the free variable. (3) One home per claim, and mentions (message string plus link) elsewhere; see the mention-versus-claim test. (4) `architecture.md` needs at most one sentence naming the pattern.

**Why:** the user asked for a generalization from first principles after bootstrap (client-local files, client-run execution) and the duplicated-rule debate; see [[no-verdict-asking]].

**How to apply:** test the reading on cases before adopting it (agent-local state, status writes, zone and subnet, secrets); related [[entity-reference-form]], [[client-agnostic-sweep-todo]].

**Constraint added 2026-10-19 (user):** the reference pages keep their path to ggarch diagrams, a data-model diagram per entity (persistence) and operation diagrams (execution). Do not trade that away unless there is good reason. Evidence so far: of the 41 removed fences (`fence-manifest.md`), roughly 25 sat under persistence (data-model slices), 15 under execution (flows, slideshows) and 1 under states; none under declaration (count by heading, approximate). Persistence has a code referent (the SQL schema) and execution a referent in loops and state machines; declaration has none of its own beyond the API surface, so it is the weakest candidate joint. The reliability test should expect most disagreement between declaration and persistence (both are immediate refusals to the user).

**Open problem raised by the user (2026-10-19):** some entities are both software and an abstraction in the database, and the abstraction takes scope relative to other abstractions. The controller is the example: it is the controller agent (an actor that executes) and the singleton controller record (a thing held in a store), and the record scopes the model records (models belong to a controller; the controller model is itself a model). Never fully resolved. In the relational reading an entity can play actor and record at once; the scoping (which records contain which) is a further structure the three-relation reading does not cover. `controller.md` currently documents no error rows at all (found when sampling for the blind-classification test).

Of 14 filed declaration, 7 were read as persistence; of 13 filed execution, 6 were read as persistence and only 5 as execution; persistence was the sponge (23 of 40 assigned). Rater B (request / stored state / world) split 12 request, 27 stored state, 1 world, and its labels were nearly independent of our filing (filed D: 5 request, 9 state; filed P: 3 and 10; filed E: 4, 8 and 1 world), so the filing is not a proxy for what the check depends on. Reading: layer is a weak organising axis for errors; it says nothing against persistence (records, schema referent) or execution (operations) as chunks for the non-error content where diagrams attach. ADR-016's locality principle (beside the thing constrained) looks like the real part; the layer anchors and raise-site filing look like a convention. Caveats: single LLM raters, my definitions, filing used code location the raters did not see. Not yet done: repeat runs for noise, a human rater, the synchronous-or-later check.

**Correction (2026-10-19, user's challenge):** span is an ownership rule, not an inclusion rule. A fact that could live lower can still be what an operator needs; docs/ must surface every operator- or client-observable fact, by pulling local facts up (generation or embedding), and only developer-only facts may stay lower. E0 now has two dimensions: span (who authors) and audience relevance (who needs it). Open question for the user: priority order of audiences (operators, client authors, platform developers).

**Proposed definition of docs/ (2026-10-19, unratified):** user's draft "contributor content that bubbles up + anything a user might need" judged too loose. Tighter: docs/ renders (1) every fact observable at a named user-facing interface (operator CLI/config/status/logs, client-developer API and errors, charm-developer hook tools/metadata/Ops), pulled up by generation from where it is authored, plus (2) spanning facts no single package can state, for platform developers. Local developer-only facts stay in doc.go, schema comments, CONTRIBUTING.md. Generous for generated facts, strict for root-authored.

**Audience ratings (2026-10-19):** 39 statements, two blind LLM raters (36/39 agree on user-facing). Local statements: 9 of 13 user-facing (the errors and rules operators meet); cross-domain: 6 of 7 developer-only; cross-process: 7 of 9 user-facing; worker loops user-relevant only when they emit something visible. So span does not predict audience, and "could live lower" would have dropped 23% of the sample that users need. Hypothesis for the structure: user-facing local facts pulled up beside what they constrain; user-facing spanning facts (operations) authored at the root; developer-only spanning facts (cross-domain record relationships, data-model diagram) at a marked developer level; developer-only local facts stay in doc.go and schema comments. Next: E5 pilot on a page, human raters, E4 corpus.

**Refinement (2026-10-19):** two joints, not three parts: data model (invariants = integrity rules) and operations (preconditions = admission rules; unfolding = progress rules), with rules and errors attached to the thing they constrain. DPE was an approximation (persistence ≈ data model, execution ≈ operations, declaration ≈ where a request meets a rule). Limit: reconciliation loops are not single transitions. Test in E5.

**No metalanguage (2026-10-19, user):** never write sentences about the page's own organisation ("this page covers", "the operations below...", "these errors:", "see above/below"). It signals crossed wires in the presentation; fix the structure so it carries the meaning (nest errors under the rule they enforce; operations name their own trigger forward; a mention is the message string, no "see"). Also no back-and-forth references that make the reader hold two places at once.

**Correction (2026-10-19, user):** inline "see X" pointers are fine in reference docs (Wikipedia style). The rule bans layout-dependent and page-describing language ("below", "above", "these errors", "this page covers"), not pointers off the page.
