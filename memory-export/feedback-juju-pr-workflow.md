Every PR carved out of `4.0-docs-rewrite-juju-architecture-juju-9632` targets **juju 4.1** (`upstream/4.1`).

- Before branching: `git fetch upstream && git pull upstream 4.1` (on local `4.1`), then create a branch whose name STARTS with `4.1-` (e.g. `4.1-docs-<topic>`).
- Follow `~/git/misc/rules.md` and `~/git/juju/CONTRIBUTING.md` (and `docs/agents/*`): Conventional Commits with detailed bodies (root cause, what/why, how verified); PR description per `PULL_REQUEST_TEMPLATE.md`, problem -> fix, grouped by reader impact, Jira link only where a card exists (`**Jira card:** [JUJU-NNNN](https://warthogs.atlassian.net/browse/JUJU-NNNN)`; only PR 4 has cards, JUJU-9632 and JUJU-9635; strike the Links section on the other PRs and never invent a number), no unheaded bullet lists.
- Review rounds (2026-09-30): re-fetch every PR's reviews before stating one is review-free (lee-van-cleef[bot] posts rounds hours apart). Commit reviewer-driven fixes as separate commits on top (see [[separate-review-commits]]) and push normally after the user says go. Only when the user asks for a rewrite of a pushed commit: `git commit -F` of a message starting `amend! <old subject>` (blank line, new full message), then `GIT_SEQUENCE_EDITOR=true git rebase -i --autosquash upstream/4.1` and `--force-with-lease=<branch>:<old sha>`; the classifier refuses `git commit --amend`. Build docs with a current venv (../juju-upgrade-guide/docs/.venv) and the sandbox off; `go` (snap) and sphinx_sitemap also need the sandbox off. Never run `autogenerate-docs.py --force` before checking `go` works: it deletes the generated pages first.
- PR text is given to the user inside a fenced code block, never hard-wrapped.
- Docs-only PRs: `cd docs && make html` must pass; check `docs/.sphinx/warnings.txt` for new warnings; state explicitly if the build is impossible.
- Autogenerated docs: fix the Go source, run `cd docs && make regenerate-docs`, commit both; never hand-edit generated .md.
- Go files touched: run `gci` (see AGENTS.md); verify claims in Go source before documenting.
- Upstream PR link format: `https://github.com/juju/juju/compare/<base>...tmihoc:juju:<branch>`.
- PUSHING (user rule, 2026-09-30): push to `origin` (tmihoc/juju) ONLY, never to `upstream` (juju/juju); ask before every push; a force-push (after a rebase) needs its own go and `--force-with-lease=<branch>:<old sha>`. The user opens and merges the PRs.
- GIT SAFETY (mistake on 2026-10-19): a failed `cd` made a rebase run in the main checkout. Chain worktree and rebase steps with `&&`, check `pwd` and `git branch --show-current` before any rebase, reset or checkout, and never touch the main checkout's HEAD. Worktrees go under `~/git/misc/` (the sandbox write list).
- PR text is written for the BASE branch the PR targets (upstream/4.1), not for the source branch the content came from; run the fidelity check against the base's pages too.
- Environment (2026-10-19): the Bash sandbox fails to start (bubblewrap user-namespace error), so git network access, `go`, `sphinx-build` and `curl` run with `dangerouslyDisableSandbox`; the old docs venvs are broken (Python 3.14): use `~/git/misc/docs-venv`.

**Why:** the user asked (2026-09-29) that this be remembered for every PR; the source branch is a 318-commit, 157-file PR being split up.
**How to apply:** check these before creating any branch/commit/PR description in ~/git/juju. Related: [[juju-docs-epics]].
