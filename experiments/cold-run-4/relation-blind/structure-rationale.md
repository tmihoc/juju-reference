# Structure rationale for draft-relation.md

Method: no template was used. I listed the facts the source holds about a relation, tagged each with the audience question it answers (T1 to T10), grouped by "same reason to change and same question" (ledger: "A chunk is facts that change for the same reason and answer the same question"), and gave a section to each group. Titles are the type names or the question's subject.

Source artifact kinds used: SQL schema (0024-relation.sql), Go domain record types and constants, domain state and service code (checks and errors), apiserver facade code (client codes), unit-agent hook tool code, firewaller worker, bootstrap config schema, charm metadata validation, and upstream docs.

Additional question added: **T11 -- Who may do it, and what does the refusal say?** (write access, leader-only writes, refusal texts). The list T1 to T10 lacks the "who may" half of T1 as an independent question for settings and status, because the leader rule differs per fact.

## What came out

Eleven parts: a lede and ten headed sections, with nesting that follows the record, not a prescribed order: type sections (peer, non-peer with three children and one grandchild), then four question sections (rules, ID and key, status, settings). The order is the order of the questions a new reader asks: what is it, what kinds are there, what must hold to make one, how do I name one, what state is it in, what data does it carry.

## Where the questions and maxims could not decide

1. **Exclusive or coexisting types.** The ledger asks for "Types of X" only for exclusive alternatives. Peer against non-peer is exclusive (one endpoint against two: core/relation/key.go:32-37). Subordinate, non-subordinate and cross-model are not provably exclusive: scope is container when either endpoint is container-scoped (relation.go:292-300), a CMR is decided by a remote application (relation.go:4126-4152), and the source never states whether a container-scoped relation can involve a remote application. The draft nests them as siblings under non-peer, as upstream did (kind-of nesting), without a title that claims exclusivity.
2. **Juju-info placement.** Source owner says application and charm; reading path says relation page. Two measures disagree, so the contract's "at least two measures agree" test yields no change.
3. **Fragment test for non-subordinate.** Alone it is a Fragment (one definition and one fact); the label's inbound link is the only reason it stays. The maxims alone would fold it into non-peer.
4. **Where the rules (T3) end and the integrate call's errors begin.** R19 says an error nests under the call that raises it; Q5 is open. The draft states the conditions as relation rules and the two client codes I could verify, and leaves other refusal codes to the call page.
5. **Status.** Status values appear in two docs (here and the goal-state hook command, a per-unit view). The questions do not say which page owns the relation status; Q1 is open.
