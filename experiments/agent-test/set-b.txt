# Machine

See also: [How to manage machines](https://canonical.com/juju/docs/juju-cli/latest/howto/manage-machines.md#manage-machines)

In Juju, a **machine** is a [compute resource](https://canonical.com/juju/docs/juju-cli/latest/reference/resource-compute.md#resource-compute) from a machine [cloud](https://canonical.com/juju/docs/juju-cli/latest/reference/cloud.md#cloud): a bare cloud instance, or a LXD container on one, requested implicitly by a deploy or add-unit placement, or explicitly through the controller API.

#### IMPORTANT
A LXD container is named after its host machine: `0/lxd/5` is LXD container `5` on machine `0`. Containers appear under ‘Machines’ in status outputs.

A machine has a **data model**, the records that describe it and the rules those records keep, and a set of **operations** that create, provision, reprovision, reboot and remove it. Each rule and error sits with the record or the operation it constrains.

<a id="the-machine-in-the-data-model"></a>

<a id="machine-persistence-rules"></a>

## Machine data model

A machine is stored in the model’s [database](https://canonical.com/juju/docs/juju-cli/latest/reference/database.md#database) as one primary record that anchors it, plus several records that each point at it. The rules and errors sit under the record they constrain.

- **Primary entry:** The single record that anchors a machine: an internal system ID the other records point at, and the name the client types (the designation `0`, `1/lxd/0`), unique per model.
  - *Rule:* A machine’s name is unique per model. Machine numbers are `0` or positive integers without leading zeros, and containers nest one level deep (`0/lxd/4`, never `0/lxd/0/lxd/0`).
  - *Related errors:*
    - **`machine not found`**: *Trigger:* A lookup by machine UUID or name that matches no machine. *Remediation:* Check the model’s machines.
    - **`machine already exists`**: *Trigger:* A model migration imports a machine whose name the target model already holds. *Remediation:* Migrate into a model that has no machine of that name.
- **Network identity:** A pointer naming the shared net node; a machine and all units running on it anchor to the same node.
- **Life:** `alive`, `dying` or `dead`, plus a flag saying whether the cloud instance survives teardown. The cloud instance record has a life of its own, which gates the machine’s deletion.
  - *Rule:* A machine becomes `dead` only when it is `dying` and hosts no containers, units or storage.
  - *Related error:*
    - **`machine is dead`**: *Trigger:* An operation on a machine whose life is `dead`. *Remediation:* None; the machine’s lifecycle has ended.
- **Base:** The OS channel plus architecture. A satellite record flags manually provisioned machines; containers carry their container type.
- **Constraints:** A pointer into the [constraint](https://canonical.com/juju/docs/juju-cli/latest/reference/constraint.md#constraint) record.
- **Parent record (containers only):** Holds two pointers, the child and its host. Removal, model migration and recovery also read it.
  - *Related error:*
    - **`machine has no parent`**: *Trigger:* Asking for the parent of a machine that is not a container. *Remediation:* Check that the machine is a container (`<host>/lxd/<n>`).
- **Cloud instance record:** Tracks the creation state, the hardware (arch, CPU, memory, root disk, virtualisation type) and the availability zone. Born with the machine; the instance ID stays empty until the cloud reports it. Removal, status, storage provisioning, network, model migration, recovery and agent passwords also read it.
  - *Related errors:*
    - **`machine not provisioned`**: *Trigger:* An action that needs the instance runs before the cloud has reported an instance ID. *Remediation:* Wait until the compute provisioner has recorded the instance.
    - **`machine cloud instance already exists`**: *Trigger:* Recording an instance for a machine that already has one. *Remediation:* Check for a second provisioner acting on the same machine.
- **Status records:** Two records.
  - The agent’s health report, written by the machine agent: `pending`, `started`, `stopped`, `error`. `down` is never written, only read when the agent has not been seen recently.
  - The provisioning lifecycle, written by the controller and by the provider or container broker: `pending`, `allocating`, `running`, `provisioning error`, `unknown`. `provisioning error` is a status value: cloud and container providers record it when allocation fails.
- **Special machine kinds:** Derived, not stored; the schema’s own views classify a machine from the records around it.
  - **LXD container:** A machine linked to its host by a machine-parent record; provisioned by the host’s agent.
  - **Manual machine:** Provisioned by the user over SSH; the records keep the manual flag.
  - **Controller machine:** Hosts the [controller agent](https://canonical.com/juju/docs/juju-cli/latest/reference/agent.md#controller-agent) and every model worker.

*A machine is one primary record that the other machine records point at. The brackets list each record's descriptive columns: the agent's identity (nonce and password hash), the keep-instance flag and the hostname sit on the primary record; the parent, manual, platform, constraint, cloud instance and status records are keyed by the machine; a reprovision request is keyed by the machine's name. Lines join a record to the record it points at, and every line is a foreign key in the 4.1 model schema.*

**Writers:** The machine service inserts the records (`AddMachine`, `SetMachineCloudInstance`); the removal service carries out the teardown.

<a id="machine-watchers"></a>

## Machine change streams

The machine domain’s watchable service offers real-time change streams over the machine records, instead of polling loops. The [operations](#the-machines-machinery) below name the stream that triggers them.

- **Machine life and dependants:** Drives the local shutdown watcher.
- **Container life:** Drives host-side container provisioning loops.
- **Model machines:** Drives the compute provisioner.
- **Instance states:** Drives the instance poller’s steady-state mirroring (life, start times, cloud instances) and the reboot machinery.

Every watcher fires an initial baseline snapshot on creation, followed by notifications on qualifying changes. See [the watcher pattern](https://canonical.com/juju/docs/juju-cli/latest/reference/watcher.md#watchers).

## Machine operations

Runtime operations are split between the controller and the individual host machine. The controller orchestrates provisioning through background workers, while the local machine agent, a [Juju agent](https://canonical.com/juju/docs/juju-cli/latest/reference/agent.md#agent), manages internal lifecycle and workload placement.

Much of this work is triggered by the machine [change streams](#machine-watchers).

<a id="machine-declaration-rules"></a>

### Machine requests

A client asks the controller for compute in two ways. An **explicit** request creates machines through the controller API, gated on model [write access](https://canonical.com/juju/docs/juju-cli/latest/reference/user.md#user-access-model-write). An **implicit** request is a deploy or add-unit placement, and most machines arise this way. A machine usually hosts one unit, and placing several units of the same or of different applications on one machine saves resources.

- **Target designations:** Comma-separated lists naming new or existing targets.
  - `0`: an existing machine; `0,4`: machines 0 and 4.
  - `lxd`: a new container on a new host; `lxd:25`: on machine 25.
  - `0/lxd/4`: the existing container `4` on machine `0`.
  - An empty designation: a new machine.
  - `lxd` or `lxd:25` with `virt-type=virtual-machine`: a VM instead of a container.
  - `3,0/lxd/2,lxd:5`: machine 3, container 2 on machine 0, and a new container on machine 5.
  - Machine clouds only; rejected on Kubernetes models.
- **Base:** A machine’s **base** identifies its operating system image: the OS name, `@`, and the OS channel as `<track>` or `<track>/<risk>` (`ubuntu@22.04`, `ubuntu@22.04/stable`). A base replaces the older notion of a series.
- **Machine constraints:** Constraints can be set directly on a machine, as well as on the model or an application. Only an architecture different from the recorded instance’s is compared.

A request for a machine is refused with one of these errors:

| Message                                         | Trigger                                                                                                                                                                  | Remediation                                                         |
|-------------------------------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------|
| `machine name "<name>" has too many containers` | A machine name with more than one container level.                                                                                                                       | Name the container directly under its host machine.                 |
| `invalid container type "<type>"`               | A designation or a container constraint names a container type other than `lxd` (the only one 4.1 supports).                                                             | Use `lxd`.                                                          |
| `invalid machine constraints`                   | The constraints name a container type or a space that does not exist.                                                                                                    | Correct the container type or the space.                            |
| `machine constraint violation`                  | The constraints are set on a machine whose recorded cloud instance has a different architecture from the one required; architecture is the only characteristic compared. | Require the architecture the machine has, or request a new machine. |

See also: [Terraform Provider for Juju | Manage machines](https://canonical.com/juju/docs/terraform-provider-juju/latest/howto/manage-machines/#manage-machines)

### Machine provisioning

- **Controller-side provisioning:** The compute provisioner, driven by the model-machines [change stream](#machine-watchers), monitors unprovisioned machines, requests cloud instances, and records the instance ID and addresses as they become known.
- **Agent-side provisioning:** Host machine agents provision and manage local LXD containers through the LXD broker, driven by the container-life [change stream](#machine-watchers) over the controller API.
- **Manual provisioning:** The controller renders a setup script, executed externally over SSH, after which the host agent registers itself.

### Machine reprovisioning

The controller accepts a request declaring that a machine’s cloud instance is lost and asking for a replacement (for example, with `juju reprovision-machine`). It checks eligibility first, then the liveness gates: the machine agent must be absent and the provider must report the instance missing or not running. One transaction then detaches the lost instance, gives the machine’s units new ordinals so the replacement unit agents start with fresh identities, departs the units from their relation scopes while archiving their settings (so the remaining units see a consistent departure), resets the machine-scoped storage state, and returns the machine and its instance to `pending`; the compute provisioner then provisions the replacement.

- **Eligible machines:** Only an `alive` machine that is not a container, a controller machine or a manually provisioned machine, hosts no containers, has no model-scoped storage attached, and has no reprovision request pending is eligible.

A reprovisioning request is refused with one of these errors:

| Message                                                                                                                                                  | Trigger                                                                                              | Remediation                                                                     |
|----------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------|---------------------------------------------------------------------------------|
| `machine is not alive`, `machine is a container`, `machine is a controller machine`, `machine is manually provisioned`, `machine hosts child containers` | The machine is `dying` or `dead`, or is of a kind that cannot be reprovisioned, or hosts containers. | Reprovision only an `alive` machine that is a plain, provider-provisioned host. |
| `model-scoped storage attached to machine`, `storage scope is ambiguous`, `machine storage is not alive`                                                 | The machine’s attached storage cannot be reset safely.                                               | Detach or remove the storage first.                                             |
| `reprovision request already exists`                                                                                                                     | A reprovision request is already pending for the machine.                                            | Wait for the pending request to complete.                                       |
| `machine agent is still present`                                                                                                                         | The machine agent still reports presence.                                                            | Stop the agent or confirm the machine is lost.                                  |
| `machine provider instance is running`                                                                                                                   | The provider reports the instance as running.                                                        | Stop or remove the instance at the provider, then retry.                        |
| `machine cloud instance changed`                                                                                                                         | The machine’s instance differs from the one checked, because a replacement appeared in between.      | Retry the request.                                                              |

### Machine removal

The controller marks the machine `dying`; the agent, which learns of it through the machine-life [change stream](#machine-watchers), triggers shutdown once assigned units and storage clear; scheduled jobs purge the records; the machine’s keep-instance flag decides whether the cloud instance is released. The removal rule is the data model’s: a machine becomes `dead` only when it is `dying` and hosts no containers, units or storage.

### Machine reboot

The reboot machinery, driven by the instance-states [change stream](#machine-watchers), decides whether a machine shuts down, reboots or does nothing: a machine whose parent needs a reboot shuts down, a machine that needs a reboot itself reboots, and otherwise nothing happens.

The reboot logic raises this error:

| Message                                           | Trigger                                                      | Remediation                                                                                                                     |
|---------------------------------------------------|--------------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------------|
| `grandparent machine are not supported currently` | The lookup finds a machine whose parent itself has a parent. | None; name validation refuses containers nested deeper than one level, so the check guards a layout that Juju does not support. |
