# Entity reference template v2: proposal for discussion

Draft of 2026-10-19. Builds on `error-inventory-vs-howto-troubleshooting.md`
(the analysis), `entity-page-form.md` and ggarch ADR-016 (the current form).
Nothing here is applied; it needs the user's decisions. Triggers in the worked
example are verified against upstream/4.1 (`internal/migration/precheck.go`,
`internal/worker/migrationmaster/worker.go`); remediations are drafted from the
code and still need a check before publishing.

## 1. What the current form gets right and where it stops

Right: every domain error constant has one home beside the thing that raises
it, with trigger and remediation, and completeness is checkable (363 constants,
49% documented at the time).

It stops short in four places, all visible in the migration howto:

1. The user holds a message and a task (migrate), not an entity. Migration's
   errors live on model, user, credential, machine and cloud pages.
2. Many messages are not constants: composed (`aborted, removing model from
   target controller: <reason>`) or templated (`machine <id> is <life>`).
3. A bullet with more than about four errors reads badly as nested bullets.
4. Nothing proves completeness, and nothing lets a howto link to one error.

## 2. Proposed changes to the template

A. **Operation bullet.** For tasks that cross entities (migrate, deploy,
   remove, upgrade, integrate) the owning entity page gets one bullet in its
   execution layer, named for the operation, with the phases in order and, per
   phase, the status message the user sees and the failures that can end it.
   Cross-entity failures appear as one row that links to the page that owns the
   error. The declaration layer's bullet for the same operation links to it.

B. **Failure table.** Above four errors in one bullet, switch from nested
   bullets to a table: Message as seen | Trigger | Remediation | Source (the
   package that raises it, one short path; useful to Juju developers and cheap
   to generate). Constants and templated messages share the table; a template
   shows its placeholders as `<name>`.

C. **Three message kinds**, stated once in the form:
   - constant: the literal Go message (today's shape);
   - composed: `<prefix>: <inner>`, documented once on the loop that composes
     it, with the known inner values listed or linked;
   - passthrough: one row per source ("errors from the cloud provider",
     "errors from Charmhub") saying to read the message; no inventory.

D. **Generated error index.** `docs/reference/error-index.md`, generated from
   the Go source (every `ConstError` in `domain/**/errors`, message, domain,
   the doc comment of the constant as the trigger) joined by message string to
   the page that documents it. Undocumented constants appear in the index as
   "not documented" (the gap is visible); a small allowlist marks internal ones.
   Same pattern as the generated CLI pages and the existing CI check
   "Autogenerated docs are up to date". Composed and templated messages stay in
   the hand-written tables, which the index links to by section.

E. **Link granularity.** An error row cannot hold a MyST label, so the index
   and the howtos link to the section that contains the row. A later step could
   add a small `{err}` role that creates a target per message; not needed for v2.

F. **Howto troubleshooting becomes a pointer.** Each howto entry is keyed by the
   message as seen and says only what to do next, linking to the reference row
   for cause and remediation. A howto keeps a procedure only where the fix is a
   multi-step task (create the user on the target, reconcile the cloud).
   A howto never restates a trigger.

G. **Stated completeness.** The form claims completeness for Go constants (the
   index proves it) and for the messages of documented operations (maintained by
   hand, reviewed against the source when the operation's code changes). It
   makes no claim for provider and store passthrough.

## 3. Worked example: model migration on `model.md` (execution layer)

Draft text for the operation bullet (shown as a pipe table for readability; the page would use a `{list-table}`); this replaces the two migration rows now on
the page and the "Troubleshooting" dropdowns in `howto/manage-models.md`.

- **Model migration:** `juju migrate` moves a model to another controller. The
  source controller's migration master walks the phases below, writing a status
  message at each step; `juju status` shows it in the Notes column and
  `juju show-model` in the migration section. If any phase fails, the migration
  aborts and the model stays on the source controller.

  Status messages, roughly in order (the wait for agents recurs in several phases): `performing source prechecks`, `performing target
  prechecks`, `exporting model`, `importing model into target controller`,
  `uploading model binaries into target controller`, `<phase>, waiting for
  agents to report back`, `checking machines in migrated model`, `activating
  model in target controller`, `transferring ownership of cloud resources to
  target controller`, `successful, removing model from source controller`.

  A failure ends in `aborted, removing model from target controller: <reason>`;
  the reason is one of the messages below, often prefixed by the phase that
  failed (`model data transfer failed, <inner>`, `model activation failed,
  <inner>`).

  | Phase | Message as seen | Trigger | Remediation |
  |---|---|---|---|
  | Source prechecks | `model is <life>` | The model is dying or dead. | Wait for it to be removed, or cancel its removal. |
  | Source prechecks | `model is being imported as part of another migration` | The model is the target of an unfinished migration. | Wait for that migration to finish or abort. |
  | Source prechecks | `model has revoked credentials` | The model's cloud credential is revoked. | Set a valid credential on the model, then retry. |
  | Source prechecks | `machine <id> is <life>` | A machine (a model machine on the source side, a controller machine on either side) is not alive. | Let the removal finish or bring a machine back, then retry. |
  | Source prechecks | `unit <unit> hasn't joined relation "<key>" yet` | A unit has not entered scope in one of the model's relations. | Wait until the unit has joined, then retry. |
  | Source prechecks | `all charms now require a manifest.yaml file, this model hosts charm(s) with no manifest.yaml file: <list>` | The model runs a charm revision without a manifest. | Refresh the listed applications to a revision that has one. |
  | Source prechecks | `fan networking not supported, remove fan-config "<value>" from migrating model config` | The model config sets `fan-config` or `container-networking-method` (fan networking). | Remove the key from the model config. |
  | Source prechecks | `cannot migrate to controller due to issues:` followed by a list | The upgrade validators found blockers for this model. | Resolve each listed issue. |
  | Source prechecks | `controller: upgrade in progress` | The source controller is upgrading (the controller checks on the source side carry the `controller:` prefix). | Wait for the upgrade to finish. |
  | Target prechecks | `model has higher version than target controller (<model> > <controller>)` | The model's agent version is above the target controller's. | Upgrade the target controller first. |
  | Target prechecks | `source controller has higher version than target controller (<src> > <tgt>)` | The controllers' major or minor versions are incompatible. | Use a target controller at the same or a newer version. |
  | Target prechecks | `model's cloud "<cloud>" not found on target controller` | The target does not have the model's cloud. | Add the cloud to the target controller. |
  | Target prechecks | `model named "<name>" already exists` / `model with same UUID already exists (<uuid>)` / `model is being migrated out of target controller` | The target holds a model with the same name or UUID, or one that is being migrated away. | Rename or remove the clashing model; wait if one is leaving. |
  | Target prechecks | `target controller does not support the model migration format; upgrade the target controller to Juju 4.1 or later` | The target's migration-target facade is older than version 8. | Upgrade the target controller to 4.1 or later. |
  | Validation | `machine sanity check failed, <n> error(s) found` | After the transfer, the machines Juju lists differ from what the cloud reports. | Reconcile the cloud and Juju (for example remove the leftover instance), then retry. |
  | Validation | `<phase>, timed out waiting for agents to report` / `<phase>, some agents reported failure` | Agents did not validate against the target in time, or reported an error. | Raise `migration-agent-wait-time`; read the agents' logs. |
  | Cleanup | `removing exported model failed: <inner>` | The source copy could not be removed after the model went live on the target. | Remove the leftover source model; the migrated model is already live. |

  Errors that come from the target's import (a missing owner, an unknown
  credential) are wrapped in `model data transfer failed, <inner>`; their inner
  messages are listed on the user and credential pages (`user not found`,
  `credential not found`) and linked from here.

What the howto keeps after this change: the preparation checklist (back up,
configure throttling for large models, same secret backend), the command, how to
watch progress, and a short "If the migration fails" paragraph: read the
message in `show-model`, find it in the table above, fix it, and run
`juju migrate` again.

## 4. What it costs and what it settles

Costs: the table form needs a decision on width in the Sphinx theme; the index
generator is a new script plus a CI step; the operation bullet means some
errors are written once and linked twice; every operation page needs a review
whenever its worker changes.

Settles: howto troubleshooting boxes become pointers (item F), the migration
messages that no page documents today get a home, and the stale 3.x messages in
the howto disappear instead of drifting.

## 5. Decisions, derived (to ratify)

Each question is settled by a principle the project already holds, not by taste.

1. **Table or bullets: errors always in a table; rules stay prose bullets.**
   The form's goal is preattentive scanning by a reader holding a message. A
   table lets that reader scan one column. A threshold ("a table above four")
   makes the page's shape depend on a count, so adding a fifth error rewrites a
   section and breaks the predictability test (the reader can locate every slot
   on every page). The split that does not depend on a count is by content:
   errors are homogeneous (same four attributes), rules are not. Use the
   `{list-table}` directive: tested nested inside bullets, no pipe escaping,
   diff-friendly. Verified with a minimal Sphinx build.

2. **Source column: omit it from the hand-written tables; the generated index
   carries it.** The raise site is how we file an error, which makes it a
   maintenance fact, not a reading fact. Code paths rot (`internal/worker/
   sshkeyupdater` was renamed within weeks); a path written by hand is the
   next stale claim, the exact failure the howto shows. A path generated from
   the source is always current. So the hand-written page keeps the message,
   trigger and remediation, and the index lists the source.

3. **Index: a generated page under Reference, plus a CI up-to-date check.** The
   index exists for the reader with a message in hand, so it has to be a page:
   searchable, linkable from howtos. The CI check is for maintainers and the
   repo already has the pattern ("Autogenerated docs are up to date"). Page and
   check are two halves of one thing; nothing is left to choose.

4. **Order of operations: migration, then removal, then cross-model relations,
   then deploy and upgrade.** Order by undocumented constants times how often
   users hit them. Undocumented now: removal 16 of 22, crossmodelrelation 10 of
   15, modelmigration 12 of 13, while the application domain (deploy) is
   already 44 of 70 documented, and the upgrade page no longer exists.

5. **Howto edits: the unit of change is one operation, reference rows and the
   howto pointer together, as a follow-up PR after #23451.** The pointer links
   to rows that must exist, and the rows without the pointer leave the howto's
   duplicate in place. Splitting either way leaves a dangling link or two
   sources of truth. It cannot ride in #23451 (model.md is already in its diff,
   so a second change to it conflicts). The template and ADR changes live in the
   ggarch repo and carry no PR.

6. **DPE ideas: not a blocker.** Items A to G change item shapes inside the
   execution layer and add a generated index. They do not touch the three-layer
   skeleton, so the DPE ideas can reshape the layers later without redoing this.

Two further rulings that fell out while testing the example:

- **Ownership of operation messages follows the raise site, as before.** The
  precheck and worker messages are raised by the migration code, so the
  operation's table owns them. Constants raised in other domains (`user not
  found`, `credential not found`) stay on their entity pages and appear in the
  operation as a link. One claim, one home still holds.
- **Row order is the order the failures occur (a Phase column), not
  alphabetical.** The operation is read top to bottom as it runs; the generated
  index provides the alphabetical view.
