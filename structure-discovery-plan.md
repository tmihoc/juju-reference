# Discovering the right structure for the reference docs: action plan

Draft of 2026-10-19 (session 77). Status: a plan, nothing in it is decided or
applied. It follows from the blind-classification result (below), the diagram
requirement, and the user's worry that declaration / persistence / execution
(DPE) may be a false chunking: "I hate false chunkings", and "it's even more
dangerous if it's mostly right".

## 0. What the structure is for: bubble-up documentation

Added 2026-10-19 on the user's steer. The target is not the errors, and the
plan must not over-optimise for them. The reference docs are the root-level
`doc.go`: the home for notions that do not fit lower in the code. A package's
`doc.go` can say what that package does; it cannot say what is true only across
packages, domains, processes or time (an entity realised by schema, state,
service, facade, worker and client; a lifecycle shared by many entities; an
operation that crosses entities; the controller as both software and a
database abstraction scoping the models). Those statements are the bubble-up.

Consequences for the plan:

- **Span decides ownership, not inclusion.** Added after the user's challenge
  (2026-10-19): a rule that says "this fact could live lower" must never mean
  "so the user docs omit it". The readers of a `doc.go` are Juju developers;
  the readers of these pages are operators, client authors and platform
  developers. Two questions, kept apart: who authors the fact once (span:
  local facts are authored lower, spanning facts at the root), and does a
  reader of any audience need it (relevance: decides inclusion). A local,
  user-relevant fact is pulled up into the reference by generation or
  embedding, so it is shown once and cannot drift. The completeness check
  against monsters: every fact an operator or client author can observe must
  appear in the reference; only developer-only facts may stay lower, behind a
  link.
- **Span is a candidate axis (H8).** Place each statement at the lowest
  common ancestor of the code it describes. A statement whose ancestor is one
  package belongs in that package's `doc.go` (docs links to it or generates it);
  one whose ancestor is a domain, `domain/`, or the repository root is
  bubble-up. What it spans (packages, domains, processes, time) may be the
  real joint, and it is checkable against the code.
- **Today's lower docs are thin.** There are 294 `doc.go` files. The
  shared-vocabulary ones are substantive (`core/life`, `core/watcher`); the
  domain-level ones are one-liners (`domain/machine/doc.go` is five lines). A
  great deal of local content (records, rules, errors) lives only in the
  reference pages. Part of the structure question is which of that should move
  down, leaving the reference to hold the spanning notions.
- **E0 comes first** (below). The other experiments then run on all kinds of
  content, not only errors.

## 1. The question, stated so it can be answered

A structure is right relative to the readers' tasks and to the system's own
joints. Two questions, kept apart:

1. **Joints.** Which divisions of the material correspond to something real in
   Juju (a separate artifact, a separate rate of change, a difference the
   reader can observe), and which are only a convenient grid?
2. **Tasks.** Which structure lets a reader reach what they need with the
   fewest wrong turns, for the tasks these pages actually serve?

A structure earns a place only if it does well on both. Wording and headings
are the last step, not the first.

## 3. Candidate structures, as hypotheses

Each gets an operational definition, so it can be classified against and
falsified. None is preferred in advance.

- **H1, layers (DPE).** Declaration, persistence, execution.
- **H2, rule kind.** Admission (who may ask, what is valid), integrity (what the
  record guarantees), progress (what the reader of the record does about the gap).
- **H3, dependency.** What the check depends on: the request, the stored state,
  the world.
- **H4, artifact.** Data model (schema), operations (loops and state machines),
  interface (API surface).
- **H5, role.** Entity as record versus entity as actor, with scope between
  records. This is the controller problem: software and a database abstraction
  at once, scoping the models.
- **H6, reader question.** What is it, what can be asked of it, what is stored,
  what happens next, what can go wrong.
- **H7, lifecycle.** Create, use, change, remove.

Include one **negative control**: a plausible but arbitrary grid (for example
errors about names, quantities and states). If raters agree on it as well as on
DPE, agreement proves nothing.

## 4. Criteria (the joint tests)

A division counts as a joint only if it meets most of these:

1. **Referent.** An artifact in the codebase corresponds to it.
2. **Reliability.** Independent raters, humans included, sort the same facts
   the same way (kappa at least 0.6 on at least 50 items).
3. **Independence.** The chunks change at different times and for different
   reasons (co-change analysis, below).
4. **Observable boundary.** A reader or an operator can notice the difference.
5. **Task fit.** At least one real reader task is served better.
6. **Derivability.** A diagram or a generated artifact can be produced from the
   chunk and checked against source.

Thresholds are set now, before the results, so we cannot rationalise afterwards.

## 5. Experiments, cheapest first

- **E0. Bubble-up audit (code and pages, then blind raters for relevance).** Take every statement
  in a sample of reference pages (records, rules, loops, states, errors,
  relationships, all kinds). For each, list the code artifacts it describes
  and compute their lowest common ancestor. Sort into local (single package),
  domain-wide, cross-domain, cross-process, and temporal (phases, lifecycle).
  The clusters show what the reference pages must carry and what could live
  lower. Feeds H8 and criteria 1 and 3.

Each says what it costs and what decision it feeds.

- **E1. Co-change analysis (git history, no people).** For a sample of entities,
  map code changes in 4.1 to the areas H1 and H4 predict (schema, state,
  service, API facade, workers) and measure how often they change together.
  Feeds criterion 3. Expectation to test: schema and workers move apart, API
  and schema move together (which would collapse declaration into persistence).
  If every change touches all layers, a layer-first page scatters each change
  across several sections, which favours organising by entity or feature.
- **E2. Observable-boundary audit (code, no people).** For every documented
  error: is it returned synchronously in the API response, or does it surface
  later through status or logs? Feeds criterion 4 and H3.
- **E3. Repeat and widen the blind classification.** Same 40 items again, to
  measure noise; add H2, H4 and the negative control; add rules, records and
  loops, not only errors; then human raters (the user and two colleagues, 30
  items, same definitions). Feeds criteria 2 and 1.
- **E4. Reader-task corpus.** Collect about 50 real questions from Discourse,
  Matrix, GitHub issues and support, plus the user's DPE team's own list. For
  each, find the answer under the current structure and under H4 and H6, and
  count wrong turns. With the generated index in place, this isolates what the
  structure adds beyond lookup. Feeds criterion 5.
- **E5. Pilot on hard pages.** Build H1 and the leading alternative on the
  scratch worktree for three deliberately awkward entities: `controller`
  (actor and record), `zone` or `subnet` (no execution), and `secret` or
  `relation` (rich). Walk a few readers through them, think-aloud, including the
  senior developer who raised the duplicated-rule concern. Feeds criteria 5, 6.
- **E6. Diagram derivability.** For each candidate chunk, produce one ggarch
  view (an ERD slice, an operation state machine from the migration stage
  table) and check it against source. Feeds criterion 6 and protects the
  diagram requirement.

## 6. Decision rule

- Adopt a division only if it has a referent and meets criteria 2, 3 and 5.
- If no candidate does, fall back to the minimal structure that makes the
  fewest claims: what it is; the data model (records); the operations (loops
  and state machines); the rules and errors beside the thing they constrain,
  with the generated index. DPE then survives only as the typical walk-through
  in `architecture.md`, as "the typical shape once a controller exists".
- The outcome is recorded as an amendment to ADR-016, with the evidence and
  the thresholds that were pre-registered.

## 9. Risks

- LLM raters share biases with each other and with the author of the
  definitions. Human raters and the negative control are the correctives.
- Errors are only one kind of content. A result on errors does not transfer to
  records, rules or loops without testing them.
- Small samples. Use effect sizes, not significance.
- Lens seduction: a tidy answer arriving early. The pre-registered thresholds
  and the fallback exist to stop that.

## 11. Results so far (2026-10-19)

- **E1, co-change (319 non-merge commits between the PR base and upstream/4.1;
  300 touch non-test code in the areas below).** 65% touch a single area. State
  and service move together about half the time (one domain-logic chunk in
  practice); schema is rare (4% of commits) and rarely moves with workers (4%);
  workers and state move together 11%; the API and state 13%. So the data model
  (schema and state) and the operations (workers) vary independently, which
  supports separating them. Caveat: code areas are not documentation layers.
- **E2, where errors are created (the 40-error sample).** Of 13 errors filed
  under execution, 9 are created on the request path, 1 in a removal job, 2 in
  migration code. Almost every documented domain error is an immediate refusal;
  asynchronous failures show up as status messages and job retries, not as
  error constants. The observable boundary does not separate declaration from
  persistence for errors.
- **E3, repeat run on 40 prose rules (not errors).** DPE definitions again:
  80% agreement with our filing (kappa 0.70), against 55% (kappa 0.33) on
  errors. Admission / integrity / progress definitions: 78% (kappa 0.66), and
  82% with the DPE rater (kappa 0.73): the same distinction under other names.
  Control grid (names, quantities, transitions): normalised mutual information
  with our filing 0.24, against 0.51 for DPE. So the control is not null
  (naming rules sit with declaration, transitions with execution), and
  agreement of 0.7 is not free, but DPE explains about twice as much.
  Disagreements: 8 of 40, six of them rules filed under execution that are about
  removal or deletion and read as admission or integrity. Caveats: the rules
  were written under the layer headings, so their wording leaks the layer; one
  run per rater; LLM raters.
- **Reading.** For rules, declaration versus persistence is reliable (it is the
  admission versus integrity distinction). Execution is a different kind of
  bin: it collects rules about operations (removal, import, migration) whatever
  their rule kind. Two axes are mixed: rule kind, and topic (operations). That
  fits H4: data model and operations as separate chunks, with admission and
  integrity rules attached to the thing they constrain. It leans toward the
  fallback structure in section 6; nothing is decided.
- **Next.** E0 (bubble-up audit), human raters, E1 at domain granularity, E4.

### E0 pilot on `machine.md` (2026-10-19)

17 statements (errors, records, loops, a request grammar), each anchored in the
code by an error constant's raise sites, a table name or a function name, then
classified by what its code spans. Crude by design (grep anchors, one page).

- **Local to one domain (could live in `domain/machine` or its `errors.go` and
  schema comments):** `machine constraint violation`, `invalid machine
  constraints`, `machine already exists`, the grandparent error, `machine agent
  is still present`, the machine primary record, machine removal as a
  single-domain loop. These restate what one package already knows.
- **Cross-domain (needs the root doc):** the parent and cloud-instance
  records are referenced by 4 and 8 other domains (removal, status, storage
  provisioning, network, migration, recovery, agent password). Who depends on a
  record cannot be stated in the machine package.
- **Cross-process (needs the root doc):** reprovisioning and the placement
  grammar run from client through API to domain.
- **Shared vocabulary:** `machine not found` is created in 57 files across
  processes; it belongs to the shared vocabulary and the index, not to one page.
- **Reading.** What bubbles up is relationships between records across
  domains, operations across processes, and shared vocabulary. This is
  testable and mechanical, and it matches the fallback structure: the data
  model (cross-domain relationships), the operations (cross-process), and the
  local rules and errors generated or linked. Caveats: one page, grep anchors
  overstate spans where a name is generic, and statements were chosen by me.

E0 correction (2026-10-19): the pilot's "local to one domain" group is not
redundant with the package docs for readers who are operators. About five of
the 17 machine statements are local and operator-relevant (`machine constraint
violation`, `invalid machine constraints`, `machine already exists` on import,
`machine agent is still present`, machine removal); applying "could live
lower" literally would drop them. Two are local and developer-only (the
grandparent error, the primary record's shape). The cross-domain statements
(dependents of the parent and cloud-instance records) are mostly platform-
developer material, which says who the root layer serves. Open question for the
user: the priority order of the audiences (operators, client authors,
platform developers). Next: blind relevance ratings, then E0 on `controller`,
`subnet` and `secret`.

Contributor-tree assumption (2026-10-19): the dissolve assumed that what bubbles
all the way up is good advanced-user knowledge. Holds in part. No separate tree
is still right, because the dissolve distributed developer knowledge to
`doc.go` files and `CONTRIBUTING.md`, next to the code. But spanning is not
audience: on `machine`, cross-process operations are operator and client-author
material, while cross-domain record dependencies are mostly platform-developer
material (3 of 17 statements). Spanning developer-only facts have no natural
lower home; the candidate answer is a marked level inside the entity page, not
a second tree. E4 (real reader questions from advanced users) is the test.

Proposed definition of docs/ (2026-10-19, not ratified). The user's draft, "any
contributor content that bubbles up plus anything a user might need", is too
loose: the second half has no edge, the first depends on today's code cut, and
the union mixes inclusion (audience) with ownership (span). Tighter draft:
docs/ renders (1) every fact observable at a named user-facing interface
(operator CLI, config, status and logs; client developer API and errors; charm
developer hook tools, metadata and Ops), pulled up by generation or embedding
from wherever it is authored, and (2) spanning facts that no single package can
state, for platform developers. Local developer-only facts stay in `doc.go`,
schema comments and `CONTRIBUTING.md`. Inclusion tests: can a reader meet the
fact at a named interface; does it span. Generous for generated facts, strict
for root-authored ones. Each fact carries the audiences it serves; audience
priority then only sets prominence. Behavioural facts still need blind
relevance ratings.

Refinement (2026-10-19): the structure is two joints, not three parts. The
data model (what exists; referent: schema) and the operations (what happens;
referent: loops, state machines, request paths), with rules attached to the
thing they constrain, not collected in a third part. Integrity rules are the
data model's invariants; admission rules are operation preconditions; progress
rules are how the operation unfolds. Errors are violated rules and sit with
them, with the generated index as the lookup. This explains why admission /
integrity / progress agreed with declaration / persistence / execution at 82%:
the layers were an approximation of it. Old DPE: persistence is the data model
(sharpest), execution is the operations (also collecting rules about
operations), declaration is where a request meets a rule (not a part). Limit:
many operations are continuing reconciliation loops, not single transitions with
pre- and postconditions, so the operations part must cover loops and status
state machines. To test in E5.

Pilot conventions after the user's review (2026-10-19):
- **Headings.** Reference headings are nominal and carry the entity name
  (ADR-011 naming law and red thread; the 2026-09 amendment allows concrete
  phrasing at the umbrella level only). Howto headings are imperative and keep
  the entity ("View a database's schema"; docs/agents rules). The pilots first
  used gerunds without the entity ("Rebooting", "Expanding to high
  availability"); renamed to "Machine reboot", "Machine removal", "Controller
  bootstrap", "Controller high availability" and so on.
- **Signposting.** Every errors table is preceded by a one-sentence lead-in that
  says what the table is ("A request for a machine is refused with one of these
  errors:"). The data-model errors have their own heading ("Machine record
  errors").
- **No audience labels on sections.** A "For platform developers" section
  repeated the audience-tag grouping the project had already dropped. The
  rating result (cross-domain statements were developer-only in 6 of 7 cases)
  informs placement and depth, not a label: dependents are now stated on the
  record bullet they concern ("Removal, status, ... also read it").
- **Watchers sit at the end of the data model.** Their contract is a property of
  the records (the changes a record's stream reports); what each stream drives is
  an operation, named in the bullet and linked. The co-change check was
  inconclusive (3 commits in the window).

Open item, watcher placement (2026-10-19). Currently at the end of the data model
in the pilots. For: a watcher's contract (what changes are observable) is a
property of the records; operations consume watchers and do not define them;
entities with no operations (subnet, zone) still need a home for watchers. Against:
a watcher is a runtime subscription (noun versus verb mismatch with the data
model); each bullet is explained by the operation it drives, so readers jump
back and forth; ADR-011 placed them under background execution. Co-change check
inconclusive (3 commits). To test with E4 (where do readers look) and a blind
classification of the watcher bullets.

Watcher placement resolved (2026-10-19), by the referent test, which is the plan's
tie-break for seam cases: place a part where its artifact lives. Watchers are
methods on each domain's `WatchableService` (for example `WatchMachineLife`,
`WatchModelMachines`, `WatchSubnets`) and are exposed through agent facades
(machiner, instancemutater, firewaller); none is defined in the schema. So they
are part of the service and API surface, the same artifact family as the
operations, and belong in the operations part as its observing operations
(commands change the records; watchers observe them). This reverses the earlier
placement in the data model, which rested on a contract-derived-from-records
argument that holds equally for every operation. An entity with only observing
operations (subnet) has an operations part made of watchers, which is consistent.
General rule for the form: classify a part by its referent (the artifact it is),
not by what it depends on.

Watchers refined (2026-10-19, user's point that they cut across operations):
a cross-cutting thing is defined once and mentioned where it applies. The shared

(controller-software)=
## Controller software

The controller's program is the controller agent: the machine agent in its controller role, a {ref}`jujuagentd <jujuagentd>` process. On machine clouds each controller machine runs one, and on Kubernetes the controller container does. A controller flag switches on the workers that only the controller needs, among them:

- **API server:** Runs the Juju API server and the HTTP server in front of it.
- **Database accessor and change stream:** The embedded Dqlite database, and the stream of changes in it that tells {ref}`watchers <watchers>` what changed.
- **Bootstrap worker:** Sets up the initial machine.
- **Model worker manager:** Starts an engine of workers for every model the controller serves.
- **SSH server:** Serves the controller's {ref}`SSH connections <juju-ssh>`.
- **Control socket:** A local socket through which the controller charm changes controller settings, such as the SSH server port.
- **Singular worker:** Each controller machine runs one, and it claims responsibility for the workers that must not run in several agents at once.
- **Log router and log sink:** Controller-only workers that handle logs.

Adding a {ref}`high-availability <high-availability>` node brings another controller agent into the controller's Dqlite cluster.

## Actors in the template (2026-10-19, session 78)

Question (the user's, from the open decision 1): the controller, machine, model and unit each have a software side. ### What the code says about the actors (4.1, `cmd/jujuagentd/agent`, `internal/worker`)

- **Machine.** One machine agent per machine: a `jujuagentd` process (`machine.IAASManifolds`), logging in to the API as the machine. Its workers act on the machine's records and on the machine itself: the machiner reports `started`, keeps the observed network configuration up to date, and on `dying` reports `stopped` and asks the controller to mark the machine `dead`, retrying whenever units, containers or storage change (`internal/worker/machiner`); the deployer starts a unit agent for each unit of the machine inside the same process (`internal/worker/deployer`, nested engine); the LXD broker and container provisioner provision containers; the reboot executor, storage provisioner, disk manager, machine actions, upgrader, SSH key updater, host key reporter and proxy updater. The old pilot text had the actor wrong or missing in three places: the removal bullet said the agent "shuts the machine down" (the code marks it dead, and the controller's removal job deletes the records), the "local shutdown watcher" is the machiner's watcher (`WatchMachineLifeAndDependants`, which also fires for units and storage), and the data model credited statuses to "the machine agent" without saying what that is. So the machine is not entity-only: its removal, its status and its unit hand-off all need the actor.
- **Controller.** On machine clouds the controller agent is the machine agent of a controller machine, with the controller-only workers switched on by a controller flag (`ifController`, `ifPrimaryController`); on Kubernetes the controller container's agent has its own identity (`names.ControllerAgentTag`, flag `--controller-id`; the TODO in `machine.go` says a separate command is planned). Controller workers: API server, Dqlite database accessor and change stream, model worker manager, bootstrap, database upgrade runner, undertaker, lease expiry, SSH server and tunneler, control socket, controller log router and sink, and a singular worker that elects a primary controller for the workers that must run once (change-stream pruner, secret backend rotation, API address setter, object store drainer, external controller updater).
- **Model.** On machine clouds a model has no process. The model worker manager (a controller agent worker) starts a dependency engine per activated model (`WatchActivatedModels`), built from `model.IAASManifolds` or `model.CAASManifolds`. One controller agent at a time runs a model's workers: the holder of the model's singular lease (`is-responsible-flag`); the workers pause during migration (`ifNotMigrating`), stop when the model is dead (`ifNotDead`), and the ones that use the cloud wait for a valid credential. Workers: compute provisioner, instance poller, firewaller (machine models); application provisioner, firewaller, model config manager (Kubernetes); removal, migration master, storage provisioner, charm revisioner, async charm downloader, remote relation consumer, secrets pruner and user-secrets drain, operation pruner, change-stream pruner, unitless. The Undertaker is a controller agent worker, not a model worker. On Kubernetes there is also a process: the model operator pod, one per model (`cmd/jujuagentd/agent/modeloperator`), started by the `caas-model-operator` worker. So `agent.md`'s "model agent" (workers for all models of a controller) was wrong twice: the workers are per model, and they are not a process of their own.
- **Unit.** On machines the unit agent is a nested engine run by the machine agent's deployer (`internal/worker/deployer/unit_agent.go`, `unit_manifolds.go`); on Kubernetes it is the `containeragent` process in the pod (`cmd/containeragent/unit`). Workers: the uniter (installs the charm, runs hooks, relations), leadership tracker, hook retry strategy, migration minion, log router, upgrader (records the version only), secret drain.

### Result: the flat template, with three adjustments

Page = lede, then optionally the actor part, then data model, change streams, operations. Test result: the proposal holds for all four entities; the adjustments are:

1. **Name the actor part by the actor, not "software".** "Machine agent", "Controller agent", "Unit agent", "Model workers". Reasons: the heading rule asks for a nominal heading that carries the entity name and a reader or an agent searches for the noun; "Machine software" says nothing a reader can match, and the model has no process, so a uniform word would be wrong for it. The slot keeps one name in the template ("actor part").
2. **Include the part when the entity has its own process or engine, and only then.** Tested on the other entities: application (per-application worker on Kubernetes), secret (pruner, rotation), storage (storage provisioner), relation, offer (remote relation workers), credential (credential validator) have workers that act for them, but those are model workers or controller workers, listed once in Model workers or Controller agent and named by the operation that uses them. They get no part. The test is crisp: an own process (controller agent, machine agent, unit agent) or an own engine per entity instance (the model's). Everything else is a worker named in an operation.
3. **Put the part first, ahead of the data model.** Reason: every later part names the actor. A count of mentions of agents or workers in the pilots (data model / change streams / operations): machine 8 / 6 / 12, controller 14 / 2 / 4, model 1 / 6 / 10. With the part first these are all backward references to a defined term (the cross-reference rule: define once, mention where it applies). With the part after the data model, the machine and controller data models would use the term before defining it. The chronology rule does not help: the record exists before the agent for machine, unit and model, and the agent before the database for the controller, so no single chronology fits all four. The parent-text rule decides: a thing that applies to all the children (the operations) is stated before them.

What the part holds: what the actor is (process or engine), where and how many, its identity, what gates it (flag, lease, migration, credential), the worker catalogue as labelled items with the worker names in code font (the names are the `manifolds.go` constants, so a reader can match them to logs and the introspection reports), and the relation to the other actors (the machine agent runs the unit agents; the controller agent starts the model workers). What it does not hold: the operations. Each operation names the actor that performs it and its trigger; the catalogue entry says in one line what the worker does and points to the operation where there is one.

One home: the entity page owns its actor. `agent.md` stays the overview of what an agent is and lists the types with pointers (labels `controller-agent`, `machine-agent` and `model-workers` moved to the entity pages; `unit-agent` stays in `agent.md` until the unit page is converted). Also corrected there: the unit agent entry (nested engine or `containeragent`), and the "model agent" entry is gone.

### Skeleton derived from first principles (2026-10-19, session 78, user: the earlier freeze was abandoned because the structure was not derived)

Premise: a reference page is a lookup structure for an entity. Any description of a thing that changes splits into state (what is true at an instant: stored and derived attributes, state variables such as life and status, invariants), dynamics (transitions: trigger, precondition, steps by an actor, effect on state), observation (how changes of state become visible: push as change streams, pull as reads), and agents (who performs transitions). This is the classical state schema plus operation schemas with preconditions and postconditions (Z notation), with observation and agency made explicit. Rules are invariants (state) or preconditions (dynamics); errors are their violations, so errors are not a dimension and nest with the rule. The E3 result (admission / integrity / progress agree with the layers at 82%) is the same distinction seen from the other side.

Order is definitional dependency: dynamics are defined over states, observation over state changes, agents over what they observe and change. So: identity and context (lede), state, observation, agents, dynamics. Each part uses only terms defined earlier. To keep that true the agent roster lists identity, gating and, per worker, the stream it subscribes to or the timer it runs on, and no behaviour; behaviour lives only in dynamics, where a trigger is a client request, a change in state (a stream) or time. Standing loops (block-device reporting, key updating, lease expiry, database upgrade) become dynamics entries with a stream or timer trigger. Reads and the "access checks" fall into place: reads are pull-observation, and the checks are the evaluation of a derived attribute (the effective level) that other operations' preconditions use.

When does something get a part of its own, and when its own page? By lifecycle coupling. Software whose lifecycle is coupled 1:1 to the entity (controller agent, machine agent, unit agent, the model's workers) is the entity's realisation and shares its page: the agent exists exactly while the entity's state permits, and removing the entity ends the agent (the workers that carry out a model's removal run until the model is dead). Things with independent lifecycles (application and unit, model and machine) have separate pages.

Test (not yet run): blind classification of the sentences of the three pilots and of `access.md` into identity, state, observation, agent, dynamics; high agreement means the dimensions are orthogonal and the skeleton is not taste. Disagreements show which sentences straddle two parts.

### E8: trying to break the five dimensions (2026-10-19, session 78, user: "orthogonal enough" is not enough; find a foolproof skeleton)

"Foolproof" cannot be proven; the aim is a skeleton that survives attempts to falsify it. Criteria fixed before running (pre-registered):
1. **No leak.** On text not written under this skeleton (corpus A: the 18 layered reference pages of #23451, written under declaration/persistence/execution; corpus B: the `domain/*/doc.go` package docs, written by developers), two blind raters agree with each other at kappa >= 0.80.
2. **Coverage.** At most 5% of statements get "none of these" as primary, and the "none" statements do not form a recurring kind of their own (if they do, that kind is a missing dimension, or an out-of-scope kind that the skeleton must name).
3. **Not free.** A control partition that ignores the dimensions (names and identifiers / quantities and limits / sequences and transitions / other) has normalised mutual information with the dimensions clearly below the rater-to-rater agreement.
4. **Straddlers.** Statements that two raters label with different secondaries form a small set that a written placement rule resolves (the rule is itself tested by re-classifying the split halves).
5. **Order.** Each rater records which other dimensions a statement presupposes (the reader must know them first). The matrix of presuppositions, over all statements, picks the ordering of the parts with the fewest forward references; the ordering is stable across the entities.
6. **Red team.** An independent agent tries to find counter-examples and a sixth dimension from the "none" and straddler statements.
Failing 1 or 2 means the dimensions are wrong. Failing 4 or 5 means the dimensions are right but the placement rules or the order need work.

### E12: a topic that is not an entity: "controller storage" (2026-10-19, session 78; user's test case)

Studied from the code (4.1). Object-store workers: `objectstore`, `objectstoredrainer` (primary controller only), `objectstoreguard` (non-primary), `objectstores3caller`, `objectstorefacade`, `objectstoreservices`. Interface for the operator: the local control socket, `POST /s3-config` with bucket, region, endpoint, access and secret key (the controller charm calls it; the charm is outside this repo, so the user-facing configuration key is unverified); `DELETE /s3-config` answers 501 "removing S3 config is not supported at this time"; the domain error `backend transition not supported` (only file to S3). Drain loop: up to 10 retries per namespace, 30 s apart, one-hour overall timeout. 16 error constants (hash and path validation, draining, backend). Watchers: `WatchDraining` and `WatchObjectStoreBackend` are consumed by workers only (internal).

Fit against the skeleton. The **object store** fits as an entity page (lifecycle type: life column on its backend record): identity, interface (control socket request, hash and path addressing), state (tables, backend type, drain phases, unique hashes), observation (nothing user-facing: internal watchers only; whether an operator can see drain progress is not established), agent (the six workers, with the primary/non-primary split), dynamics (put, get, remove by path or hash; transition to S3; drain), failure (16 errors). The **database** keeps its substrate shape. **"Controller storage" as a page does not fit**: it is a topic that spans an entity (object store), a substrate (database) and consumers (charm, resource, agent binary, action output). Findings for the theory: (1) the page unit is chosen by lifecycle coupling, and the topic is served by a derived placement map ("where Juju keeps its data": which store holds which entity's records and blobs), computable from foreign keys and the object-store users; (2) the interface part must allow non-API interfaces (the local control socket, whose client is the controller charm); (3) one entity can span scopes (backend controller-wide, metadata and drain per database namespace); (4) "storage" collides with charm storage, so identity must disambiguate and the page should be named for the entity (object store); (5) explicitly unsupported transitions are state-machine facts to derive from the code; (6) the observation part can legitimately be empty for docs/ even when internal watchers exist.

### E15: version stability of the typing, 4.0.15 against 4.1 (2026-10-19, session 79)

Test 2 of the predictor programme. **Typing and inventories (functions of the DDL alone).** Per table: life (a `life_id` column), status (a `*_status` table or `status_id` column), watched (a `trg_log_<table>_insert` trigger), immutable (an immutable or unmodifiable trigger), lookup (a seeded table of at most three columns). **Pre-registered pass criterion (all must hold):**
- (a) Stability: no table outside C has a different typing tuple.

Tables named only in trigger-generating Go code are counted by reading the generator.
- (e) Domain stability: every domain none of whose owned tables is in C (owner map of 4.1) has the same domain typing under the 4.0.15 owner map; each other difference is explained by a table in C.
Reading of a failure: (a) or (b) failing means the typing is not a function of the schema, or the script is wrong; (c) or (d) failing means the derived inventory is blind to real change; (e) failing means the domain typing depends on code the schema does not show.
Caveats fixed in advance: (a) is nearly true by construction, since the typing is computed from the DDL, so it checks the script; (b) to (e) carry the evidential weight. One pair of versions only; ownership is heuristic.

### E17: does the typing carry information? Schema features against Go-level parts (2026-10-19, session 79)

Question: if the part inventory of an entity follows its artifact classes (H1), then cheap features read from the schema alone should predict the presence of parts that live in Go. Unit: a domain package together with the schema topic files assigned to it (the sql file names in `domain/schema/{model,controller}/sql` are the ownership source; the assignment of topics to domains is in `experiments/e17/topics.json`, fixed before the run; topics without a domain are left out). Schema features (from the 4.1 DDL, replayed in SQLite, and the sql files): owns at least one non-lookup table; has a life column; has a watched table (change-log trigger); has an immutable-trigger table. Go-level parts: `Watch*` methods in the domain service; a removal job type (`removal_type` value mapped to the domain in `topics.json`); a `modelmigration` package; error constants.

**Rules fixed in advance (from the theory) and thresholds:**
- R1: the domain has `Watch*` methods iff it owns a watched table. Accuracy at least 85% over domains that own a table. (E11 already found one violation, access: a trigger and no watch method.)
- R2: a life column implies a removal job. Holds for at least 90% of the domains with a life column. The converse (removal job implies life column) is expected to fail for secrets and resources and is reported, not gated.
- R3: a `modelmigration` package exists iff the domain owns a non-lookup table. Accuracy at least 85%.
Reported with each rule: the majority-class baseline and the list of violating domains. Fewer than 20 domains with tables means no verdict. Caveats: few domains; the topic-to-domain assignment is hand-written input; `Watch*` presence is not the same as client exposure (tiers are not used here).

#### E17 results (2026-10-19, session 79)
Scripts and data: `experiments/e17/` (`e17.py`, `topics.json`, `e17_result.json`). 36 domains own tables (21 with model-database tables, 15 controller-database only).
- **R1 (watch methods iff a watched table): pass.** 32 of 36 = 89% against a majority baseline of 58%. Violations: storage (its watch methods live in `storageprovisioning`, outside the assigned unit), access and keymanager and externalcontroller (a trigger but no watch method at the service, the E11 finding generalised to three more domains).
- **R2 (life column implies a removal job): fail as registered.** 6 of 8 = 75% (threshold 90%). Violations: `objectstore` and `controllernode`, both lifecycle entities whose life column is in the controller schema. The converse fails as expected for secret and resource (removal job without life column).
- **R3 (modelmigration package iff owns a table): fail as registered.** 22 of 36 = 61%, equal to the baseline.
- **Post hoc, by schema scope (not registered):** a life column in the model schema implies a removal job in 6 of 6 domains; the two lifecycle entities that live only in the controller schema (controller node, object store) have no removal job type of their own, because `removal_type` is a model-database lookup (checked: the controller node record is deleted as a step of removing the controller application's unit, `domain/removal/service/unit.go:338`, through `DeleteDqliteNode`; the object store has `RemoveMetadata` for blobs and uses its life column for the drain). Model-scope domains have a `modelmigration` package in 17 of 21 (the four without are mechanism or infrastructure domains: agent binary, ssh, object store, removal); five controller-only domains have one too (access, keymanager, external controller, lease, cloud image metadata), because their data travels with the model.
**Reading.** The presence of observation follows the schema well (89% against 58%). Removal and migration do not follow from "owns a table" or "has a life column" alone; they follow the **scope** of the data: model-database entities are removed through the shared removal mechanism and migrate with the model, controller-database entities are not removed that way, and some controller-database records migrate anyway. Scope (which database holds the entity: controller-wide, model-scoped, or both) is therefore a typing axis the skeleton lacks, as predictive as the life column, and readable from the schema topic files. It is also the missing piece of E12 (placement) and fits the E15 finding that domain typing depends on where code and data live. Proposed for the typing: identity states the scope; lifecycle (life column) and scope together choose the removal part; scope chooses the migration part. To be tested: that scope plus life predicts the part inventory of the 36 domains better than life alone (a decision-table check).

#### E17b: does scope add to life? Leave-one-out decision table (pre-registered before the run, 2026-10-19, session 79)
Types are tuples of schema features over the 36 domains of E17. Typing A (life only): (has a life column anywhere). Typing B (scope and life): (scope in {model, controller, both}, life column in {none, model schema, controller schema}). Typing C (B plus observation): B plus (owns a watched table). Targets: has `Watch*` methods, has a removal job, has a `modelmigration` package. ### Order of the parts: closed as a convention with hard constraints (2026-10-19, session 79)
Evidence collected (E8, E10, E19b, E21): the only robust precedence constraints are identity first, state before dynamics, state before failure, dynamics before failure; interface presupposes and is presupposed by almost nothing; observation and agent have too few items for an order (E8: 8 agent statements; E10: 44 pairs). #### E29d: operation/action/task and status (descriptive, 2026-10-20, session 79)
**Operation, action, task.** The `operation_*` group has 10 tables: `operation`, `operation_action`, `operation_parameter`, `operation_task`, `operation_task_log`, `operation_task_output`, `operation_task_status` with its value lookup, `operation_machine_task`, `operation_unit_task`. **Three page-unit patterns so far** (E29 to E29d): (A) a noun group with its life entity (machine, unit, application, relation, storage); (B) a user-facing noun that joins table groups (action: declaration plus runs); (C) a facet page that spans entities (status, annotation, constraint, configuration). ### E30: exposure by call graph (pre-registered before the run, 2026-10-20, session 79; TODOS 3)

#### E30 tuning after seeing results (recorded 2026-10-20; the criteria K1 to K4 above were fixed before the run, these choices were not)
The first run (class-hierarchy graph, no filters) reached every table from nearly every root, so the program was changed several times. In order, each change made after looking at output:
1. Skipped wiring and constructors in the traversal (`domain/services`, `internal/worker`, `internal/provider`, `environs`, `cmd`, functions named `New*`, `Register*`, `init`).
2. Switched from the class-hierarchy graph (CHA) to rapid type analysis (RTA), with the 336 constructors and `domain/services` functions added as extra analysis roots so that service types count as instantiated.
3. Excluded `internal/database` from the traversal (the transaction runner dispatches closures to every state package) and treated closures defined inside a visited function as part of it.
4. Dropped edges that are calls through function values (they resolve to every closure of the same signature), after seeing a secrets facade reach a controller-upgrade closure.
5. Attributed tables only through state functions that name fewer than 20 tables; functions naming 20 or more (generic export and import, two removal helpers) are recorded as bulk operations.
6. Added view names to the matcher and mapped each view to its tables (controller config is read through `v_controller_config`).
7. Added facade roots from the full method sets of the facade types (promoted methods from embedded types such as the common controller-config API), and allowed synthetic wrapper functions in the traversal (promoted methods such as the operation service's `GetOperations`).
8. Left the CLI roots out of the table results, because the call from a command to the server is an RPC with method names as strings, which a Go call graph cannot see.
Stopping rule adopted (from the user's second opinion): no further tightening of this measure without asking; an RPC bridge from CLI to facade is a separate, later task.

### E34: the grouping manifest as a hypothesis, with falsification tests (pre-registered before the manifest is built, 2026-10-20, session 79)
Hypothesis H: there is a table-to-page assignment (the manifest) in which every non-lookup table of both 4.1 schemas has exactly one home page, shared lookups belong to no page, attachments of other nouns are listed as pointers, and a reader who has not seen the assignment would place at least 90% of the tables on the same pages. Theory-maker rule: the manifest was written from the three signals (first word, writing domain, schema file) and the E33 audit, so those are training data; the tests below use data or judges that did not take part in writing it.
**Falsification tests (each can break H):**
- M1 (blind placement): an independent judge who has not seen the manifest receives the list of pages (a name and one sentence each) and all non-lookup tables, and places each table on one page or on "none fits". The tables new in 4.1 (E15: 19 tables, none of them in the E33 audit or training) are marked in the list and scored separately.

- M3 (structural cohesion): the share of foreign keys between non-lookup tables that stay inside one page is at least as high as for each of the three rule partitions (first word, writing domain, schema file). - M4 (new-table rule): a fallback rule (a table not in the manifest goes to the page of its schema topic file, or to the page of its first word when the file is shared) is applied to the 19 tables new in 4.1; agreement with the blind judge of M1 is at least 80%. - M5 (existing pages): each of the 23 existing reference page names (the upstream pages plus the pilots) maps to exactly one manifest page, or is declared a page that spans several (pattern B of E29d, with the reason); at least 90% map cleanly, and `status`, `space`, `zone`, `access` and `agent`, which the first-word rule could not match, are reported separately.
- M6 (small pages): every page with fewer than 3 non-lookup tables carries a stated reason (facet, mechanism, substrate, or a small noun a user addresses).
Caveats fixed in advance: judges are fallible and shallow reads are likely (the earlier audits used 12 to 24 tool calls), so every flag is verified by me and unflagged errors are possible; the page names and descriptions given to the blind judge are mine and may leak the answer; the existing pages are human-chosen and are not ground truth.

### E35: character or leg? (pre-registered before the run, 2026-10-20, session 79; user concern: is a page for a character or for a character's leg)
Source of the concern: `docs/agents/AGENTS.documentation.rules.md` defines reference pages as entity references ("concrete entities users work with"), concept, tool and process references, attribute-based, with the entity as subject; child entities share a parent's how-to only when "tightly coupled". The phrase "dictionary of primitives, cast of characters" is not in the file; the user's metaphor stands as the working assumption. The manifest (E34) carries hand-assigned kinds (noun, facet, mechanism, substrate), which E31 showed cannot be derived from facts, so this test uses four observable properties and no label.
**Properties of a page's group of tables G with noun N:**
- (a) addressed: a token of N (folded to singular) is a command noun (`cmd/juju`, `cmd/plugins`), a client facade name, or a hook tool name token; counted separately: by command or facade, by hook tool only.
- (b) own identity: the lead table of G (the table of G with the most foreign keys pointing into it from G itself, ties by shortest name) has a primary key that is not a single foreign-key column to a table of another page (a 1:1 extension such as `application_agent`, whose key is the application's key, fails).
- (c) referenced elsewhere: at least one table on another page has a foreign key into a table of G.
- (d) own lifecycle clause: a life column in G, or a command or client facade method with a removal verb (remove, delete, destroy, kill, revoke, unset, cancel) whose noun is N.
**Definition fixed now:** a page is a **character** when (a), (b) and (c) hold; (d) is reported. A page that fails any of (a), (b), (c) is a **candidate leg**.
**Predictions fixed now:** (1) at least 25 of the 39 pages are characters; (2) these are candidate legs, at least 4 of 5 fail the definition: `port`, `zone`, `agent-version`, `model-defaults`, `telemetry`; (3) all of the nine pages whose group has a life column (application, machine, unit, relation, storage, model, controller, object-store; offer's proxies carry the life columns of its group) pass.
**Negative controls (sub-nouns that are legs of a larger page, declared before the run; the test must fail them or it does not discriminate):** cloud-instance (`machine_cloud_instance`, its status, `instance_tag`), unit-state (`unit_state`, `unit_state_charm`, `unit_state_relation`), relation-unit (`relation_unit`, its departure record, settings and hashes), application-endpoint (`application_endpoint`, `application_extra_endpoint`), application-scale (`application_scale`), machine-placement (`machine_placement`, `machine_placement_scope`). At least 5 of the 6 must fail the definition.
**Independent falsifier:** a judge who has not seen the test results receives the 39 page names and descriptions and the 6 negative controls, and for each answers, from the code, "would a user look this up by itself (character), or find it as part of another page (leg), or is it a process rather than a thing (mechanism)?", with evidence of how users address it and what refers to it. Agreement of the judge's character-or-leg answer with the definition, over the pages the judge does not call a mechanism, must be at least 80%; every disagreement is adjudicated by me against the code.
Caveats fixed in advance: (a) uses names and so inherits the E20b weakness (a vocabulary of about 90 nouns matches many words); (d) by command verbs misses removal done by workers; the judge may read shallowly (earlier judges used 4 to 24 tool calls), so the instruction demands a large budget.

### E38: page or section by dependency (pre-registered before the run, 2026-10-20, session 79)
Why this is next: E37 gives primitives but every primitive satisfies the same properties, so the code did not say where a page ends. Candidate principle, from the structure of the software alone: **containment by dependency.** Let the referrers of a primitive G be the other chunks that depend on it. A primitive with **exactly one** referrer P is only meaningful as part of P: it is a **section of P**. A primitive with **two or more** referrers has no single owner, and placing it inside one of them is a false grouping: it is a **page**. A primitive with **no** referrer is not contained in anything: a **page**.
**Chunks** (the finest chunking so far): the 38 table-backed pages of the manifest, with seven groups carved out of their pages so that they can be judged on their own: `storage-pool` (from storage), `relation-unit` (from relation), `application-endpoint` and `application-scale` (from application), `cloud-instance` and `machine-placement` (from machine), `unit-state` (from unit). Referrer notions, both reported: **structural**: a table of another chunk has a foreign key into a table of G (lookups ignored); **behavioural**: an operation of a client, agent or controller facade whose package maps to another chunk reaches a table of G (the E30 and E37 call-graph measure; facade-to-chunk map as in E36 with `storage`, `application`, `machinemanager`, `spaces`, `subnets`, `usermanager`, `secrets`, `keymanager`, `applicationoffers`, `action`, `cloud`, `controller`, `modelmanager` and `modelconfig`, `credentialmanager`, `charms`, `resources`, `block`, `annotations`, `imagemetadatamanager`, `secretbackends`). The call graph over-approximates, so a behavioural referrer is weak evidence of dependence and an absent one is strong; the principle is applied to **both**, and a section is a **robust section** only if it has at most one referrer under both notions.
**Controls and predictions fixed now:** (1) the seven carved-out sub-groups other than `storage-pool` and `relation-unit` and `application-endpoint` are expected to come out as robust sections of their parent: `application-scale` of application, `cloud-instance` and `machine-placement` of machine, `unit-state` of unit; at least 3 of 4; (2) the hubs come out as pages: model, charm, machine, application, unit, cloud, controller, user (at least 7 of 8; each has at least two structural referrers); (3) `port` (an attribute of a unit) comes out as a robust section of unit, `telemetry` of controller; (4) the principle makes a **new prediction about the three groups that E37 showed to have lifecycles of their own**: `storage-pool`, `relation-unit`, `application-endpoint` have two or more referrers and so are pages, which contradicts the upstream chunking (sections) and is the claim to examine.
**Falsification of the principle (beyond its own definition):** (a) an independent judge, shown only the list of primitives and asked "which other primitives' operations or data depend on this one, from the code", gives referrer sets; the principle's classification from the judge's sets must agree with the classification from the mechanical sets for at least 80% of the primitives with at most one referrer in either (the judge tests recall of referrers); (b) stability: the structural referrer sets computed on the 4.0.15 DDL equal the 4.1 sets for at least 90% of the chunks whose tables did not change; (c) consistency with the manifest audit (E34 M2): of the 18 association tables with two plausible homes, the principle gives a verdict (page or section of one of the two); report how many it settles without a tie.
**Output:** the list of chunks with level (page or section of X), the evidence, and the diff against the manifest, the E35 judge and the existing pages as candidate corrections, never as errors of the principle by themselves.
Caveats fixed in advance: the facade-to-chunk map is hand-written; behavioural referrers inherit the over-approximation; a section of one referrer may still deserve a page for reasons outside the code (reader needs); the principle has nothing to say about tool, process and concept pages, which have no tables.

### E38c: identifying-key principle (pre-registered before computed; stricter form of E38b, 2026-10-20, session 79)
**Principle.** A table is **weak** when a foreign key column is part of its primary key (its identity is borrowed from the owner). A weak table is a **section of its owner's page**. A table with no foreign key in its key is **strong**: a page-level primitive, with mandatory non-identifying references kept as pointers (attachments). A family of tables each borrowing a different owner's key (the eight `annotation_*` tables) is a **facet**: a section in each owner's page and one concept page across them.
**Audit use, table level (all non-lookup tables of both schemas):** for each weak table compare its owner's page with the page where the manifest (v2) homes it. A weak table homed on a page other than its owner's is a **candidate misplacement**; a weak table homed with its owner is consistent.
**Predictions fixed now:** (1) at least 90% of the weak tables are homed with their owner; (2) the cross-page weak tables include the 8 `annotation_*` tables and the `cloud_defaults` pair (owner cloud, homed on `model-defaults`); (3) the principle flags at most 3 of the 7 tables that the independent adversarial audit of E34 found misplaced (it is a different criterion, so low overlap is expected; a high overlap would be evidence); (4) `permission`, `resource` and `port` are strong (pages) under this principle, which the E37 derivation and the how-to evidence support.
**Independent check:** an independent judge is given a sample of 20 weak tables (cross-page ones first) and asked "can this exist without its owner, and would a reader look for it on the owner's page?"; the principle's verdict (section of the owner) must agree for at least 80%; a judge disagreement is adjudicated against the code.
Caveats: the key columns are the schema's, which may encode convenience; a surrogate key hides identity; the principle has no evidence on strong tables that are only mandatorily referenced.

### E45: which diagrams the docs need, derived from the software (pre-registered before it is computed, 2026-10-20, session 81; epic JUJU-9635 due 2026-10-21; user directives: use first principles, nothing random, do not discard the reference work, ERDs on data-model parts and sequences on operations parts so every client benefits)

**Principle.** A diagram earns its place where prose serialises a structure badly. Two kinds of fact do that: (S) a set of at least four entities joined by relations with multiplicities, and (O) an ordered exchange among at least three actors. A third kind is (L) a life or status enumeration with at least three states and explicit allowed changes, and a fourth (T) a deployed shape with multiplicities that differs per deployment (high availability, cross-model). The form follows the kind: S is an ERD, O a sequence, L a state diagram, T a topology. A thing with none of the four gets no diagram, whatever the page length.
**Derivation, all from code.** (S) foreign keys of the 4.1 model and controller DDL (`experiments/e11/*.ddl`, replayed) joined to the manifest page of each table (`experiments/e33/page-manifest.json`): per page, the largest connected component of tables joined by foreign keys inside the page. (O) the interface operations (CLI command, API facade method, hook tool) and the actors the call graph reaches (`experiments/e30`, `e37`): client, API server, domain service, worker or agent, provider or outside system, hook execution. (L) tables with a life or status lookup and the explicit transition tables (ledger C16, C39). (T) the topology facts in ledger rows C13 and the HA and cross-model code.
**Thresholds fixed now.** An ERD candidate has a component of at least 4 and at most 12 tables (above 12 it is two figures or a section split, E41 levels; below 4 prose does it). A sequence candidate crosses at least 3 distinct actors with at least 4 ordered steps and is reachable from an interface a client uses. A candidate that fails its threshold is listed as 'no diagram' with the number.
**Ranking.** (1) Exposure: the number of interface kinds that reach the subject (CLI, API, HTTP route, hook tool, charm metadata), from the E21d and E41 exposure data (amendment A2): more reach, more readers. (2) Reach across pages: the number of other pages whose operations or tables point at the subject (page-manifest 'points to' column). (3) Already drawn: subjects that exist in `docs/juju.ggarch` views or in legacy figures rank by the gap, not by novelty. Ties by the order of the user's causal chain (records, streams, agent, operations, configuration). No other criterion.
**Legacy figures.** Each non-ggarch figure in `docs/` is dispositioned by the same rule applied to its own subject: convert to a ggarch view if the subject passes a threshold, discard if it fails or if the figure states something the code contradicts (checked against the code before conversion). Screenshots of the dashboard or web CLI are not diagrams and stay.
**Verification.** Every node and edge of an ERD comes from `ggarch scaffold` on the DDL, and every sequence step cites a file and line from the code; `ggarch check` passes; both docs builders pass; the caption and alt text restate the figure's facts (the AI reader meets the alt text, E44).
**Caveats fixed in advance.** The thresholds (4 entities, 3 actors) are chosen from the shape of the existing views (the pilots use 11 and 10 nodes), not tested; the exposure ranking inherits the E21d counts; the epic's fourth acceptance criterion, user feedback, cannot be met in one day and is reported as open; every judge and reader remains the same model family as the author.
