## One system, multiple clocks

A controller provides authenticated API and HTTP entry points and coordinates model-scoped state and agents. A model associates its own identity, life, cloud, region and possibly credential with that controller (`apiserver/facades/client/modelmanager/modelmanager.go:1061-1100`); many models can have different settings and permissions while sharing a controller. A request's principal, target and access level matter independently of the model's state: permission levels differ by target kind (`domain/access/service/permission.go:34-64`; `core/permission/access.go:86-105,129-140,169-206`). Model command blocks are separate model controls: only calls that consult a block check inherit its restrictions (`apiserver/common/block.go:51-80`; `apiserver/facades/client/block/client.go:45-110`). A controller-only login, model type or maintenance can further restrict dispatch (`apiserver/root.go:496-551,599-635`); registered does not mean callable. CLI local context, plugins and remote API are not the controller's model state (`cmd/juju/commands/main.go:215-266,303-320`).

Credential removal illustrates both coupling and synchronous effects: the traced API checks credential-owner authority; removal without force refuses a credential used by any model, while forced removal clears the affected models' credential references in the same transaction that deletes it (`apiserver/facades/client/cloud/cloud.go:597-628`; `domain/credential/service/service.go:380-412`; `domain/credential/state/state.go:813-867`). The separate credential-update path checks cloud authentication type but its per-model connectivity validation currently returns no errors without checking the model (`domain/credential/service/service.go:323-372`). Neither fact proves the result of a later provider call. See `held-out-115.md` for the registered outcome and limits.

A charm is a reusable declaration and executable workload logic; an application is a model's deployment of a charm, and units are separately managed members of that application. Their lives are coupled, not identical: adding units targets an application and the traced AddUnits path rejects CAAS; removal of one unit and removal of its application take distinct paths (`apiserver/facades/client/application/addunit.go:23-47`; `domain/removal/service/unit.go:85-125`; `domain/removal/service/application.go:86-130`). Configuration also has several scopes: a charm declares options; an application has values, while model and controller configuration govern other scopes (`domain/deployment/charm/config.go:30-140`). A bundle is an input to deployment, not the resulting application; its full execution semantics remain untraced here. Charm resources have distinct model/application/unit download and upload authorization (`apiserver/apiserver.go:895-916,971-985,1122-1134`). External charm behavior cannot be predicted merely from Juju's declarations.

Application trust is a separate application setting, not a user-to-model grant: updating config extracts trust, and the unit cloud-spec access path reads the application's setting (`domain/application/service/application.go:1514-1541,1906-1922`; `apiserver/facades/agent/uniter/access.go:66-87`). In the traced Kubernetes path, a settings watcher leads the provisioner to request the provider apply roles; an error can prevent that application (`internal/worker/caasapplicationprovisioner/application.go:223-225,430-447`; `internal/worker/caasapplicationprovisioner/ops.go:443-463`; `internal/provider/kubernetes/application/trust.go:73-80,91-125`). The desired setting is not proof of completed provider authorization.

A charm declares endpoint role, interface, scope and limits; an application realizes and binds its endpoints. A relation composes endpoints of participants; it is not either participant's endpoint. Relation creation infers endpoints (`domain/deployment/charm/meta.go:195-204`; `domain/relation/state/relation.go:80-111`); subsequent unit entry requires an alive relation, an alive unit and membership of its application, with further subordinate checks (`domain/relation/state/relation.go:2045-2098`). Relation application and unit settings vary per participant: `relation-set` selects a scope, checks leadership for application settings and writes or deletes keys (`internal/worker/uniter/runner/context/relation.go:42-62,96-134`; `internal/worker/uniter/runner/jujuc/relation-set.go:163-200`). An offer makes selected endpoints available to another model, whose remote controller and access conditions are further dependencies (`cmd/juju/crossmodel/offer.go:55-83`). Matching endpoints therefore does not by itself guarantee unit scope entry or remote propagation; timing and complete remote failure behavior are not established by these traces.

Cross-model relation ingress further couples relations to networking: the service validates CIDRs against a supplied whitelist and state rejects insertion for a non-alive relation (`domain/crossmodelrelation/service/relation_network.go:57-74,96-116`; `domain/crossmodelrelation/state/model/relation_network.go:27-64`). The machine firewaller separately filters remote-relation ingress by local application and uses model `SAASIngressAllow` as a fallback if more than 20 merged CIDRs remain (`internal/worker/firewaller/firewaller.go:1221-1262`). These conditions do not demonstrate a provider firewall or reachable application.

A unit agent reacts to state and runs charm hooks with an execution context (`internal/worker/uniter/runner/runner.go:320-344,381-388,546-561`). A watcher can deliver relation-unit changes (`apiserver/facades/agent/uniter/watcherrelationunit.go:104-139`), but is not the cause of every hook: a timer advances update-status state and the resolver selects the hook when it has no earlier eligible work (`internal/worker/uniter/remotestate/watcher.go:515-518,679-688,720-729`; `internal/worker/uniter/resolver.go:362-390`). Hook-command availability and success depend on event context, not just registration (`internal/worker/uniter/runner/jujuc/server.go:38-107,192-203`; `internal/worker/uniter/hook/hook.go:81-140`). A charm action declaration is not a run: action invocation and administrative command execution create operations with tasks under different permissions; exec can target machines as well as units (`apiserver/facades/client/action/operation.go:32-98,241-261,296-310`). Enqueuing does not prove a task finished or succeeded.

Secrets are separately identified, revisioned model data; a backend stores content when supported and varies independently of a secret's identity (`domain/secret/service/service.go:268-321,323-346`; `apiserver/facades/client/secretbackends/secrets.go:35-58,171-184`). URI and label are shared vocabulary, but selector precedence and validation differ by call (`work/surface-probe-111.md`). Backend failure and external availability constrain behavior. A lease coordinates claims within a namespace/model; leadership is a particular application/unit relationship, not a synonym for every lease (`internal/worker/lease/manager.go:242-263,284-316,331-338`). No generic expiry or failover timing follows from that slice.

Machine-model placement combines requirements and location requests but neither is a promise of infrastructure: on the traced machine creation path Juju merges model and request constraints, sends a provider directive to provider precheck only for provider placement, then persists the effective constraints (`domain/machine/service/provider.go:191-219`; `domain/deployment/placement.go:72-116`). Provider availability and capabilities can still prevent allocation. Cloud, region and credential are distinct dependencies; actual provider authorization was not exercised. Machines, cloud instances and containers are not interchangeable; model type changes the available paths. A space is not a subnet, zone or network interface: subnet listing filters by space and zone, while removing a space has separate binding and constraint checks (`apiserver/facades/client/subnets/subnets.go:67-69,111-148`; `apiserver/facades/client/spaces/remove.go:22-80`). Network interface data in status may be empty before machine deployment (`apiserver/facades/client/client/status.go:926-949`). Exposure and model firewall settings are different controls; their provider effects are conditional (`internal/worker/firewaller/firewaller.go:1176-1262`; `cmd/juju/firewall/setrule.go:86-107,126-153`). SSH keys and the SSH server/transport are distinct from machine provisioning; image metadata is a separate provisioning input (`apiserver/facades/client/sshclient/facade.go:92-102,111-158`; `domain/provisioner/service/imagemetadatafetcher.go:95-184`).

Storage spans the workload and infrastructure. A model pool is reusable provider configuration; an instance has an identity and backing filesystem and/or volume; attachment relates an instance to a unit and entails machine-side attachments. Pool selection can generate multiple instances; attach validates the unit, storage, charm and machine; detach schedules removal of a relationship rather than simply deleting the instance (`domain/storageprovisioning/unitstorageargs.go:127-142,183-235`; `domain/application/service/unit.go:390-445,470-535`; `domain/removal/service/storage.go:258-317,385-475`). These are distinct contracts even where one operation affects more than one. On the traced EBS-backed filesystem path the filesystem is machine-scoped but its volume and resulting ownership are model-scoped; forced machine removal schedules attachment cleanup without selecting that instance and volume for destruction (`domain/storageprovisioning/provisioning.go:90-138,147-170`; `domain/removal/state/model/machine.go:158-225,246-299`). Forced jobs may outrun provider detach. Thus neither a machine-local mount nor a successful request establishes data loss or survival; no EC2 removal was run.

A model's status is a composed observation, not the same object as its desired changes or proof that all agent and provider work completed (`apiserver/facades/client/client/status.go:126-174,926-949`). Logs and telemetry are additional observation paths with their own endpoints and context (`apiserver/apiserver.go:864-885,1074-1085`; `internal/worker/controlsocket/worker.go:287-321,342-354`). Database records and object-store objects are different stored artifacts; backup exports controller and model databases and includes objects (`internal/worker/backupcreation/creator.go:153-205`). Controller backup is an administrative multi-artifact mechanism, not a database-only synonym; consistency and restore behavior are not proven. `juju-db-repl` requires agent identity/configuration and can modify state (`cmd/jujuagentd/agent/dbrepl.go:74-150`); `dump-db`'s traced server method is not implemented (`apiserver/facades/client/modelmanager/modelmanager.go:566-573`).

Removal, scaling, migration and upgrade cross subject boundaries. Removing a unit, application or machine can schedule different cascades, subject to force and storage options; a returned request is not proof of completion (`domain/removal/service/unit.go:85-125`; `domain/removal/service/application.go:86-130`; `apiserver/facades/client/machinemanager/machinemanager.go:442-455`). Model migration involves source controller, target controller and model (`apiserver/facades/client/controller/controller.go:623-665`); upgrades can change maintenance access while agents roll forward (`apiserver/root.go:496-525,544-551`). The scope and timing of each cascade, migration or rollout need their own path evidence, not a universal ordering inferred from the word lifecycle. Scaling and HA are distinct properties with platform-specific implementations; a particular unsupported HA method is not proof that HA is absent (`apiserver/facades/client/highavailability/highavailability.go:42-47`).

**Deduction and limit.** A valid request to attach an existing instance may later be followed by a detach that removes its attachment while preserving the instance; it does not imply the pool or all other attachments disappear. Whether attach is valid, the job completes, and the provider permits reattachment remains conditional. Likewise, a provider precheck can reject a machine even after constraints merge, and an alive endpoint match does not guarantee unit entry. These are deductions from the paths cited above, not live demonstrations or universal guarantees.

## Structure derived from the model, before looking at the TOC

A **semantic address** is a stable linkable place for a contract, not necessarily a separate file. Distinguish independently varying, observable subjects (controller/model; application/unit; secret/backend; pool/instance), relationships with participant-dependent behavior (relation; storage attachment; user grant), and shared cross-subject mechanisms (watcher; removal; migration; task/operation). Each needs a stable address if its behavior matters on an included surface. A specific grant is an instance of the access relationship; an application's endpoint binding is its facet; a charm's endpoint declaration and relation composition are different contracts. The evidence supports separating their meanings, not a unique file for each. Prefer an existing subject home for a local facet, a neutral mechanism home when a participant home would falsely imply exclusive ownership, and explicit links among participants. If more than one home is defensible, record the tie; do not infer ownership from SQL, package, worker, facade, command name, reader question or independent ID alone.

E59's disk-inventory challenge failed its registered supported-observation evidence criterion: machine-agent collection and provisioner use alone do not establish that a reader can meet the inventory item. This does not prove there is no such surface. Independent internal state is not sufficient for inclusion; the supported surface and relevance gate must also be met. Its credential challenge did not establish the predicted downstream provider behavior, and its model-reference clearing is synchronous, not evidence that all consequences are asynchronous (`held-out-115.md`).

Facts shared by calls belong to the shared subject or mechanism; call-specific caller, conditions, error and result belong with that call. A cascade needs the initiating rule and a link to the affected subject; link rather than repeat its full contract. Conditions, precedence and observability distinguish synchronous refusal from asynchronous progress and provider-dependent consequences. Questions test relevance and coverage only. One home is an editorial convention, not a proof of navigation performance; a physical page versus anchor is also a convention unless evidence distinguishes them.

**Conditional entry parts in the user's settled order:** define the subject and its scope; provide relevant stored records/invariants; applicable change streams; actors and their inputs when needed; interactions/operations with triggers, permissions, rules, outcomes and asynchronous effects; then configuration and failure indexing where applicable. Define local vocabulary and shared semantics before the claims that require them, or link it. These roles are not mandatory headings; omit inapplicable parts. Mechanisms and tools follow their own dependencies; migration exceptions link the process. This records the chosen causal-chain ordering (`structure-discovery-plan.md:890-892,1169-1170`), not a claim that all behavior follows database → watcher → actor: the timer-driven hook is a counterexample. Entry order is not a runtime sequence or a demonstrated reader-performance improvement.

## Limits

The connected model covers the named system scope but is not an exhaustive facade, provider, permissions, error, hook, output or external-integration audit. Several categories above rely on representative traces, not complete contracts. No new live controller, provider, charm or removal job was run. Relationship propagation, remote failures, real-world completion, backup restore, complete migration/upgrade rules, platform capability and data survival remain open. Later tests must pre-register predictions before inspecting their cases; finite passes cannot prove complete coverage.
