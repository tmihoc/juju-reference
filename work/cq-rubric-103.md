## 1. The inclusion test (a fact stays iff all three hold)

1. **Quality (Grice I):** true, traced to the code on a supported surface.
2. **Surface:** exposed via CLI output, the API wire, status, an operator log line, or DB tooling (`juju dump-db`, `juju-db-repl`, backups).
3. **Relevance (Grice II, via competency questions):** it answers a recorded question of a named audience, and each question has exactly one owning section.

Filter only — never structure. The axes cut independently: surface-without-question → relocate to the page whose question it answers (the migrating marker: model.md → model-migration.md); question-without-surface → restate at the surfaced level ("how is the leader picked" → "the unit holding the lease"); neither → the code.

## 2. The audiences (verified derivable from the Caller taxonomy)

| Audience | Their competency questions | Grounding Caller forms (of 201 lines) |
|---|---|---|
| **Operator** (human via any client; reads status/logs) | What is X? What can I do to X, and who may? What states can X be in, which follow which? Why did this fail and what do I do? What happens to X during maintenance (migrate, upgrade, destroy)? Where do I see X's state and what do its log lines mean? | "A client, for a user with … access" (~90) |
| **Client/tool developer** (human or AI writing against the controller API) | Which calls read/change X, with what request, result, error shapes? What access does a call need? What invariants must my tooling respect (uniqueness, allowed values)? How do I subscribe to changes of X — which watcher, what does each delivery carry? What exact strings/codes can the wire return so my client can branch? | the same client lines + wire/error surfaces |
| **Charm developer** (client = the unit agent; hook commands, ops library, statuses, leadership) | What hooks fire for my charm, and why does each fire — which change, how promptly, why coalesced? What may my charm read or change, with what rules and errors? What statuses can it set/receive, which values? Am I the leader, how do I check, what comes with it? What happens to its world during maintenance? | "A unit agent, for its own unit." (22), "The action code of a running task" (4), hook-command pages |
| **Storage/incident inspector** (operator/support with DB access: dump-db, db-repl, backups) | What records make up X's storage, in which database? What must always hold of those records, so a dump can be judged sane? What bookkeeping does the storage layer itself keep (change log, watermarks, sequences)? | "A shell on a controller machine, where the `juju-db-repl`" (1); the `For Juju developers` dropdown's actual service |
| **AI reader** (agent answering questions about Juju or driving a client) | Inherits the union; its demand is answerability: one owner per question, linked vocabulary, no undefined jargon (recipe :34 is its rule). | all forms |

**Excluded: Juju developers** — the code is their doc. The one honest exception: `howto/manage-the-databases.md:282`, dropdown "For Juju developers: View change stream" — passes the surface test via `juju-db-repl .change-stream`; it answers the inspector's deepest question and is honestly audience-labeled. Singular, not a pattern.

The charm developer's set is bounded: Juju's behavior *toward* the charm, not the craft of writing one (that lives in the ops/charmcraft docs, linked via intersphinx).

The change-streams sections are not all the charm developer's — the holder named in each page's opener decides the reader. Where the unit agent holds watchers that fire hooks (unit, relation, link-layer-device, storage, secret — and the model-configuration item wherever it appears), the section answers the charm developer's hook-timing question. Where controller workers hold them (controller, machine, external-controller, offer — the consuming side is a worker whose charm sees the result through relation hooks — application, charm, agent-version, log, telemetry, cloud, controller-upgrade), the section answers the operator's debugging question (what does my controller watch, why did it act) and the tool developer's. The machinery's own streams (database.md) answer the inspector's. The family's invariant is the question's shape — what changes to this entity can a holder follow, and what does each delivery carry — not the reader; the per-page holder attribution in each opener is the relevance justification done in the text.

## 4. DECIDED (session 103) — charter amendment resolving the doc.go tension

**The audit of `docs/agents/` (identical in the 4.1 anchor and our branch):** the doc.go discipline IS captured — in `AGENTS.doc-dot-go-rules.md`, nearly verbatim: the Locality Principle sends cross-package concerns "to the package that directly embeds all related packages or in project wide documentation where directory distance is greater than 1" (:5-12) — that second arm is the charter's "bubbles up" clause; "Document contracts, not implementation … Never describe internal mechanisms (locks, goroutines, data structures)" (:134); "Verify claims against code … If unsupported: remove the claim" (:157-162); "When in doubt, omit" (:32). What the rules never state — because at package level the Go toolchain supplies it for free — is the enforcement: godoc renders only exported identifiers, and its readers are package users by construction. Prose has no compiler. So the docs/ tier inherited the rules' letter and lost the toolchain, and two gates were never restated: the visibility rule (the prose equivalent of export = the surface test) and the reader definition (= the CQ rubric); plus the one-home rule locality implies but never says (a scope, not a single owner, for each fact — the duplicate-facts problem). The germ is already in `AGENTS.documentation-landing-pages.md:198` ("Domains of concern that are architecture-facing instead of user-facing" listed as a content gap) — but scoped to landing pages only. And `AGENTS.documentation.rules.md:433-444` orders reference pages "broad to specific" ending at "technical implementation details … Database implementation (Dqlite technical details)" — an unbounded license for implementation depth; correct for the owning mechanism page (database.md), wrong unbounded.

**The decision (derived, not proposed):** docs/ is the project-wide tier of the doc.go Locality Principle, so the doc.go Writing Guidelines apply to it verbatim, plus the two toolchain-supplied gates restated for prose. The surface test is the prose tree's export rule; the CQ rubric is the reader definition godoc gets for free; one owning page per mechanism is locality's prose equivalent. The charter was incomplete, not wrong — it quoted the locality ladder's top tier without the writing guidelines that bound every other tier.

- Interface projection passes the surface test (§1).
- Bubbled-up architecture stays at **mechanism level** (what happens, who drives, in what order, where it surfaces), in **surfaced vocabulary** (facade names, log modules, wire strings), **answering a recorded question of a non-developer audience**, with **one owning page per mechanism** (watcher.md, database.md, model-migration.md). Code artifacts (tables, columns, internal markers) belong to the storage page only, and only where the tooling surfaces them.

**Amended charter wording:** "docs/ is the top-most doc.go: it documents what the codebase exports — everything projected onto a user interface (CLI, API wire, status, log lines, DB tooling) — and the cross-cutting mechanisms no lower-level document can own, at mechanism level, in surfaced vocabulary. Everything else is implementation and lives in the code."

**Consequences:** no batch verdict flips; Batch 2 (model-migration restructure) is the first page authored under the amended charter.
