## The system we are documenting

Juju is not one linear chain of database change -> watcher -> hook. A partial operational graph, traced from 4.1 source, is:

- A client can request model and application changes through controller calls (`apiserver/apiserver.go:442-453`, `apiserver/root.go:599-635`, `apiserver/facades/client/application/application.go:293-324`). Requests can be rejected based on authorization, input or context.
- An application and its units are related but distinguishable: adding units targets an application and yields unit names (`apiserver/facades/client/application/addunit.go:23-47`); removing a unit and removing an application schedule different cascades (`domain/removal/service/unit.go:85-125`, `domain/removal/service/application.go:86-130`). Their platform conditions differ: the exposed AddUnits method rejects CAAS models (`addunit.go:34-38`).
- An application exposes named endpoints derived from charm metadata; a relation is made between inferred endpoints (`domain/deployment/charm/meta.go:195-204,263-266,576-579`, `domain/relation/state/relation.go:80-111`). A unit can participate in a relation only subject to relation/unit life and application membership (`domain/relation/state/relation.go:2045-2088`). A relation is not simply an attribute of either application, and an endpoint is not the relation itself.
- Resource requirements, explicit placement and cloud provisioning are different inputs/effects: machine creation merges model and machine constraints, and passes a provider placement directive to the provider's precheck when its type is provider (`domain/machine/service/provider.go:191-217`); placement parsing distinguishes machine, provider and container cases (`domain/deployment/placement.go:72-116`). This evidence does not establish every provider's placement precedence or successful provisioning.
- Secrets and backends have distinct behavior: a user secret's content is saved via a backend, with an external reference when appropriate (`domain/secret/service/service.go:268-321`); backend creation and removal are independently callable (`apiserver/facades/client/secretbackends/secrets.go:35-58,171-184`). Backend support and availability are conditional. A backend may serve multiple revisions; a secret and its backend are not the same thing.
- Changes can reach a unit agent via watchers: a relation-units watcher observes changes and delivers a change payload (`apiserver/facades/agent/uniter/watcherrelationunit.go:104-139`). The agent also has a periodic timer that updates the update-status version (`internal/worker/uniter/remotestate/watcher.go:515-518,679-688,720-729`), and the resolver selects update-status after earlier eligible work (`internal/worker/uniter/resolver.go:362-390`). A watcher and a hook are different mechanisms with different conditions; one is not a mandatory prerequisite for every instance of the other.

This graph is a source-traced slice, not a full topology or proof that every change follows one route. Storage, status, logs, CLI, backup, HTTP, remote controllers, migration, many provider paths and the range of model types still require discovery. Architecture prose and existing page titles are orientation, not proof.

## Derived structural procedure

1. **Discover the subjects and interactions.** Follow supported surfaces into the running behavior: actors, managed things, relationships, reusable values/rules, processes, interfaces and observations. These are discovery lenses, not mutually exclusive mandatory page types. A source item is a lead, not automatically a topic; exclude internal-only detail under the established surface/relevance gate.
2. **Separate things that can differ in the system.** Record what each candidate denotes, its context, how its state or behavior can differ, and what it affects or is affected by. Independent identity or life is useful evidence, not mandatory or sufficient. A shared rule or relationship may have no independent lifecycle; a dependent unit can still have distinct behavior.
3. **Assign an address, then a file level.** A subject with a stable meaning and behavior reused across contexts, or a relation/mechanism with its own contract, deserves a stable reference address. A context-bound facet belongs at its parent with an anchor unless its independently varying contract warrants an entry. A named address can be a page or a section: the evidence does not mechanically force a file. Prefer a standalone page for a distinct subject with its own observable lifecycle/contract or a reusable cross-subject concept, especially where embedding under one participant would imply false ownership; use an anchored parent section for a locally scoped facet. Record a tie if these criteria conflict, instead of using page length, a table key or a list of questions to manufacture certainty.
4. **Place facts at the subject or interaction they describe.** General behavior belongs with the common concept or mechanism; behavior particular to an interaction belongs with that interaction. Relation-owned facts go with the relation; participant-owned facts stay with the participant. References from other subjects supply paths without repeating the contract. The direct object of a change is a useful lead, not an infallible owner: cascading effects must link both the initiating call and the affected subject, and multi-party rules can be tied. Do not move or duplicate a fact merely because several audiences or questions need it.
5. **Order by semantic dependence, not a physical execution layer.** Begin an entry by identifying what the subject is and its boundary. Define a local term before relying on it, or link its definition. Present state, relationships and shared semantics before a later claim that depends on them; describe an interaction with conditions, actor, permitted outcomes/errors, effects and observable timing where relevant. Link independent mechanisms, storage and observation at their natural dependency points. No evidence here forces a single total order of schema, change streams and calls: independent aspects admit more than one valid order. Use meaningful subject-specific headings and the established conventions where they fit, rather than requiring every role as a heading.
6. **Enable deduction, not false certainty.** State precedence, scope, defaults, lifecycle and error placement where they change an observable outcome. Describe concurrency, asynchronous scheduling, provider-dependent behavior and partial failures at their real limits. Facts needed to interpret a contract must be locally stated or linked; one fact, one owner does not mean a reader has to guess a missing cross-link.

The stable semantic address, single fact ownership and semantic-dependency ordering are proposed conventions derived to serve navigation and consistency; they do not mathematically follow as unique physical file layout from runtime behavior. The exact split and tie-break for every possible subject remain unproven.

### Proposed default reading order

Use this as a candidate navigation convention, not a claim that the source code proves a unique total order:

1. **Definition and boundary:** identify the subject and its relationships to neighboring subjects.
2. **Structure and shared semantics:** introduce constituents, vocabulary, states and invariants that apply across the subject's behavior. Use specific names, not mandatory generic headings.
3. **Behavior and interactions:** describe lifecycle or process transitions and calls as applicable, with their conditions, outcomes, errors and consequential effects. Put shared mechanics in their own entry and link them; retain local differences here.
4. **Observation:** where independently relevant, describe how status, streams, logs or other supported surfaces reveal the subject and its changes. State timing and limitations.
5. **Persistence:** where independently relevant to inspection, describe the externally inspectable stored representation and its storage-enforced invariants.

Omit inapplicable parts and order any actual dependent explanation after its prerequisite; a link can supply that prerequisite. Tool, concept and process entries follow their own subject's dependencies rather than imitating an entity. Cross-cutting process rules belong with the process; subject-specific effects can be linked and situated where they matter. The schema/streams/calls sequence in the current recipe is an existing convention; changing it to this candidate requires authorization and comparative validation. In particular, no finding here proves persistence must be last or that behavior must precede observation.

## Registered fresh boundary challenges

- **Storage pool vs storage instance: supports the prediction.** Pool creation names a model pool and provider (`apiserver/facades/client/storage/pool.go:58-90`); a storage directive associates a pool with a count of storage instances and the provisioning path creates instance arguments for that count (`domain/storageprovisioning/unitstorageargs.go:17-45,127-142,178-220`). Pool semantics are reusable across instances; an instance is not the pool. Candidate: separately addressable entries linked by provisioning. The specific 4.1 create path does not establish every update/remove operation or runtime behavior on every provider.
- **Access vs individual grant: supports the prediction with a qualification.** Permissions connect a user, a target and an access value (`domain/access/service/permission.go:34-48,94-109`, `domain/access/types.go:16-27`). Object kinds include cloud, controller, model and offer, but valid access levels differ by kind (`core/permission/access.go:86-105,129-140,169-206`). Thus the reusable access contract is independently addressable; a particular grant is an instance of the user-target relationship. Do not imply a single identical set of levels or precedence across targets.

Neither case proves a globally complete partition or a unique physical file split. Both were traced only after their predictions were registered; they remain deliberately chosen boundary probes.

## A behavioral deduction, exercised within its limit

For the default constraints validator, model fallback `arch=amd64 mem=4096M` merged with specific `cores=2 mem=8192M` yields `arch=amd64 cores=2 mem=8192M`: the specific memory value overrides the fallback, while unspecified architecture falls back. `core/constraints/validation.go:336-345,365-387` defines this, and a throwaway Go program invoked `constraints.NewValidator().Merge` and observed exactly that output. Application resolution passes model and application values in that order (`domain/application/service/provider.go:957-981`). This demonstrates the merge behavior, not successful cloud allocation, a live controller, or the semantics of a provider-specific validator with additional conflicts and validation.
