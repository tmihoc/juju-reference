# Skeleton v6 for reference pages (proposal, session 80, 2026-10-20; rewritten from `claims-ledger.md`, E40)

Status: proposed, not ratified. Every rule cites a ledger row (`Cnn`, in `claims-ledger.md`) and through it the experiment in `structure-discovery-plan.md`. A bare `Cnn` is a row that is supported, a user decision, or a convention. **`Cnn*` marks a row that is partial: the finding was checked, but a registered criterion was missed, the basis is a judge or precedent, or a post hoc reading carries part of it; read the row before relying on the rule.** A rule whose row is falsified or open is not in the page tables: it is under its own heading with what is missing. Nothing on a page changes until this file is proposed and agreed (rule 5 of HANDOFF).

## What the evidence supports
1. **Parts are conditional on artifact classes, not typed templates** (C01, C02). Over 36 domains only state is universal; 28 distinct part sets; typed templates need 10 types for 81% accuracy.
2. **Spine for a topic that earns a page: identity, state, interface, dynamics, failure** (C03). Present in 15 of 15 topics of three registered fit tests on unseen topics; the 15-domain census is a post hoc cut.
3. **No topic labels** (C14). Identity states facts, each when true.
4. **Statements come from the code through a gate** (C10*): 94% of claims on old pages are code-decidable, 28% of those fail on unseen pages, 10% on the page written with the pattern (C59*). Every statement cites an artifact or is tagged `convention`.
5. **The schema typing (life, status, watched, immutable, lookup) is version-stable and exact** (C05*).
6. **Page list** (C45*, C46*, C44*): 39 pages, 264 tables, one home each, associations homed by the table name and pointed to from the other page. No mechanical rule reaches 10% misplaced tables (first word 37%, writer domain 63% right, schema file 79% right), so the list is reviewed, not generated.
7. **Level of a table group** (C52*, C53*, C63*): a table with a foreign key in its primary key is a section of its owner's page (142 of 153 homed so; judge 17 of 20). A strong group with one mandatory owner and no dependents is an anchored section of that owner; with dependents it is a page (12 sections, 33 pages of 45 chunks, stable on 4.0.15). Of 33 groups with a level in all of the E35 judge, the E43 judge and that rule, 23 agree: six sections (`machine-placement`, `application-scale`, `port`, `unit-state`, `model-defaults`, `cloud-instance`) and 17 pages. Those are the levels this skeleton can state; the other ten are in the open list.

## The page

Order: identity first; state before dynamics and failure; dynamics before failure (C29*, from 44 presupposition pairs, judge). Beyond those, the user's causal chain: records, change streams, agent, operations, then configuration (C30, user decision).

## Rules on entries
- **Operation entries** state authority as a value with a kind: required level (72% explicit), caller-scoped, owner by tag, none beyond login, inherited, or parameter-dependent (cloud credential update with `force` needs a controller admin, `cloud.go:529-533`) (C25*). They state the block kind chain (`RemoveAllowed` also checks the change block); an operation that checks no block says so (C26*, asymmetry not yet re-verified).
- **Unavailable methods** (all answers not implemented, not supported or not yet available) are listed as unavailable, never as operations: client watchers, `RemovePool`, `UpdatePool` (C21, C38).
- **Migration** states the generic export, the exclusion list (at least 15 tables), the legacy 3.6 import operation where registered, and ordering dependencies between import operations (C06*, C31).
- **A guard one entity imposes on others** (block commands) is stated once on its own page with a pointer from each affected operation (C41, convention).
- **Status** is three things: per-entity status tables (12 `*_status` tables in the model schema), the history log store, and the full-status read model (C39).
- **Controller-scope lifecycle entities** have no removal job: the controller node record is deleted as a step of removing the controller application's unit; the object store backend's life column drives its drain (C40).
- **Operation, task, action** are one table set and one noun (C34).
- **Shared tables** have one home and a pointer (C37, C46*).

## Rules with a missing piece (partial)
- **Configuration key home** (C27): home is the page of the entity the key configures. Untested on topics with keys; the red team found three tie-breaks needed (storage pool attributes, the model secret backend setting, `storage-default-block-source`).
- **Applies-to clause** (C15): the 'at least three entities' rule has no validated implementation (E26 failed, E26b and E33 R4-prime were tuned after seeing results).
- **Levels that split** (C63*): both judges say part of one parent while the schema rule says page for `agent-version` (model), `application-endpoint` (application), `external-controller` (offer), `link-layer-device` (machine), `relation-unit` (relation), `telemetry` (controller): none has a single mandatory owner (four) or has independent create and remove operations (E37; two). `charm`, `subnet` and `resource` split because address and lifecycle disagree: `charm` and `resource` are removed only as a side effect of application removal or by a retried job; no user operation creates or removes a `subnet`. The user's rule, kind decides, is what decides these nine. **Accepted by the user, 2026-10-20 (session 82): "Kind decides the level -- I accept that."** The levels of the nine are not yet derived; applying the rule needs the kind of each group written down first.
- **`permission`** (C64*): a concept page across controller, model, cloud and offer, not a section of user (`grant_on` is an untyped string, so the schema hides the second owner); `ssh-key` is a section of user by the rule and a character by both judges, because `model_authorized_keys` references it. The post hoc rule variant (association dependents make a page) fits `ssh-key`, `resource` and `model-migration` and is untested.
- **Storage directives** (C54): the weak-table rule homes the two directive tables on application and unit; E34 moved them to storage by precedent. By the 2026-10-20 correction the key rule decides, pending the user's acceptance of manifest v3.
- **Page list** (C45): the blind placement held in a harder form: 243 of 264 (92.0%) with page names only and judges that cite the code, against 255 of 264 with shallow judges and descriptions. Of the 21 disagreements 17 are decided for the manifest by the weak-table rule; one manifest error remains (`application_remote_offerer_relation_macaroon`, a weak table of relation, homed on offer: on the v3 list) and two tables have two defensible homes (`block_device`, `model_namespace`). Still the same model family as the author, and the M4 failure stands (new nouns need review).
- **Level labels** (C47*, C50): the character-or-leg rubric now rests on two judges of one model family, one with the user's metaphor and one without (38 of 45 agree, 6 of 6 controls); kind decides level (user position), mass does not.

## Open

- **Failure part** (C24). Errors are authored once under the operation or rule that raises them; the lookup by message is one generated index keyed by what the client sees. Whether a page has any failure part is undecided; no page carries an error section until it is.

## Session 82 decisions on the page form (user, 2026-10-20; proposed in discussion, accepted as the working form for the pilots; not tested on readers)
- **No Identity section.** The lede is a tl;dr: what the thing is, where it lives, how it comes and goes, what it attaches to. Lifecycle detail sits where the facts are: creation and removal under operations, the life column and its rules under the data model. Reason: the Identity part was never tested as its own section (C13*, C15*), and one sentence could belong to it or to the data model, which invites drift.
- **Every section opens with a one or two sentence definition**, never a bare bullet list. Order within a section (user, 2026-10-20): the figure first, because a figure sits at the top of its section as a redundant preview that stands on its own (its caption and alt text carry every fact it shows), then the definition, then the body. A bullet list never appears without a main-text introductory sentence before it, and a list of one item is prose.
- **Section titles carry the entity** (`<Entity> data model`, `<Entity> change streams`, `<Entity> operations`, `<Entities> and model migration` for the exception, so that the title says a model migration affects the entity and not that the entity migrates); configuration, removal and the migration operation are subsections of operations. Agent and workers sections of the pilots are open (C23). Check: `experiments/e46/check_titles.py`.
- **One data model figure per page, no separate neighbours figure.** Records show only primary and foreign key columns so that ggarch draws the 1 and m cardinalities (they are computed from declared columns; hand-written label-only records draw none). Neighbour entities from other pages are collapsed key-only chips. ERD lower bound of 4 tables dropped; the upper bound of 12 (split by section) stays.
- **Table names** stay out of bullet titles and figure labels (no client interface shows them; E44 `internal` questions scored 0 on both page versions). One closing sentence of the data model section lists the tables for readers of the database shell. Plain nouns name the boxes, with the table in the node's `ground`.
- **Reason for the structure is maintainability** (drift check by script, generated parts, version-stable page list C05, C63); E44 did not show a reader benefit and the structure-free control is still not run.
- **Jargon is linked or defined at its first mention in each section**, not only on first mention in the page, because a section is often read alone (an AI reader gets a heading-sized chunk). Link to the entity's reference page, the access-level anchor or an external definition, never to a CLI command page (reference pages are client agnostic: the interface is the API and the platform's behaviour, the `juju` CLI is one client and appears only as an example, without links); where no page exists, give a short parenthetical definition (a facade is a group of related API methods). Applied to the `ssh-key` pilot only.
- **ERD context boxes.** In a page's data model figure, the page's own tables are `record` chips (solid border, record badge) and records that other pages own are drawn as `context-record` chips (solid border and an outlined corner arrow, "described elsewhere"; the dotted border stays the entity's meaning in the architecture diagrams); every box has the same size (`same-size` constraints). Each box has a bullet or is covered by one bullet that says other pages own it. Chip labels are plain nouns that match the bullet titles; the table name is in the bullet in parentheses and in the node's `ground`.
- **Operation subsections are titled with a gerund nominal and the entity** (`Adding SSH keys`, `Importing SSH keys`, `Listing SSH keys`, `Removing SSH keys`) and ordered as in the how-to guide for the entity (add, import, view, remove). The how-tos use plain imperative verbs (`Add an SSH key`); the gerund keeps the reference title distinct from the how-to title while sharing its keyword. Each opens with a sentence whose subject is the gerund ("Adding SSH keys stores ..."). The platform's verb for removal is `remove` (the API method says delete). Applied to the `ssh-key` pilot only.
- **Sections are self-contained; chronology lives in sequence diagrams (user observation, 2026-10-20).** The ADR-016 DPE form (declaration, persistence, execution) coupled each fact to a step in an operational chronology; data model and operations read well alone. Section order follows the causal chain as a reading path, not a dependency. An operation's order of events is carried by a sequence diagram under that operation, not by the structure of the text. Open: whether `data model` (persistence-shaped) is still code organisation rather than the running thing's logic (amendment A1); the form maps onto DPE (operations = declaration, data model = persistence, change streams and agent = execution), which I knew while shaping it, so agreement is not independent evidence.
- **Sequence diagrams are selective** (user and session 82): one under an operation only when it crosses at least three actors, at least one outside the controller or running on its own, and the order decides what the reader sees. On the `ssh-key` pilot only "Importing SSH keys" qualifies (client, controller, Launchpad or GitHub, database; steps cited to `keymanager.go:271-380`, `service.go:261-324`, `importer.go:35-62`, `state.go:293-313`). Adding, listing and removing run inside the controller. The page's import errors now carry the client-visible messages from `keymanager.go:345-380`, not the Go constant names.
- **Wording (user question, 2026-10-20):** the docs spell American (`authoriz` 55 uses against 1 `authoris`; `behavior` 83 against `behaviour` 34), so prose uses authorize, authorization and favor. The label for the access an operation needs is `Required access` (what the access levels show), not `Authority`: the skeleton's word "authority" (C25) is our coinage, and "authorize" is already used for a key on a model and for the SSH server's check. Applied to the `ssh-key` pilot only; the other pilots still say `Authority`.
- **Every opening sentence is a definition, not a description of function (user, 2026-10-20).** The page lede and each section opener name the kind of thing and what sets it apart ("The SSH key data model is the set of records that ...", "Adding SSH keys is the operation that ..."); "X is how Y does Z" is not a definition. A section about another entity's operation (model migration, user removal) does not define that operation and does not announce what it covers (no metalanguage such as "this section covers"): it states the effect on this entity in one high-signal paragraph, with the operation linked in passing as background (user, 2026-10-20).
- **No unearned negation about life (user, 2026-10-20).** The data model states life stages when the entity has them and is silent when it has none; the earlier "has no life stages" line was removed from the `ssh-key` and `cloud` pages.
